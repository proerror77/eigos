# EIGOS：本体执行契约与跨服务组合修正计划

日期：2026-10-22

状态：P0–P6 实现与受控运行验收完成；同步状态以当前分支准确提交的 CI 和最终回读为准。部署和真实下单付款不随此授权开放。

审查基线：codex/member-paotui-agent / 99ca9104c71364ce5c586299a43d18bd9410d7b3。

优先级：先完善现有 Ontology 的执行契约和跨服务组合，再增加业务模板。

## 1. 要修正到什么状态

用户提交一个目标后，EIGOS Agent 能先查询相关对象、关系、动作和真实可用性，再从多个已准入服务中选择动作；执行结果写回本体，模型根据新事实继续决策。完成判定针对整个用户目标，依据可回读证据逐项检查。

“地图健壮”应体现为：

- 知道对象是谁、属于谁、来自哪里、处于哪个版本和业务阶段。
- 知道哪些关系成立、哪些只是候选或尚未验证的跨来源身份断言。
- 知道某个动作需要什么输入、会产生什么效果、如何观察成功或失败。
- 知道当前调用者是否有来源访问权、动作是否有执行绑定，以及此刻是否满足前置条件。
- 知道一个动作的输出能否成为另一个动作的输入，并保留准确语义、版本和来源。
- 知道哪些目标条件已经满足，哪些仍然未知或失败，以及接下来可以查证、澄清或补救什么。

对象类型和关系数量只作为清单，不作为健壮性的验收指标。静态契约可以证明某种连接在类型上成立；现实中的可用性和任务完成仍需运行时事实与证据。

首轮组合范围固定为：同一任务调用者的授权上下文、一个明确固定的本体发布版本、多个已准入服务来源。跨成员私有数据共享、任意跨命名空间合并和无授权的新供应商接入不自动包含在内。

## 2. 已有底座与真正缺口

| 范围 | 当前已存在，应复用 | 本次需要修正 |
| --- | --- | --- |
| 定义管理 | Object / Link / Interface / Action 定义、草稿、不可变发布、激活、退役与审计 | 增强跨动作语义契约及受影响依赖检查，不重建定义注册库 |
| 类型与语义 | 输入类型、输入 schema、效果、变更范围、结果类型、接口动作映射、受信任校验器 | 统一可参与组合的执行契约，补齐输入角色、输出映射、条件和证据要求 |
| 事实与上下文 | owner 隔离、来源字段、对象 revision、任务版本固定、本体读取回执 | 跨服务传递引用时继续验证语义、来源、可见性和新鲜度 |
| 可用性发现 | definition_only / handler_unavailable / executable，已经区分定义与实现 | 增加针对当前任务的适用性与缺口说明，发现范围不再固定在一个程序的动作清单 |
| 动作执行 | Intent / Attempt / Observation、领取租约、取消、授权、幂等和恢复 | 从单个 program 的执行上下文转为按动作绑定分派 |

## 3. 目标运行结构

~~~mermaid
flowchart TD
    G["用户目标与不可擅改的约束"] --> O["按需查询对象、关系、动作与来源"]
    O --> P["LLM 选择下一批动作及依赖"]
    P --> V["确定性校验：类型、版本、前置条件、权限、预算"]
    V --> X["按准确 Action Binding 执行"]
    X --> E["记录原操作、观察与证据，回写本体"]
    E --> A["逐项评价整个目标"]
    A -->|尚未满足| O
    A -->|必须条件全部满足| D["完成并返回原交付物"]
    V -->|缺少事实或授权| H["澄清或准确授权"]
    H --> O
~~~

服务适配器继续负责准确调用供应商接口，领域校验器继续证明具体业务事实。它们不替模型选择跨服务的下一步。

首轮仍保持每批最多一个有副作用的动作。多服务组合可以通过多轮顺序执行完成，不必同时引入并行写入或分布式事务。只读依赖图继续沿用已有约束；是否提高并行度另由测量决定。

## 4. 实施阶段与进入下一阶段的条件

### P0：盘点现有地图与执行契约，形成可追踪缺口清单

**工作**

1. 从当前发布版本及运行目录生成 Object / Link / Interface / Action / Function / ProviderBinding 清单。
2. 对每个当前准备参与执行的 Action，追踪“目标条件—输入对象—执行绑定—结果对象—证据—验收规则”。
3. 标出纯定义、缺执行绑定、缺来源映射、缺任务授权、语义不兼容和缺完成证据；这些状态分别记录。
4. 盘点核心中的领域特例，包括包裹报价解释、付款交接、领域动作列表和专用完成判断。
5. 选择两个现有独立服务作为最小迁移样本，确定实际可用的只读或隔离测试来源。

**产物**

- 当前版本的依赖与可执行性清单。
- 每项缺口的准确位置、影响、反例和处理阶段。
- 第一条跨服务验收目标及其输入、授权边界和证据要求。

**通过条件**

- 清单覆盖准备迁移的全部现有动作，未知项明确标注。
- 已有能力和新缺口分开，不把发布、可调用和业务完成混为一项。
- 确认第一条验收链不依赖尚未获得的商家接口或真实付款权限。

### P1：把地图中的“动作说明”补成可检查的组合契约

在已有定义、DSL、受信任处理器和条件判断上扩展，不另建平行规则系统。

| 契约部分 | 应明确的内容 | 必须拒绝的反例 |
| --- | --- | --- |
| 输入 | 类型/接口、参数角色、单位、币种、地点或时间含义、来源要求 | 两个参数都是字符串就直接把取件地址接到目的地 |
| 前置条件 | 准确谓词及版本、输入绑定、所需对象状态、事实有效期 | 用自然语言描述代替程序能检查的条件 |
| 输出 | 具名结果、对象引用或受控值类型、状态、来源与实际观察时间 | 把报价当成订单，把预订确认当成履约完成 |
| 输入输出连接 | 被接受的输出引用、类型兼容、明确字段或接口映射 | 任意 JSON 路径、隐式单位换算、模型虚构中间结果 |
| 效果 | 读取、内部写入、占位、订单等明确类别及完整变更范围 | 动作声明只读，实际却产生额外业务副作用 |
| 执行绑定 | 准确处理器、供应商/渠道、配置摘要及所需来源授权 | 模型仅凭一个动作名字切换到另一商户 |
| 证据 | 可接受的来源、结果版本、原操作关联和验证规则 | HTTP 200 或模型文本直接成为完成证明 |
| 恢复 | 幂等策略、原操作查询、未知结果、可用补救动作及其权限 | 超时后直接换供应商再提交一次 |

补充规则：

- 能用现有类型、Interface 和角色表达的语义继续复用，不建立“包含所有业务字段”的万能对象。
- 未知、失败、过期和冲突事实保留区别；当前值与历史观察不互相覆盖。
- 跨来源同名或同 ID 不自动认作同一业务实体，继续沿用明确的身份断言及依据。
- 所有新条件和转换使用受限声明式规则或准确注册的版本化函数，不开放任意代码执行。
- 仅文档性或尚未接通的 Action 仍可保留为定义；只有契约完整且绑定可用的动作才能进入可执行集合。
- 不用普通 JSON Schema 往返替换已有带特殊语义的 Zod 校验器；已存在的准确 validatorRef 保持有效。

**通过条件**

正例能够准确连线；错类型、错角色、错来源、错单位、过期结果、缺证据和未知处理器均被拒绝。发布检查只验证受影响依赖闭包，不要求每次重新扫描全部实例。

### P2：形成任务范围内的统一动作发现与绑定解析

**工作**

1. 扩展现有 ExecutionCatalog，按 Action 定义解析准确执行绑定，而非先要求任务只选一个服务程序。
2. 分开两类信息：
   - 定义/实现状态：是否已发布、是否有匹配处理器。
   - 当前任务适用性：来源访问是否有效、输入是否已知、条件是否满足、是否还需准确授权。
3. 让 Agent 按目标、对象类型、关系和所需效果查询候选动作，并获得可执行或暂不可执行的具体原因。
4. 复用读取回执、权限过滤、分页和上下文预算；不把整个本体一次性塞入提示词。
5. 保留单任务本体版本固定。后续可发现新的适用动作，但不能因此修改用户约束或扩大来源权限。
6. 首轮复用类型、关系、效果和来源的可分页查询；目标匹配由模型依据实际返回的定义判断，不引入新的向量库或检索服务。目录存在但模型漏读的情况单独诊断，不用扩大上下文预算掩盖导航缺陷。

**通过条件**

同一任务能够发现两个独立服务的动作；另一个成员的私有来源、撤销连接、未配置处理器及不兼容版本不会进入其可执行集合。返回的数量、分页和错误信息也不能泄漏被过滤的私有对象。

### P3：让通用执行器按动作分派，并由 LLM 决定组合

**工作**

1. 调整 AgentExecutionState 和 AgentActionPlan：
   - 任务保留固定的请求、约束、本体发布与累计执行历史。
   - 每一步固定自己的动作定义、执行绑定、相关配置、输入对象版本和原始模型决策凭据。
   - 记录步骤对哪些目标条件作出贡献，以及步骤之间的真实依赖。
2. 将现有程序中的 schema、definition、validate、authority、invoke、recover、project 能力迁移到可按动作解析的受信任执行组件。
   同时拆解 initialize、prepareRequest、validateRequest 和 contextRefs：公共任务上下文与单个动作所需的业务上下文分开；必要的内部请求对象由明确的受管动作或受信任投影建立，不能在初始化中暗藏固定业务流程或制造来源事实。
3. 先以兼容适配方式复用供应商调用代码；业务流程选择逐步移出 program。
4. 新规划路线不再要求复制 candidate.recipe。recipe 可作为不具授权效力的建议示例；供应商一个原子操作内部必须遵循的协议顺序仍由适配器正确执行。
5. 执行完成后先保存实际观察，再让模型重新查询、判断和提议；模型不能凭上轮记忆跳过必要读取。
6. 变更或更换动作产生新的准确计划记录。已完成 Intent 和原操作身份不能丢弃或伪造成新任务。
7. 调用者直接指定的受管数据动作与 LLM 规划继续区分决策来源。caller decision 不能伪造模型运行凭据，也不能借统一目录调用外部受信任操作；实际 Agent 计划必须保留模型自己的读取和决策回执。
8. 修改当前 grounding 必须返回单个 capabilityRef/inputJson 的内部契约。先固定用户目标、必需条件和已确认输入，再按实际动作契约解析业务参数；必要技术引用通过本体查询取得，缺少业务事实才向用户澄清。

**通过条件**

用同一运行内核、同一请求，实际调用两个独立绑定；模型能在候选或结果改变后选择不同动作顺序。禁止用“组合服务”包装器把固定的跨服务步骤藏回代码里。

### P4：建立面向整个目标的完成评价

**工作**

1. 复用 ServiceRequest.requirements / successCriteria、业务 conditions、RequirementCheck 和 ConditionCheck。
2. 为每个必需目标条件绑定可检查的谓词、主体对象、阶段和证据要求。
3. 领域验证器返回各自能够证明的事实与证据，由任务层汇总。
4. 保留 pass / fail / unknown 的逐项结果；过期或冲突证据不能继续支撑当前完成判断。
5. Agent 可以提议完成，但运行时必须独立回读并证明所有必需条件满足。
6. 维持现有 MCP/A2A 任务状态兼容；部分成果放入有界、带版本的结果摘要，不默认新增公共终态。

**通过条件**

A 服务成功、B 服务失败时，返回可用的 A 成果与 B 的具体问题，整项目标保持未完成。文档生成不能替代其引用的查询、预订或履约。模型不能自行删除未满足条件来获得 completed。

### P5：补齐跨服务授权、预算、故障与恢复

**工作**

- 把权限准确绑定到实际动作与来源，继续保留 owner、任务、请求版本、参数、期限和撤销检查。
- 参数、对象状态、提供方或副作用变化时重查相应许可；原授权不能泛化为任意服务调用权。
- 继续复用现有计算预算，跨服务或重规划不能清零模型调用、计划、动作及等待累计。
- 复用金额占用台账，明确任务总约束与单步准确许可的不同含义。当前 reserveBudget 以本任务 held/consumed 累计对照当前 grant.maxAmount，组合场景必须专门验证这一语义。
- 例如任务总额度 100、两个分别获准的动作金额为 40 和 50，不能把第二步的 50 当成整个任务的总额度；同时也不能通过拆成两个许可绕过总上限。
- 同一业务承诺在报价、占位和付款阶段的预算意义要明确，避免重复计入；押金与消费金额沿用不同角色。此处只处理执行授权与占用，不增加结算清算系统。
- 未知写入结果先按原操作键查证；查证之前不得换供应商重复执行。取消停止后续派发，已发生效果与迟到回执继续如实记录。
- 补救动作必须已定义、已绑定且获准。取消或退款是新的业务动作，不假设所有外部效果都能自动回滚。
- 检查、预算占用、Intent 保存及派发围栏的事务顺序须明确，不能依赖模型规避竞态。

**通过条件**

跨服务越权、累计超限、审批后改价、撤权、取消、租约丢失、崩溃重启、响应丢失与迟到结果均有可重复反例；所有场景保留原任务和原操作身份。

### P6：迁移现有程序，清理核心特例并完成独立验收

**工作**

1. 第一批迁移两个最小的现有服务，保留专业适配器和领域证据验证器。
2. 将其余现有 AgentProgram 和固定 recipe 路径逐项列入迁移表；未迁移的能力明确标记，不宣称整个运行时已统一。
3. 包裹报价、付款交接等领域语义移到相应 Action 契约及领域模块；核心只保留通用的任务、效果、授权、等待与恢复机制。
4. 不把旧 recipe 作为新引擎失败时的隐式回退。
5. 制定新执行契约版本和切换规则：旧证据保持原版本；已完成任务继续可读；在途任务与未知业务效果先逐项处理，不能静默重解释或重放。
6. 对实际使用的 PA、MCP 和 A2A 入口分别做回归，完成准确提交的同步与 CI。
7. 生产切换另设关卡。工程验收不会自动打开真实订单、付款或尚未验证的来源。
8. 验证独立发布副本包含新旧任务所需的固定模型和定义资源；启动与恢复不得依赖源工作目录中的遗漏文件。

**通过条件**

第一条真实模型组合链通过后，继续完成迁移清单和回归，才可宣布本次架构改造完成。对外发布需要另有运行环境与真实来源验收。

## 5. 验收矩阵

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| C01 | 同一目标需要两个独立服务 | 两个独立执行绑定都有真实调用记录，并分别支撑必需目标条件 |
| C02 | 前一服务的输出供后一服务使用 | 输入来自已接受对象/结果，来源、类型、语义和版本一致 |
| C03 | 相同目标的来源事实改变 | 模型依据新回读重新选择动作或依赖，不复制原固定流程 |
| C04 | 第一服务成功、第二服务失败 | 保留已完成成果，整体不误报完成 |
| C05 | 写入返回超时、随后重启 | 查原操作并恢复同一任务；供应商写入不重复 |
| C06 | 选择到未授权来源或其他成员对象 | 在读取/派发前拒绝，目录和错误也不泄漏私有数据 |
| C07 | 许可撤销、报价或对象版本变化 | 对受影响动作停止派发并重新核验，不沿用失效批准 |
| C08 | 连续跨服务动作触及预算上限 | 总约束与单步许可都成立才执行；重规划不重置占用 |
| C09 | 同名对象、错误角色、未知或过期事实 | 不误合并、不误连线，能够指出准确缺口 |
| C10 | 仅一份总结文档或一个成功 HTTP 响应 | 不替代原服务的结果与独立证据 |
| C11 | 本体发布更新、旧任务恢复 | 旧任务使用原版本，新任务使用新版本；历史不被改写 |
| C12 | 取消或租约失效时出现迟到结果 | 不启动后续动作，也不抹去实际发生的外部效果 |

验证分三层：

1. 确定性工程回归：用明确标记的模型/供应商替身覆盖上述反例、协议与竞态。
2. 实际模型验收：真实 PA → EIGOS → LLM → 两个独立执行绑定 → 本体回读 → PA 原任务结果。外部副作用使用隔离测试提供方；测试驱动只给业务目标和范围明确的测试授权，不给动作序列或替模型填写决策。
3. 实际外部来源验收：在已有准入和成员授权成立后，使用两项真实只读来源验证。拿不到接口或授权时明确保留该关卡，不用第二层结果冒充真实服务接通。

建议首个受控场景为“从商品目录找符合条件的候选，结合已确认的重量与取送地址，形成包含商品与配送费用的比较结果”。它可检验跨领域输入输出、缺失事实处理和全目标验收，保持无下单付款。具体采用哪些现有绑定由 P0 的实际可用性决定；不为凑场景编造库存、配送能力或完整价格。

实模型验收至少包含正常、条件变化、第二服务失败三种变体，并保留模型自己的本体读取与决策凭据。只给固定路线换数据，不算重新组合通过。

## 7. 保留、替代与本轮不扩大的范围

**保留并复用**

- 已有动态定义注册库、不可变发布、准确受信任校验器、对象与关系版本。
- owner/source 隔离、真实来源授权、任务上下文与规划读取凭据。
- Intent / Attempt / Observation、幂等、租约、取消、累计预算与原任务恢复。
- 供应商连接器及仍然必要的领域验收逻辑。
- PA 的提交、澄清、查询、取消和读取交付物的使用方式。
- 确定性计算、数据处理和显式直调用的工具可以继续存在，例如只生成任务说明的 brief.prepare；它们的完成不能冒充组合业务目标已完成，也不能成为目标执行失败后的隐式旧流程回退。

**需要替代**

- 任务选定一个 program 后，该程序成为所有后续动作的硬边界。
- 要求模型照抄预制业务步骤的规划约束。
- 一个程序的 complete 决定整个跨服务目标是否完成。
- 在共用编排器中按具体业务名称解释事实、排列步骤或处理交接。

**范围控制**

先完善已有领域及已注册原语，不增加新的业务模板，不同时重建数据库、引入图数据库或云平台，不做支付结算层，不开放任意连接器安装或任意代码执行。跨服务编排能力与真实商家准入、部署、下单付款分别验证。

## 8. 风险与处理方式

| 风险 | 处理方式 |
| --- | --- |
| 同名或形状相似的值被错误连接 | 检查角色、来源、单位和证据语义，要求明确映射，不靠字段名字猜测 |
| 全目录暴露导致越权或上下文膨胀 | 先鉴权再分页；按任务与对象关系检索；保持现有读取预算 |
| 模型利用新规划丢弃旧副作用 | 原 Intent 和已接受观察持续属于同一任务，重规划前先核对实际执行历史 |
| 一个大“组合服务”重现固定工作流 | 验收检查两个独立绑定、模型决策变化和没有硬编码跨服务顺序 |
| 静态连通被误当现实可行 | 分别报告结构兼容、当前可执行与实际完成 |
| 部分领域验收无法泛化 | 保留注册的领域验证器，任务层只汇总它们能证明的条件 |
| 旧任务迁移丢失事实或承诺 | 固定版本；切换前处理在途任务和未知效果；禁止静默重放 |
| 为兼容保留永久双引擎 | 使用明确迁移清单和移除条件，拒绝隐式旧流程回退 |

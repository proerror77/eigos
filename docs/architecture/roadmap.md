## 线二：Functions

详细做法见 [Functions 实施方案](plans/functions.md)。

F1 的设计决定，以调研为依据，修正了对标计划原先"沿用 spared"的写法：

- **宿主：** 自建基于 wasmtime 的函数宿主进程，不沿用 spared。原因有三：
  1. F2 的 Ontology API 需要宿主函数。spared 只给受限的 HTTP，还禁止回调本机，F1 若绑定 spared，F2 就要换宿主。
  2. wasmtime 原生支持按 fuel 计量 CPU、限制内存和截止时间。spared 的 `cpu_ms` 计的是墙钟时间。
  3. spared 是未经外部审计的预览版。

  函数宿主与内核分开运行，因为内核的内存里有所有 owner 的数据。
- **接口：** 定义 EIGOS 自己的 WIT world。F1 只有 `invoke(input) -> result<output, error>`，F2 在同一个 world 上增加 Ontology 宿主接口。
- **语言：** 组件由作者自己编译，EIGOS 不在服务器上编译代码。
  - TypeScript 经 ComponentizeJS 编译，是主要语言，先做技术验证；
  - 同时提供 Rust 模板；
  - Python（componentize-py）放在之后。
- **版本：** 函数版本由 apiName、语义化版本、组件 SHA-256、参数与返回值 schema 和资源上限组成，发布后不可变。
  - 发布走定义分支。准备阶段与基线发布中的同名函数比较：删除或重排输入、新增必需输入、改变输入或输出类型，都要求主版本加一（0.y.z 除外）。
  - 消费方按版本范围引用，激活时解析为范围内最高的已发布版本，并固定在发布里。
- **限制：** 每个版本声明自己的上限，宿主再规定上限的上限。
  - 宿主控制 CPU（fuel）、内存、截止时间、输入与输出大小；
  - EIGOS 控制调用深度，以及从 F2 起每次调用读取的对象数。
- **权限：** 调用需要 `execute_function`；上传组件需要 `edit_definition`；发布沿用定义分支的审阅。

| 阶段 | 内容 | 依赖 | 验收 | 规模 |
| --- | --- | --- | --- | --- |
| F1 运行时 | 函数宿主、WIT 接口、组件存储（按 SHA-256 去重）、版本发布与兼容检查、版本范围、资源上限、TypeScript 与 Rust 模板 | 无 | 作者编译的组件经审阅发布后可被 Action 和 Agent 调用；超出上限的调用按约定失败；破坏性变更不能以次版本发布 | 4–6 PR |

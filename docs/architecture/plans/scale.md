# 09 规模化设计

09 的交付物是按瓶颈选择扩容方式的设计。各项实现独立发布。沿用已安装的 Ontology、PostgreSQL 中的任务和 Action 回执、原 PA 授权，以及 Indexer 的提交游标。

## 从测量选择改动

每次实验记录源码提交、发布、数据规模、owner 数及倾斜度、并发、槽位和连接池配置。分别测量排队、数据库等待、模型时间、供应商时间、人工等待和端到端时间。记录样本数、错误分类和等待最长的 owner。使用实际等待时长以及同一请求在参考实现上的结果做比较。

| 观察到的现象 | 对照实验 | 决定 |
|---|---|---|
| 多个 owner 访问不同对象时读写仍受表或索引大小影响 | 固定每个 owner 的工作集，扩大其他 owner 的数据；比较执行计划、缓冲区读数、WAL、P95 和写入吞吐 | 优先评估 09.1。单个对象锁等待集中时先走 04.3 |
| 同一变化重复产生大量待办，消费位置逐渐落后 | 对比均匀到达和一次突发提交，再用相同数据重启消费者 | 评估 09.3。保留每个订阅的正确唤醒结果 |
| 一个供应商的失败或变慢拖延另一个供应商及排程 | 只对一个合成供应商注入 429、超时和断流，读回另一供应商的领取时间 | 评估 09.4，分别调整出口并发和 Worker 并发 |
| 跨服务任务卡在已派发但回执未知，或 PA 恢复时重复执行 | 在每一步派发前后、中间回执落库后重启，检查原操作键 | 优先落地 09.2 的恢复语义 |
| 大量长期观察工作占用交互执行资源 | 区分实际执行、等待人工和等待事件的时间，测量执行槽占用 | 用 09.5 拆分可持久化的等待步骤 |

100,000 规模的 Engine Benchmark 08 已显示起点数会改变查询路径的收益。单起点三跳时参考实现和内核的 P50 分别为 27.8 和 51.4 毫秒；10,000 起点一跳分别为 869.9 和 33.5 毫秒。前沿、Object Set 完整性、数据库 I/O 和任务排队需要各自的实验。东京一次真实 Worker 样本不足以建立高峰容量线；上线顺序由新增的有代表性样本和同输入复现决定。[Nightly 测量](https://github.com/proerror77/eigos/actions/runs/46003486683)

## 09.1 在线分区

先试一张经测量受益的表。对象及关系优先验证按 owner 哈希分区，分区内索引保留 projection 和对象或边的完整身份。对历史表同时比较按月裁剪与 owner 哈希；按月方案必须与 90 天归档和未消费的提交窗口共同验收。提交顺序、订阅位置、外键及请求幂等键保留原语义。特别核对所有唯一约束是否包含候选分区键。需要跨分区唯一的旧主键时，保留原权威身份表或推迟该表迁移。[PostgreSQL 分区约束](https://www.postgresql.org/docs/17/ddl-partitioning.html)

1. 建立影子表和分区，复制列约束、索引、角色授权、RLS 策略和外键清单。验证运行角色在父表和子表上的可见范围。
2. 在统一的写入口为权威表和影子表安装同事务变更记录，涵盖插入、更新、删除与身份键移动。用一致性快照分块复制。每块记录主键边界和完成位置。
3. 回放快照后的去重变更键，从权威表重新读取最终值。已删除的键在影子表执行删除。先完成历史块，再消费其变更，防止后台复制覆盖新值。持久化游标与回放写入同事务提交。
4. 在写入压力下对账每个 owner 和 projection 的行数、内容指纹、反向差集、约束、索引查询和权限。截断窗口或任一不一致时，保持旧表权威并补齐缺失范围。
5. 用有时限的锁关闭切换窗口，排空增量，按已盘点的依赖切换读写入口、触发器与外键；验证旧连接的准备语句和新连接的读取。表名交换不会自动改变已绑定关系 OID 的依赖。锁超时则退出切换，由旧路径继续服务。[PostgreSQL ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html)
6. 保留旧表及反向补写直到观察期结束。切换后发生新写入时，先反向同步和核对，包括删除，再恢复旧路径。验收覆盖长事务、并发不同 owner、迁移中断、带新写入的回滚和归档任务同时运行。

## 09.2 跨供应商 Saga

跨供应商流程由已发布逻辑和原 Workflow 持有业务身份。每步引用已发布的正向 Action、只读对账能力以及可选的补偿 Action。记录流程实例、固定发布、步骤、原请求、外部操作键、授权范围、真实回执引用和前置步骤。敏感供应商内容沿用现有权限存储。

状态从待执行进入已派发，再进入已确认、结果未知或明确失败。将步骤状态、请求键和待派发副作用写入同一事务。使用现有 ExternalOperations 和 Action 提交通道。相同键重试先读原回执；派发后超时只对账原操作。供应商无法证明结果时，保留结果未知并交回原 PA。成功的前置步骤按逆依赖顺序补偿。每个补偿有自己的幂等键、授权证据和回执；费用、取消或不可逆变化需要覆盖该次具体操作的许可。缺少许可时持久化等待，不占执行槽。[Action 语义](https://www.palantir.com/docs/foundry/action-types/overview/)

合成验收使用三个服务、一个不可逆步骤和一次独立批准。分别注入回执丢失、重复投递、两 Worker 竞争、授权撤回、补偿失败和断电恢复。按原业务对象回读每步最多一次确认的效果、补偿结果和仍需人工处理的步骤。完成状态要求原始目标或明确批准的补偿目标已可核对。

## 09.3 事件风暴

以已提交的 owner 游标和发布投影驱动消费。通知只提示可读的变化；重启后从持久化位置继续。每轮在有限的提交窗口内，按订阅、原流程实例和发布去重；涉及解除关联时使用关系历史中的原端点。普通订阅、M3 的候选重算与相应排程继续沿用自己的授权。

积压时合并同一实例的状态重算，按最新可见快照重新求值。需逐事件执行的 Action 保留原有事件身份和顺序。跨 owner 按轮次领取，限制每个消费者单批处理量。游标推进、通知去重、排程变更必须在同一事务提交。消费落后于可用历史时标记缺口，执行有界快照重建，再接回增量；任何缺口都要可观测。监控最老未消费提交年龄、每批影响对象数、重算数、唤醒数和归档被阻塞的游标。

验收对单个 owner 重放突发更新、重复通知及关联重建，同时向另一个 owner 写入单一变化。比较逐事件参考结果与合并后的最终状态，核对第二个 owner 的首次领取、断点前后游标连续性、不同安装身份隔离和内存峰值。对每笔必须执行的外部业务动作逐项核对回执。

## 09.4 供应商治理

每个已发布 Source 绑定出口策略和凭据引用。每次调用复查当前身份、数据标签、允许的地址及方法。并发上限、每分钟预算、突发额度、累计额度与 Action 外部写入预算分别记录。配置缺省继续沿用现有不限速行为。按供应商、操作类型及 owner 分别计量，避免某个租户的故障影响全局。密钥轮换通过版本引用生效，OAuth 刷新保留跨实例的锁和未知结果围栏。

隔离故障时先阻止新的高成本派发，保留原单只读对账。退避优先服从供应商的重试时间；延后任务释放交互槽。半开探测使用已授权的低成本读取，成功后分批恢复并发。告警只含来源别名、分类及聚合指标。验收包括 429、连接中断、刷新令牌轮换、预算耗尽、其他供应商正常运行和受限身份被拒绝。生产启用名单、阈值和真实外部写操作另行按业务授权配置。

## 09.5 分层 Agent 运行时

单一 Function 或 Action 仍直达已有入口。跨服务任务持久化计划修订和原任务身份。规划步骤引用发布版本、目标和待满足条件；执行步骤只领取已授权的候选；观察步骤订阅相关变化，并用原 PA 和提交窗口恢复同一任务。排程继续承担时间和资源约束，Scenario 承担拟议编辑和基线比较。模型输出属于建议，Action 的权限、提交条件和提交回执是执行依据。

恢复时比较计划修订、发布、已确认回执和授权版本。过期候选进入局部重规划，已确认的步骤直接读回。观察者不能从通知内容推导新的外部写入授权。最终验收从原对话发起，经历计划修订、资源冲突、人工批准、进程重启和最终读回；分别统计排队、推理、供应商和人工等待，并验证原任务与原 Action 始终可追踪。

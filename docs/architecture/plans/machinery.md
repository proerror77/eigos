# Machinery：M1–M3 的实施方案

本文是 [路线图](../roadmap.md) 线四的详细做法，Palantir 的依据见 [对标计划](../palantir-parity.md#machinery补可配置监控再做编排扩展)。

## 现状

- **流程日志：** `addProcessLogs`（`packages/ontology/process-definition.ts`）为每个被跟踪的 `(type, property)` 生成一个 ProcessLog 类型，记录状态转换。每个日志跟踪一个状态属性。
- **分析：** `analyzeMachinery`（`machinery-analysis.ts`）按时间窗、对象或 Object Set 读取日志，计算以下内容：
  - 挖掘：最少案例数、覆盖率、排除边；
  - 一致性：已建模与已观察的对比、偏离实例；
  - 瓶颈 P50/P95、路径、停留分布；
  - 筛选：状态、当前、边、路径、一致性、停留时长。
- **复盘与提案：** `machinery-reviews.ts` 定期复盘；模型提案生成定义分支。
- **过程规则：** `process-automation.ts` 支持转换规则（`from` → `to`）和停留规则（`dwellSeconds`），作为自动化的触发器。

## M1：监控对齐

### 指标视图

**状态：** 四种视图、自定义指标、着色和 Sankey 流量已实现，接口和工作台都可以用，见 [Machinery 指南](../../guides/machinery.md#视图选择与指标)。

- **四种视图：** 计数 × 时长，各分历史和当前。
  - 历史：时间窗内的转换次数，以及停留时长的 P50/P95；
  - 当前：此刻处于每个状态的实例数，以及已停留的时长。
- **实现：** 在 `analyzeMachinery` 的输入里增加 `metrics: { kind: 'count' | 'duration', scope: 'historical' | 'current' }`。
  - 现有计算已经产生这些数，只需按请求的视图组织输出；
  - "当前"视图要从每个实例的最后一次转换算起：用一条 `DISTINCT ON (instance)` 的 SQL，按实例取最新的日志行。
- **自定义指标：** 节点和边可以绑定一个聚合，即 Object Set 聚合，在当前处于该节点的实例上计算。这一聚合经过查询内核。
- **条件着色：** 定义里为指标设阈值，例如停留时长 P95 超过目标时标红，由工作台渲染。
- **Sankey：** 输出每条边的流量，即经过这条边的实例数，工作台用 Sankey 图展示。

### 选择输出

**状态：** 已实现：多选节点（当前处于、曾经处于）和多选边（经过、最后一次转换）；选中的流程可以保存为静态 Object Set，或保存为每次读取都重新分析的动态 Object Set（`machinery` 操作）。

- **节点：** "当前处于"或"曾经处于"。
- **边：** "经过"或"最后一次转换"。
- **输出：** 选中的实例作为 Object Set 输出：`refs` 节点，或者可以保存的动态 Set。下游的分析、Automation 和 Action 可以直接使用。
- **实现：** 在 `filter` 中增加 `selection: { node?: { state, mode }, edge?: { from, to, mode } }`，结果用 `collectMembers` 收集实例引用。
- **数量：** 超过 1 万个实例时分页，与 Object Set 的上限一致。

### 一个类型上的多个状态属性

**状态：** 已实现，见 [Machinery 指南](../../guides/machinery.md#流程容器)。容器不另设定义：同一类型上的流程用 `parallel` 关联，嵌套沿用 `subprocesses`，嵌套不能成环；分析结果给出并行流程和子流程的当前状态对齐。

- **流程容器：** 一个类型可以有多个被跟踪的状态属性，每个属性一个 ProcessLog。新增"流程容器"把它们组织起来：
  - 容器属于一个对象类型，包含若干状态属性的流程模型；
  - 容器之间可以嵌套（子流程）或链接，链接可以跨类型，沿一个 Link。
- **定义：** 流程模型的定义里增加 `containers`，由 `validateMachineryModel` 校验：属性存在、日志已发布、嵌套无环。
- **分析：** 按容器给出各自的指标，也可以按链接把父容器与子容器的状态对齐显示。

### 状态与停留超时通知

**状态：** 已实现，见 [Automation 指南](../../guides/automation.md#通知规则)：通知规则、按转换去重、停留到期复查、送达收件箱（工作台和 PA 读取），以及在流程图上直接配置。外部 IM 或邮件出口不由 EIGOS 直接发送，而是由用户的 PA 读取后转发。

- **触发：** 复用过程规则，转换规则和停留规则已经能触发自动化。
- **补上的部分：**
  - 通知渠道：工作台内通知，以及已配置的 IM 或邮件出口，受出口策略约束；
  - 在 Machinery 视图里直接为节点或边创建规则；
  - 停留规则的到期扫描。Worker 定期扫描"当前"视图中停留超过目标的实例；同一实例同一规则只通知一次，按 `(rule, instance, transition sequence)` 去重。
- **验收：**
  - 四种视图、选择输出和容器在工作台可用；
  - 停留超时通知能送达，且不重复。

## M2：按当前状态推导下一步 Action

Machinery 的状态和转换沿用 M1 的 ProcessLog 与流程定义。Palantir 的流程图把 Action 绑定到输入和输出状态，提交条件仍随 Action 校验。EIGOS 在同一发布里补充跨流程守卫、参数绑定和分支汇合，通过现有 Action Engine 提交。 [Machinery 状态和 Action](https://www.palantir.com/docs/foundry/machinery/core-concepts/) · [流程图和转换](https://www.palantir.com/docs/foundry/machinery/draw-a-graph/) · [Action 提交条件](https://www.palantir.com/docs/foundry/action-types/submission-criteria/)

### 发布时编译

- `validateMachineryModel` 校验已有的状态、转换、Action 和容器。M2 在有 Action 的转换上声明主体对象参数、可从同一对象绑定的参数，以及跨流程条件。发布时校验参数名、对象类型、Link 方向、目标 ProcessLog 和允许的目标状态。需要用户填写的参数沿用 Action 的公开 schema。
- 并行流程使用 M1 的同对象状态属性。子流程沿已发布 Link 找到关系对象。守卫明确要求任一或全部相关实例达到指定状态。没有关联实例时，守卫等待所需实例。发布时拒绝互相等待的流程依赖。业务状态机仍可表示返工和重试的转换。
- 按发布和 ProcessLog 缓存从状态到转换、Action 和守卫的映射。一个 Action 绑定多个转换时，当前状态和主体参数必须能确定适用的转换。已有 Action 继续使用其已发布的参数和调用入口。

### 读取候选和提交

1. `nextActions` 接受业务对象引用，可指定 ProcessLog。读取对象的一致快照，从当前状态列出候选转换。参数自动填充来自调用者可读取的发布对象及其关系。多个平行流程返回各自的候选，方便 Agent 和工作台选择。
2. 先校验 Action 权限，再求值跨流程守卫。使用 `Objects`、`Access` 和现有查询内核路径。结果区分条件满足、条件阻塞、需补参数和待检查。关系读不完整或状态被遮罩时返回待检查。阻塞原因只包含调用者获准读取的信息。
3. 参数完整、条件可只读验证时，复用 `Actions.validateSubmission` 的参数和提交条件检查。需要外部来源或人工确认的条件保留到原 Action 的执行步骤。候选查询只读取数据，调用方仍使用相同发布、Action 和请求 ID 完成提交。
4. 对定义为必需的跨流程守卫，在 Action 的提交检查中用同一求值器复查，包括直接调用 Action 的入口。通过现有提交事务锁和读取依赖判断是否需重试。关联实例或权限在建议和提交之间变化时，用当前结果阻止无效转换。
5. 动态分支由其守卫选择可用转换。子流程由父 Action 建立关联对象并各自执行已发布 Action。汇合由父流程的任一或全部条件计算。需要比较执行时机或竞争资源时，沿用动态排程。

### 验收和 M3 依赖

- 用合成行程实例覆盖航班、接送、酒店三个流程。初始只返回符合条件的准备 Action。关联状态变化后，候选和阻塞原因随之更新。验证任一和全部汇合、关联为空、参数待补和终止状态。
- 用两个身份分别验证可读和遮罩后的候选。先读取候选，再改变依赖状态或撤回权限，确认提交阶段拒绝原转换。验证直接调用同一 Action 也执行守卫。保留原请求和 Action 的幂等回执。
- 每次求值可从编译结果得到所读取的源类型、Link 和目标流程，并记录本次对象引用与已提交位置。M3 利用 05.4 的变化位置和这些依赖定位受影响的父实例。先用修改一个子流程仅重算其关联父流程的测试验证范围。

## M3：事件驱动与治理（原 07.5–07.7）

1. **局部重规划：** 已实现按实例订阅 Funnel 05.4。Indexer 根据对象编辑和关系两端匹配受影响的实例，按当前权限重算候选 Action，复查原排程及观察计划。PostgreSQL 回归覆盖提交、回滚、解除关联、重复投递、权限撤回和发布切换。[使用与验收](../../guides/machinery.md#已提交变化触发的局部重规划)
2. **改进提案：** 从 Workbench 分析保存模型时，服务端记录窗口内的偏离实例数、完成停留 P95 和受影响转换。审阅绑定候选和依据，旧版依据支持刷新。已用 PostgreSQL 验证独立审阅、激活与原发布的历史回读。具体规则如下。
   - 提案生成定义分支，现有的模型提案已经能做到；
   - 提案附上依据：偏离实例的数量、瓶颈的 P95 和受影响的边；
   - 经审阅后激活。
3. **版本与发布：** 流程模型属于 Ontology 定义，沿用定义分支的版本、审阅和发布。
   - 已激活的流程版本固定在发布里；
   - 运行中的实例按它所在的发布解释，换发布时不改变已发生的历史。
4. **验收：**
   - 变化发生后只重规划受影响的实例，用读取的实例数断言；
   - 提案经审阅后作为新版本发布。

## 依赖与顺序

- M1 只依赖已完成的 C4；选择输出和自定义指标用到 Object Set 内核。
- M2 依赖 M1 的容器。
- M3 依赖平台线的 05.4 和 M2。

# Machinery：M1–M3 的实施方案

本文是 [路线图](../roadmap.md) 线四的详细做法，Palantir 的依据见 [对标计划](../palantir-parity.md#machinery补可配置监控再做编排扩展)。

## 现状

- **流程日志：** `addProcessLogs`（`packages/ontology/process-definition.ts`）为每个被跟踪的 `(type, property)` 生成一个 ProcessLog 类型，记录状态转换。每个日志跟踪一个状态属性。
- **分析：** `analyzeMachinery`（`machinery-analysis.ts`）按时间窗、对象或 Object Set 读取日志，计算以下内容：
  - 挖掘：最少案例数、覆盖率、排除边；
  - 一致性：已建模与已观察的对比、偏离实例；
  - 瓶颈 P50/P95、路径、停留分布；
  - 筛选：状态、当前、边、路径、一致性、停留时长。
- **复盘与提案：** `machinery-reviews.ts` 定期复盘；模型提案生成定义分支。
- **过程规则：** `process-automation.ts` 支持转换规则（`from` → `to`）和停留规则（`dwellSeconds`），作为自动化的触发器。

## M1：监控对齐

### 指标视图

- **四种视图：** 计数 × 时长，各分历史和当前。
  - 历史：时间窗内的转换次数，以及停留时长的 P50/P95；
  - 当前：此刻处于每个状态的实例数，以及已停留的时长。
- **实现：** 在 `analyzeMachinery` 的输入里增加 `metrics: { kind: 'count' | 'duration', scope: 'historical' | 'current' }`。
  - 现有计算已经产生这些数，只需按请求的视图组织输出；
  - "当前"视图要从每个实例的最后一次转换算起：用一条 `DISTINCT ON (instance)` 的 SQL，按实例取最新的日志行。
- **自定义指标：** 节点和边可以绑定一个聚合，即 Object Set 聚合，在当前处于该节点的实例上计算。这一聚合经过查询内核。
- **条件着色：** 定义里为指标设阈值，例如停留时长 P95 超过目标时标红，由工作台渲染。
- **Sankey：** 输出每条边的流量，即经过这条边的实例数，工作台用 Sankey 图展示。

### 选择输出

- **节点：** "当前处于"或"曾经处于"。
- **边：** "经过"或"最后一次转换"。
- **输出：** 选中的实例作为 Object Set 输出：`refs` 节点，或者可以保存的动态 Set。下游的分析、Automation 和 Action 可以直接使用。
- **实现：** 在 `filter` 中增加 `selection: { node?: { state, mode }, edge?: { from, to, mode } }`，结果用 `collectMembers` 收集实例引用。
- **数量：** 超过 1 万个实例时分页，与 Object Set 的上限一致。

### 一个类型上的多个状态属性

- **流程容器：** 一个类型可以有多个被跟踪的状态属性，每个属性一个 ProcessLog。新增"流程容器"把它们组织起来：
  - 容器属于一个对象类型，包含若干状态属性的流程模型；
  - 容器之间可以嵌套（子流程）或链接，链接可以跨类型，沿一个 Link。
- **定义：** 流程模型的定义里增加 `containers`，由 `validateMachineryModel` 校验：属性存在、日志已发布、嵌套无环。
- **分析：** 按容器给出各自的指标，也可以按链接把父容器与子容器的状态对齐显示。

### 状态与停留超时通知

- **触发：** 复用过程规则，转换规则和停留规则已经能触发自动化。
- **补上的部分：**
  - 通知渠道：工作台内通知，以及已配置的 IM 或邮件出口，受出口策略约束；
  - 在 Machinery 视图里直接为节点或边创建规则；
  - 停留规则的到期扫描。Worker 定期扫描"当前"视图中停留超过目标的实例；同一实例同一规则只通知一次，按 `(rule, instance, transition sequence)` 去重。
- **验收：**
  - 四种视图、选择输出和容器在工作台可用；
  - 停留超时通知能送达，且不重复。

## M2：流程编排（原 07.1–07.4，Palantir 之外的扩展）

1. **编译执行结构：**
   - 从 Ontology 和流程定义编译出状态机：状态、转换、每个转换对应的 Action，以及 Action 的提交条件；
   - 结果缓存在发布里，随发布失效。
2. **推导合法 Action：**
   - 对一个实例，取它的当前状态，列出从这个状态出发的转换，再用提交条件判断哪些 Action 此刻可以执行；
   - 接口 `nextActions(ref)` 返回 Action 和参数的模板。
   - Agent 用它决定下一步，不再靠提示词里的流程描述。
3. **跨流程依赖：**
   - 流程模型可以声明依赖，例如"订单进入 `shipped` 需要关联的发票处于 `paid`"；
   - 依赖沿 Link 求值，读取经过查询内核；
   - 不满足的依赖在 `nextActions` 里列为阻塞原因。
4. **动态分支、组合与汇合：**
   - 分支：一个转换按条件走向不同状态；
   - 组合：一个实例启动多个子流程；
   - 汇合：子流程全部或任一完成后，父流程继续。

   这些都写成流程定义里的结构，编译成状态机的转换和守卫条件。
5. **验收：** 一个跨流程用例，例如行程预订涉及航班、接送和酒店，能自动推导出下一步 Action 和阻塞原因。

## M3：事件驱动与治理（原 07.5–07.7）

1. **局部重规划：** 订阅 Funnel 05.4 的变化通知。相关对象提交后，只对受影响的实例重新计算 `nextActions` 和排程，不重算全部。
2. **改进提案：** 挖掘出的偏离和瓶颈转成提案：
   - 提案生成定义分支，现有的模型提案已经能做到；
   - 提案附上依据：偏离实例的数量、瓶颈的 P95 和受影响的边；
   - 经审阅后激活。
3. **版本与发布：** 流程模型属于 Ontology 定义，沿用定义分支的版本、审阅和发布。
   - 已激活的流程版本固定在发布里；
   - 运行中的实例按它所在的发布解释，换发布时不改变已发生的历史。
4. **验收：**
   - 变化发生后只重规划受影响的实例，用读取的实例数断言；
   - 提案经审阅后作为新版本发布。

## 依赖与顺序

- M1 只依赖已完成的 C4；选择输出和自定义指标用到 Object Set 内核。
- M2 依赖 M1 的容器。
- M3 依赖平台线的 05.4 和 M2。

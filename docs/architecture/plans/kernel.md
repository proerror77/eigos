# 查询内核：上线与 C4b、C5、C6 的实施方案

本文是 [路线图](../roadmap.md) 线一的详细做法。语义依据和已完成阶段见 [查询内核](../query-kernel.md)，使用方式见 [查询内核指南](../../guides/query-kernel.md)。

每个阶段都遵守同一个原则：内核只回答它已证明与参考实现等价的查询，其余交回参考实现。证明靠两类测试：
- 套件 46 的差分测试；
- 在严格影子模式（`EIGOS_KERNEL=shadow EIGOS_KERNEL_SHADOW_STRICT=true`）下跑全量测试，每次求值都同时走两条路径比对。

## 上线：直接切到路由模式

用户 2026-11-26 决定跳过影子观察期，直接以 `EIGOS_KERNEL=route` 上线。部署套件见 `eigos-archives/kernel-deploy-20261126`，步骤如下：

1. **发布二进制：** 对一个 CI 已通过的 main 提交触发 `Kernel release`。工作流在 ubuntu-24.04（与生产相同的 glibc 2.39）上编译，剥离符号，启动检查后发布 `kernel-<12 位提交号>` 和它的 SHA-256。
2. **安装内核服务**（不改变任何请求）：
   - 角色 `eigos_kernel_reader_20261126`：可以绕过 owner 隔离，默认只读，只有 `objects`、`links`、`change_commits`、`edit_history`、`link_history` 五张表的 SELECT 权限。
   - 增加一行 `pg_hba`，认证方式为 scram-sha-256。密码只保存在主机的 `kernel/database.env`。
   - 下载二进制并按 SHA-256 核对。
   - 用户单元 `com.eigos.primary.kernel.service`：监听 127.0.0.1:3215，数据目录为 `kernel/data`，轮询间隔 1 秒，检查点间隔 5 分钟，内存上限 768 MB。
3. **常规部署：** 依次执行 stage（核对 commit、tree、文件数和实现 digest），在 `pg_dump` 副本上演练激活与回滚，然后有保护地切换。
   - 激活事务里会建立索引 `change_commits_sequence`。
   - `server.env` 增加 `EIGOS_KERNEL=route`、`EIGOS_KERNEL_URL` 和 `EIGOS_KERNEL_DATABASE_URL`。
4. **门槛：** 切换前后各运行一次 `kernel-smoke`。它用新版本的代码，在严格影子模式下对数据最多的 owner 做只读求值，任何不一致都会让它失败。切换前失败就停止部署；切换后失败就执行下面的停用操作。
5. **停用方式：** 把 `server.env` 的 `EIGOS_KERNEL` 改为 `off` 并重启三个单元，所有查询就回到参考实现。内核服务可以继续运行，它只读。

上线后要观察的指标：
- 内核交回参考实现的次数和原因（409 版本不足、422 参考实现会失败、规划层不支持）；
- 内核的载入次数、检查点耗时和内存；
- Object Set 接口的延迟。

前两项写入运行日志，并在 C6 汇总进基准报告。

## C4b：`Objects.query` 经过内核

**状态：** 已实现，见 [查询内核指南](../../guides/query-kernel.md#objectsqueryc4b)。字符串排序按 UTF-16 码元实现，不交回参考实现。

### 范围

`Objects.query` 在参考实现里有三条路径，对应不同的排序和游标：

| 路径 | 何时走 | 排序 | 游标 |
| --- | --- | --- | --- |
| 普通 | 没有 filter、orderBy、派生属性、嵌套字段 | `type`、`id`，按 `COLLATE "C"` | 键集游标：`{query, type, id}` |
| 下推 | 过滤条件可在存储中执行（`scalarCandidates`） | orderBy（null 在后），再按 `to_json(type)`、`to_json(id)` 排序 | 偏移游标，加上全部匹配对象的摘要 |
| 候选 | 过滤条件读取派生属性或不能下推 | 在 JS 里排序：orderBy（null 在后），再按 `JSON.stringify(ref)` 的字节顺序 | 同上 |

- **普通路径留在参考实现。** 它已经是带键集分页的单条 SQL，内核带不来好处。
- **另外两条路径交给内核，统称"完整求值"。** 参考实现在这里最多读一万个候选或匹配对象，超出就报错，过滤在 JS 中执行；内核去掉这个上限。

### 做法

1. **排序规则：** 照参考实现实现。
   - 第一键是 orderBy 的列，只支持数值和布尔；null 不论升降序都排在最后。
   - 最后按 `JSON(type)`、`JSON(id)` 逐字节比较。JSON 字符串字面量里，没有转义的双引号只出现在结尾，所以一个字面量不会是另一个的真前缀。比较 `JSON.stringify(ref)` 因此等价于先比 type、再比 id 的编码。内核在查询时用 `json_string` 为成员计算 `$jid`，不占快照内存，检查点格式也不变。
   - 内核载入对象时新增 `$jid` 列，即 JSON 编码的 id；扫描时附上 `$jtype`。
   - 字符串按 UTF-16 码元比较，与 JS 相同。内核用 `utf16_key` 把字符串转成大端 UTF-16 字节再排序。若按 UTF-8 字节比较，补充平面的字符会排到 U+E000–U+FFFF 之后，与 JS 不同。
2. **跨类型排序（Interface 查询）：** 每个实现类型把 orderBy 的视图字段映射到自己的列，先经过遮罩，再统一成一个类型，然后合并排序。这与 C2c 的聚合相同：
   - 某个类型没有映射这个字段，就按 null 处理；
   - 各类型的列类型不一致时交回参考实现。
3. **读取：** 与 Object Set 的查询节点规则相同。
   - 下推路径读取匹配的行；
   - 候选路径读取全部可读的行。
   - 两者都要计算派生属性，所以内核报告的读取范围也相同，规划层沿用 `candidates` 标记。
4. **页：** 内核返回本页的引用和成员摘要。
   - 客户端用 `Objects.readBatch` 补读本页对象，再按查询的视图投影，最后应用 `select`。
   - 投影规则与参考实现的 `queryObjects` 相同：`visibleViewField` 加 `propertyName`。
5. **游标：**
   - 内核给出内核游标：查询身份、偏移和成员摘要，格式与 C4a 相同。
   - 参考游标（偏移游标、键集游标）只在参考实现上继续。
   - 内核游标在成员变化或内核不可用时失效，返回 `InvalidInput`。
6. **接入：** 在 `Objects.query` 里，只有同时满足以下条件才走内核：
   - 模式不是 `off`；
   - 客户端是连接池，也就是不在调用方的事务里；
   - 没有 Scenario（C5 之前）；
   - 不在记录决策证据；
   - 查询会走完整求值。

   `Objects` 在很多地方被直接构造，所以内核来源用进程级的默认值（`kernelMode()`、`defaultKernels()`），另设一个测试用的覆盖入口。
7. **影子模式：** 结构与 C4a 相同。参考实现回答，内核和参考实现再各在一份分叉的访问上下文里算一遍并比对，严格模式下不一致即失败。

### 验收

- 套件 46 新增差分测试，覆盖以下情况，分别在三种许可级别下比对结果、分级、依赖和标记：
  - 数值和布尔的 orderBy，null 的位置；
  - 多键排序；
  - Interface 跨类型排序；
  - 派生字段排序；
  - `select`；
  - 关系查询（`from`）；
  - 内核游标的分页与失效。
- 在严格影子模式下跑全量测试，`Objects.query` 的比对零不一致。
- 基准：在 10 万和 100 万个对象上，"按派生属性过滤并排序取首页"的延迟。参考实现超过一万个候选时报错，内核正常返回。

### 实现边界

- `intervalOverlap`、`text` 和 `regex` 谓词仍交回参考实现。
- 补读期间 owner 有新提交时交回参考实现，保证页内对象与顺序出自同一版本。
- 普通路径不改。

## C5：Scenario、多跳与向量

### C5a：Scenario 叠加层

**状态：** 已实现，见 [查询内核指南](../../guides/query-kernel.md#scenarioc5a)。上线时，内核角色要加上三张 Scenario 表的 SELECT 权限。

**现状：** Scenario 的编辑保存在 `scenario_objects` 和 `scenario_links` 里。参考实现用 `viewTables` 把正式数据和这些改动合成为查询用的视图，内核遇到 Scenario 就交回参考实现。

**做法：**
1. **请求：** 规划层带上 `scenario: {id, revision}`。Scenario 每次编辑都会让 `scenarios.revision` 加一，所以修订号可以作为改动的版本。
2. **读取改动：** 内核按 `(owner, scenario id, revision)` 读出改动并缓存。
   - 对象改动：每行的 `properties` 为 null 表示删除，否则是改动后的值；
   - 关系改动：增加或删除。

   改动按 C3 的覆盖层方式叠加在当前版本上：基础行减去改动的键，再并上仍然存在的改动行。只在这次查询中生效，不写入共享的版本。
3. **一致性：** Scenario 绑定发布，内核核对投影一致。Scenario 过期或会话关闭时，参考实现的 `checkScenario` 会报错，这时交回参考实现，由它报告。
4. **读取与依赖：** 在 Scenario 中，参考实现为读到的每一行记录行依赖（`trackRow` 带上 Scenario id），与类型是否受对象策略约束无关。所以内核为每个可读类型报告读到的行，客户端照此记录。

**验收：**
- 套件 46 增加带 Scenario 的差分测试：创建、编辑、删除对象，增加和删除关系，然后查询、遍历、聚合，与参考实现比对。
- 在严格影子模式下跑全量测试，Scenario 相关套件（09、19、Scenario 评估）零不一致。

### C5b：多跳与 Search Around

**状态：** `Objects.follow` 已经过内核，见 [查询内核指南](../../guides/query-kernel.md#objectsfollowc5b)。2026-11-27 的 Nightly 在 10 万个路线、10 万个乘车请求和 1 万个地点上，从 500 个请求出发做 7 次测量。单跳中位数从 67.3 ms 降到 41.2 ms，数据库语句从 10 条降到 2 条。三跳中位数从 84.8 ms 降到 71.0 ms，数据库语句从 12 条降到 2 条，其中内核执行占 65.5 ms。选择性排序和前沿提前停止分别需要集合组合与高分叉用例的对照结果。先以固定的 1、100 和 1 万个起点补齐规模曲线，再看何时应改执行计划。 [Nightly 报告](https://github.com/proerror77/eigos/actions/runs/45924409983)

加入固定起点矩阵的 Nightly 已跑完整套严格影子对比。总计比对 2,047 次，149 次由参考实现回答，1 次在重载投影后恢复一致。影子汇总按 query、follow、evaluate 和 aggregate 分项记录，并单独报告内核不可用，供后续按真实回退类型补查询覆盖。 [严格影子测试](https://github.com/proerror77/eigos/actions/runs/46003486683/job/140520751799)

承接 OSS 03.2 留下的问题：候选分页 100 行、一万个对象时 JS 处理成为瓶颈、每次 `follow` 调用的固定开销。

**做法：**
1. **`follow` 经过内核：** 对单个对象读取关系的 `Objects.follow`，由内核计算目标，客户端用 `readBatch` 补读。
   - 关系读取的完整上限照旧，超出时交回参考实现报错。
   - 含字段分级的普通对象也能走关系内核。运行时读取源对象及每个返回目标，按调用者权限遮蔽字段并记录分级。过程日志等虚拟类型继续由参考实现读取。 两个合成配送用例合计 80 次关系读取，回退由 54 次降到 5 次。
   - Agent 一次调用多条关系，在内核里一次完成。
2. **多跳的执行顺序：**
   - 每一步先套用目标类型的行规则，再连接边表，并去重；这一点 C1 已实现。
   - 新增一项：交集和差集中选择性高的一侧先求值。依据是内核为每个类型维护的行数统计，以及每个 Link 的平均出度。
3. **前沿上限：** 每一步的前沿超过请求给定的上限时，提前停止并报告（Search Around 的上限语义），而不是物化整个结果再截断。

**验收：**
- 套件 46 覆盖 `follow` 的等价，包括 Interface 导航、关系分级标签和目标的行规则。
- 基准：从 1、100、1 万个源对象出发走 1 跳和 3 跳，比较参考实现和内核的延迟与语句数。

### C5c：向量检索的去留

**状态：** 已决定：留在 pgvector，按授权候选精确排序。测量和依据见 [查询内核](../query-kernel.md#向量检索的去留c5c-决定2026-11-26)。

**现状：** 语义检索用 pgvector。

**做法：**
1. 在 1 万、10 万、100 万条向量上测量三种方案的召回率与延迟：
   - pgvector 精确检索；
   - pgvector HNSW 近似检索；
   - 内核内的暴力检索：Arrow 定长列表与 DataFusion 向量距离。
2. 决定规则：
   - 单个 owner 的向量数量在常见规模下，精确检索已能满足交互延迟时，保留 pgvector，并为大 owner 加 HNSW 索引；
   - 只有当检索需要与内核里的过滤、遍历组合，并且 pgvector 无法高效执行时，才把向量迁入内核。
3. 结论写进 [查询内核](../query-kernel.md)，选定的方案另开 PR。

## C6：基准与容量

**状态：** 已完成。基准脚本 `scripts/benchmarks/engine-08.ts`、报告比较和 `Nightly` 工作流已加入。容量说明用 10 万和 100 万规模的 Linux 实测写成，见 [查询内核指南](../../guides/query-kernel.md#容量c6linux-实测)。门槛实际定为：内核中位数变慢 1 倍以上时失败，变慢 20% 以上时警告，因为共享 runner 的波动比计划设想的大。

**做法：**
1. **Engine Benchmark 08：** `scripts/benchmarks/` 下的可重复脚本，数据由合成生成器产生。规模分 10 万、100 万、1000 万个对象，每个对象一到两条边。
   - **只读：**
     - 过滤取首页（存储字段、派生字段）；
     - 1 跳、3 跳遍历；
     - 全量聚合；
     - 带 orderBy 的查询；
     - Interface 查询。
   - **写入：**
     - 单对象编辑；
     - 批量源导入，包括 Funnel 追平和合并覆盖层；
     - Action 提交到查询可见的延迟，即读后写延迟。
   - **恢复：** 全量载入与检查点恢复。
2. **指标：** 记录 p50、p95、p99 延迟，以及语句数、CPU 和常驻内存。内存在 Linux 上实测，macOS 的内存压缩会让数字偏低；用 CI 的 ubuntu runner 或一台测试 VM。
3. **对比：** 参考实现与内核在同一份数据上各跑一遍。参考实现超出一万个对象的上限时记为"不支持"。
4. **回归门槛：** 每晚在 main 上运行规模为 10 万的子集。p95 比上次报告恶化 20% 以上时，CI 失败。
5. **容量说明：** 根据测量结果写出：
   - 每个对象和每条边的内存；
   - 检查点的大小；
   - 不同数据规模下推荐的主机内存。

   一并写进查询内核指南。

**验收：** 基准报告进入文档，夜间任务在 main 上运行。

## 覆盖缺口

按上线后"交回参考实现"的统计决定先后，各自一个 PR：

1. **带属性级分级标签的类型和 Interface：** 载入时为每行记录"有哪些属性"（属性存在位图）。内核据此报告每个带标签的属性是否在读到的行里出现、是否被单元格策略允许，客户端照参考实现观察这些标签。
2. **带单元格策略或整列不可见的派生属性：** 参考实现只在可见的行上计算这类属性。预取路径和逐对象路径的读取范围不同，需要分别建模。
3. **文档分块和过程日志：** 它们的行规则引用别的对象。要把父对象的规则编译成半连接，才能在内核里执行。

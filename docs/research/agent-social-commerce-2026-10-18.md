# Agent 社交网络与 EIGOS 商业协作 MVP

研究日期：2026-10-18。只读公开资料；未注册平台账户、安装远程技能、发送消息或调用交易接口。远程技能文件作为研究资料阅读，里面的注册、定时访问和发帖指令未执行。本笔记提出产品设计，不声称对应能力已存在于 EIGOS。

## 判断

Agent 社交可以补充商业网络的发现、协商和复购，但“有交流”不能证明“有交易需求”。EIGOS 更值得先建设的是可追责的商业关系网络：知道谁能做什么、谁与谁合作过、在什么条件下可以继续合作。推荐流、点赞和闲聊可以增加活跃度，也可能放大垃圾内容、互刷信誉与模型成本。

建议把组合关系定义为：**社交负责发现与建立联系；交易负责授权、承诺和状态；履约证据负责信誉。** 这三个领域共享身份与对象链接，但不能互相代替。

## 1. Moltbook：有真实社交 API，信誉和权限需另建

### 已核实

官方主页定位为 Agent 分享、讨论和投票的平台，并提供人类观察入口。当前静态页面提取的计数为零，未获得动态统计；不能当成真实零用户，也不能引用第三方滚动数字当当前真实规模。[官网](https://www.moltbook.com/)

2026-10-18 直接 GET 成功读取的官方 `skill.md` 标为 v1.12.0。内容公开了 Agent 注册/认领、个人资料、发帖/评论、投票、submolt 社区、订阅、关注、个性化 feed、语义搜索、通知和 `/home` 聚合入口。认领流程描述邮箱与 X 验证；这是账户归属机制，不能证明操作者必然是 AI，或已经具有商业信誉。[官方技能/API 手册](https://www.moltbook.com/skill.md)

外部应用身份服务仍标为 Early Access：应用需申请邀请码与 `moltdev_` key；Agent 生成临时 identity token，应用通过 `verify-identity` 验证。文档称 token 一小时过期，返回 karma、帖子数、认领状态等。**持有社交身份不能自动取得 EIGOS 下单、支出或商户管理权限。** [官方开发者页](https://www.moltbook.com/developers)

### DM 文档存在不一致

- `https://www.moltbook.com/messaging.md` 在本次网页与直接 HTTP 读取中均返回 404。
- 当前 `heartbeat.md` 仍写 `/home` 包含 DM 未读和待批准请求，并要求新 DM 获人类批准。
- `rules.md` 仍描述新账户前 24 小时禁用 DM；其 API 限流说明也与较新的 `skill.md` 数字不同。

因此只能确认当前文档仍描述 DM，**没有验证可调用的完整 DM 合同**。若后续真要对接，先核对官方当前接口与账户权限。不能用旧镜像中的 endpoints 直接投入生产。[Heartbeat](https://www.moltbook.com/heartbeat.md)、[Rules](https://www.moltbook.com/rules.md)、[本次 404 路径](https://www.moltbook.com/messaging.md)

### 对产品的启发

`/home` 式聚合入口很适合 Agent：一次取回需处理事项、订阅更新和关联对象，减少反复抓 feed。EIGOS 可以借鉴它，返回“待澄清需求、待响应报价、待审批动作、临期履约、异常与售后”，并以事件游标增量读取。不能照搬“定时刷帖、点赞、追求 karma”的目标。

## 2. Chirper 与 Chirp：区分运营平台、开源实现和商业证据

### Chirper

[Chirper 官方站](https://chirper.ai/) 有 Agent 社交 feed 与 Agent 资金支持入口。[官方 Agent Wizard](https://chirper.ai/wizard) 展示名称、简介、system prompt、OpenAI-compatible 模型配置、MCP 连接、语言、社交链接以及锁定头像/简介等控制。这说明它把 Agent 托管配置与社交身份结合；本次未核实开放给外部 Agent 的稳定发帖 API、付费交易协议或对 EIGOS 的互操作合同。

独立研究作者的 [Chirper 原始论文](https://arxiv.org/abs/2504.10286) 分析超过 65,000 个 Agent、770 万帖子；页面注明 CSCW 2026 接收。它是历史数据集的活动证据，不能推成当前日活、独立企业数量、付费客户或商业成交量。

### Chirp 社区版

[chirp-oss/chirp 自有仓库](https://github.com/chirp-oss/chirp) 提供开源 Agent 社交实现及接口示例：帖子、关注、DM、通知、资料、审核；Agent 使用 API key 加会话 token，人使用浏览器管理通道。其“Agent 才能发帖”是 API 通道设计，不能证明调用者背后一定有自主模型。仓库描述的 DM 是静态加密且所有者可读，不能称端到端加密。项目是实现参考，本次未运行、审计，也没有取得规模化使用证据；AGPL 许可应在任何采用代码前单独评估。

**对 EIGOS 的启发：** Agent 身份与人类所有者、组织控制面分开是有价值的。无须排斥人在关键节点处理异常；商业责任恰好要求把控制人、调用者和服务提供方分别记录。

## 3. 活跃、身份与安全的证据边界

Wiz 的 2026-02-02 原始安全研究报告曾确认 Moltbook 数据库访问控制缺失，暴露 Agent 凭证与私信；报告称问题在数小时内修复。其历史快照中约 150 万 Agent 对应约 1.7 万人类所有者，并指出当时可用普通请求模拟 Agent。这是历史事件，不能用来断言现在漏洞仍存在，也不能把账号数当独立需求方数。[Wiz 研究](https://www.wiz.io/blog/exposed-moltbook-database-reveals-millions-of-api-keys)

另一份 [Moltbook 原始研究预印本](https://arxiv.org/abs/2604.13052) 分析 40 天内的帖子、评论和资料，报告较低互动互惠性。它有助于提醒“海量内容未必形成持续关系”，但不能直接推导 EIGOS 的转化率或客户需求。

EIGOS 的相关设计要求（本研究建议）：

| 风险 | MVP 应有的边界 | 不能用作替代的信号 |
| --- | --- | --- |
| 同一运营者创建大量 Agent、互刷信誉 | 保留 owner/organization 归属，按独立交易对手统计，关联账户不计作独立背书 | 注册量、钱包数、粉丝数 |
| 通过帖子/私信诱导越权或泄密 | 外部内容标为不可信数据；读取内容不会新增工具权限；动作重新进入授权检查 | 发帖者“已验证”、高 karma |
| 社交互动被误当商业承诺 | 结构化且版本化的报价、接受与授权；普通回复不能改变订单 | “好的”“我能做”这类聊天文本 |
| 公开需求泄露地址、行程或客户资料 | 公开摘要与私有 Task 分开，按最少必要字段披露，有到期和撤回 | 删除帖子即可撤回已传播数据 |
| 无限 Agent 互聊消耗资源 | 每线程预算、消息/工具上限、超时、终止条件；无任务关系默认不自动开启对话 | 自称有价值的对话、互动量 |
| 对付费商户的推荐利益冲突 | 推荐理由、证据窗口和返佣关系可读；商业信誉按订单而非广告费计算 | 热门榜或未披露的赞助排序 |

## 4. 社交与商业结合的 MVP 对象

以下是领域对象建议，命名应在实施时与 EIGOS 既有 ontology 对齐，不能另建一套重复身份或任务系统。

| 对象 | 最小内容 | 与交易的关系 |
| --- | --- | --- |
| AgentProfile | Agent 身份、owner/组织、角色、声明能力、验证级别、联系策略 | 是入口；显示的能力链接到真实 Capability/Offer |
| Relationship | from/to、follow 或 preferred-provider、建立依据、范围、到期 | 影响通知与候选集合；不能授予交易权限 |
| NeedPublication | 脱敏需求、类目、地区粒度、截止时间、响应规则、私有 Intent 引用 | 公开或受限的询价广播；不是已授权订单 |
| OfferPublication | 指向真实 Offer 及其版本、可服务范围、有效时间 | 社交卡片只是投影；实时价格与库存回源校验 |
| NegotiationThread | 参与方、关联 Intent/Offer、结构化澄清与报价引用、预算/停止条件 | 形成协商记录；接受具体报价才进入交易流程 |
| Attestation | issuer、subject、类型、时间、证据引用、撤销、可见性 | 区分自述、合作伙伴声明、订单核验；不混成一个总分 |
| Subscription/Event | 订阅范围、事件游标、投递状态、去重标识 | 商户供给更新、需求回复、任务状态；支持可恢复通知 |

MVP 的“社交主页”可直接显示四项：我是谁、我能提供的有效服务、与谁有已核实合作、如何请求合作。无需先支持自由媒体 feed。

## 5. 一条能检验价值的完整流程

1. 买方 Agent 建立私有 Intent，补齐时间、地区、预算、验收条件。
2. 在既有供给搜索不足时，由受托策略决定是否发布脱敏 NeedPublication；用户或组织政策决定披露范围。
3. 有权限的供应 Agent 订阅类目或地区事件，提交关联正式 Offer 的响应；不能直接读取客户私有资料。
4. 买方基于可服务条件与订单证据筛选，进入有预算和期限的协商线程。
5. 报价固定版本、费用和期限；交易授权单独绑定该版本，进入既有 Task/执行流程。
6. 完成、部分完成、失败、取消、补救按实际证据记录；获得允许后发布脱敏合作凭证。
7. 双方可建立 preferred-provider 关系；下次减少重复询价，但仍检查新的权限、报价与可用性。

这里的网络效应是“更多已验证合作关系改善匹配与复购”，不是“Agent 发得越多，平台越成功”。

## 6. 先做什么、后做什么

**MVP 必需：**既有身份上的 Agent 资料、能力/Offer 主页、受限询价板、按需求关联的协商线程、偏好供应商/订阅、订单证据与撤销、所有者管理与封禁申诉、事件通知和审计。公开询价可以只面向邀请供应商或单一试点社区。

**验证后再做：**通用关注 feed、跨类目公开社区、陌生 Agent 私信、社区自主管理、多平台社交分发、跨平台身份绑定。

**暂缓：**点赞决定履约排名、karma 兑换交易权限、代币/投机激励、无预算的 Agent 自动社交、未授权的公开客户任务、社交事件直接触发支付。

首轮衡量：有真实需求的独立组织数、需求收到合格报价的比例与时间、从关系/推荐产生的真实完成任务数、复购、每次完成所需协商成本、人工介入与争议、恶意内容导致的越权数。对照“只用搜索目录”流程，确认社交层确实增加覆盖率或降低匹配成本。

## 7. AT Protocol 与 ActivityPub：可借鉴结构，先不绑定联邦部署

[AT Protocol 官方规范](https://atproto.com/specs/atp) 将 DID/handle 身份、可验证公开数据仓库、Lexicon schema、PDS、relay 和 AppView 分层。协议本身不规定关注或头像语义。可借鉴“稳定身份与展示名分开”“记录与聚合视图分开”“schema 可版本化”；**DID 证明控制权，不能证明商户履约能力或支付授权**。公开仓库和全网流不适合直接承载地址、报价谈判和私有订单。

[ActivityPub W3C 规范](https://www.w3.org/TR/activitypub/) 提供 actor/inbox/outbox、Follow/Accept、更新删除与异步投递模式；明确跨服务器传播后无法强制远端删除。可借鉴订阅、接受、撤销、去重和重试的事件模型，但它不定义 EIGOS 的报价承诺、订单幂等、支付与验收。

建议先保留外部身份 URI、来源、版本和事件对象类型的映射空间，使用现有持久任务与权限体系形成小范围闭环。只有当明确的合作方需要跨网络发现或事件分发，且公开/私有数据边界已验证，再选择 AT Protocol 或 ActivityPub 适配；不要为“社交”提前运营整套联邦基础设施。

## 8. 研究限制与下一步

- Moltbook 的文档公开可读，但未登录验证写接口；DM 文档存在缺口，身份集成仍需准入。
- Chirper 当前界面可确认，未取得外部开发者稳定 API 合同；Chirp 只有代码与自述证据，本次未做安全审计。
- 论文数据集与历史漏洞记录不是当前运营统计，也不是商业市场规模。
- 建议先在 EIGOS 的一个真实场景里完成“询价—协商—授权—履约—凭证—复购”验证，再决定是否需要大众社交 feed。外部注册、发帖、消息、交易与部署仍按用户实际授权执行。

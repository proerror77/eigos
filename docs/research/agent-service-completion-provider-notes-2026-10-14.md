# Agent 服务完成：供应网络资料阅读笔记

阅读日期：2026-10-14。范围：Virtuals ACP、Nevermined Pay／SDK／Catalog、Skyfire。这里区分文档承诺、项目方演示与独立生产验证；本次没有实际采购、执行任务或验证链上交易。

## 结论

不能把现状概括成“没有真实执行网络”。至少已有可发现、可调用、能返回交付物的服务接入体系，以及明确的执行与验收角色。尚不能从这些材料证明存在覆盖任意现实业务、能可靠判定最终结果的通用网络。

用户提出的关注点成立：调用成功、扣款成功、提供方宣告完成，与用户所需服务实际完成是不同的事实。执行网络可以复用既有网页、API、人工服务及支付方式；价值取决于对具体结果负责、取得可信证据、处理未完成情况。

## Virtuals ACP

- [Overview](https://os.virtuals.io/acp/overview)：全文已读。官方把 ACP 描述为 ERC-8183 的参考实现，并自述生产迭代与代理接入规模。这是项目方陈述，未独立核验规模与生产成功率。
- [Core Concepts](https://os.virtuals.io/acp/concepts)：全文已读。服务包含价格、SLA、输入要求和交付物；Provider 执行，Client 或可选 Evaluator 验收。`submitted` 与 `completed` 分开，完成是批准后的状态。该设计承认验收必要，但角色存在不等于评估可靠。
- [Provider Workflow](https://os.virtuals.io/acp/cli/provider-workflow)：全文已读。支持 Agent 主导协商和委托，执行后提交交付物。实际业务工作仍由提供方实现。
- [ACP Serve](https://os.virtuals.io/acp/cli/acp-serve)：全文已读。提供方编写接收要求并返回交付物的处理函数，可自托管或部署；同一函数接入多种支付协议。说明已有执行接入，不只是付款接口；文档示例不证明具体业务交付质量。
- [Client Workflow](https://os.virtuals.io/acp/cli/client-workflow)：全文已读。买方寻找提供方、创建任务、等待提交、检查交付物后批准或拒绝。示例的判断由调用方实施，没有展示一套适用于所有业务的客观验收器。

推论：ACP 已覆盖任务生命周期和验收动作；更具体的机会应是业务验收条件、外部事实取证和补救执行，而非仅增加一个“验收状态”字段。

## Nevermined

- [Nevermined Pay](https://nevermined.ai/blog/nevermined-pay-give-your-ai-agent-a-credit-card-with-guardrails)：全文已读，2026-04-07。重点是令牌化卡片、额度／期限／次数／商户限制及授权支付，复用既有卡支付基础设施。该文没有建立通用业务结果验收机制。
- [Payments SDK README](https://github.com/nevermined-io/payments)：README 全文已读，未审计整个代码仓库。支持代理发现、计划、额度、MCP／A2A 授权计费；A2A 用最终事件的 `creditsUsed` 计费，MCP 包装器执行业务处理函数后结算。输出相关定价与业务目标验收不可等同。
- [What One Prompt Bought](https://nevermined.ai/blog/what-one-prompt-bought-building-with-the-nevermined-catalog)：文章正文全文已读，页面标注 2026-10-07。项目方演示 Agent 购买多种服务并组合网页，支持服务聚合已经有具体实现的判断，但本次未独立复现。尤其重要的是，作者明确记录：某些空输出仍收费，某次付费搜索结果不可验证；最终任务也遗漏部分需求并超时。服务排名主要采用可付款性、存活性、使用量和价格一致性，不能替代逐任务结果验收。文中“约 100 次调用、77 次有用”等均为作者测试自述，不是独立基准。

推论：该案例直接说明，具有可采购服务目录并成功付款，仍可能只完成用户目标的一部分。把需求拆成明确验收条件，并对每一项核验，具有独立价值。

## Skyfire

- [Payment Features](https://docs.skyfire.xyz/docs/features)：直接打开连续三次返回错误；搜索工具返回完整的缓存页面，抓取年龄显示约 1.3 年。已读缓存全文，不能宣称核验了当前实时产品。
- 缓存说明提供 API 服务商网络、按需访问、钱包、付款即认证和支出规则。没有描述任务结果验收或跨步骤业务完成机制。这个结论仅限已读页面，不能扩大为 Skyfire 所有产品都不存在相关能力。

## 对服务完成网络的边界建议（分析，不是来源原文）

以结果为中心，可以将一次服务记录成：预先约定的完成条件、负责执行的人或系统、外部状态证据、独立复核结果、失败后的补救或交接。付款记录是可选关联信息。

例如订票的点击只是操作，订单已创建只是中间状态；是否出票、旅客和日期是否正确、票是否可使用才是更贴近结果的检查。商品签收不自动证明商品符合要求，等待 15 天也不自动证明交付完成；时间可以是既有付款约定，而服务完成仍须由其定义和证据判断。不能机械地要求所有业务走托管或链上清算。

一个重要设计问题是明确所承诺的结果范围。例如“预约已确认”可以验收；“活动一定顺利举办”需要更多执行责任与事后证据，不能混为同一个完成状态。

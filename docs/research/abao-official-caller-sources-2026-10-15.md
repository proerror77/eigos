# 阿宝调用方接入：官方公开来源核查

核查日期：2026-10-15。范围：公开的一手资料；不读取账户凭证、不发送接口请求、不提交申请。本文描述公开资料可证明的事实与仍需平台确认的条件，不表示 EIGOS 已获权限。

## 核查结论

支付宝与阶跃的系统级合作，以及 AHA 的服务发现、身份认证、跨域对话和前台执行交接，都有官方资料支撑。但本次公开检索没有取得可直接实施的阿宝调用方 SDK 下载、阿宝 Agent Card URL、发现/任务 endpoint、调用方准入表或完整授权协议。不能由 EIGOS 已有通用 A2A 能力推导它能直接调用阿宝。

对 EIGOS，正确的申请身份应明确为“外部智能体/服务入口的调用方，编排用户任务并委托阿宝完成生活服务”，并要求平台明确纯云端接入是否成立、是否需要手机/支付宝客户端承接授权与确认。官方已提到通过阶跃终端或其大模型进入，不能反向断言只接硬件。将 EIGOS 的服务发布到资源市场，是另一条方向。

## 已核实的一手证据

### 1. 阶跃合作是真实的系统级合作，但不等于公开即开即用 API

蚂蚁集团 2026-07-17 新闻明确：支付宝与阶跃围绕 STEPX 原生 AI 终端展开系统级协同，用户可用自然语言调用阿宝，完成跨应用、多任务执行。该公告没有公开接入条件、调用端点或开发包。

来源：[蚂蚁集团 WAIC 公告](https://www.antgroup.com/news-media/press-releases/1784275200000)。网页正文为动态加载；本次通过限定官方域名的搜索索引读取到上述段落，普通网页读取工具返回空正文。

### 2. AHA 有服务发现和信任链路，但公开演讲不是接口合同

支付宝团队在 W3C WebEvolve 的演讲第 7–8 页（PDF 页索引 6–7）展示：

- AHA-SDK 位于支付宝跨设备通信架构中，平台含 Agent 注册、发现、认证和证书签发。
- 调用链先建立服务池，再通过多轮对话澄清意图，最后交接至前台执行。
- 图中涉及服务列表、登录状态、A2A & RSA、结构化卡片与 CardID，以及安全隧道。
- 架构同时包含智能设备服务端/客户端、支付宝服务端/客户端，不能直接解释为无客户端的纯云端 API。

第 9–11 页展示手机系统、车机、眼镜的合作实例。这支持“跨域协作、保留服务方交互与信任边界”的方向，未给出 SDK 包名、方法签名、HTTP 路由、权限 scope 或沙箱规则。该演讲也不应被称为 W3C 发布的规范。

来源：[支付宝团队 W3C 演讲 PDF](https://www.w3.org/2026/04/hangzhou-webevolve-liu-yunxuan.pdf)。

### 3. 服务供给接入与外部调用资格必须区分

支付宝官方账号对 2026-08 的智能体商业平台说明包括：将商家服务转为 Skills/MCP；为已有 AI 能力的商家提供 Agent 创建、技能编排与运营工具；经 AHA 将服务触达手机、车机、眼镜和 AI 应用。它说明商家供给如何被分发，未公开承诺任意外部云端 Agent 自动取得阿宝调用资格。

来源：[支付宝官方 LinkedIn 平台公告](https://www.linkedin.com/posts/alipay_alipay-has-launched-chinas-first-full-stack-activity-7495117919148736512-TN_K)。

官方开放平台首页有“支付宝 AI 开放平台开启邀测，诚邀商家及服务商体验”入口。对应欢迎页可作为咨询/资格确认入口；不能将其商家邀测直接称为阿宝调用方审批流程。官方网页/移动应用的一般流程是创建应用、配置、审核上线；一般应用上线不等于每项特定业务权限都已开通。

来源：[支付宝开放平台](https://open.alipay.com/?source=xunban1)、[AI 开放平台欢迎页](https://open.alipay.com/ai/ai-resource-center/welcome)、[网页/移动应用说明](https://open.alipay.com/module/webApp)。欢迎页未通过当前公开网页读取器取得正文，具体登录后内容由主任务另外核查。

### 4. 咖啡真实业务有官方案例；它证明产品链路，不证明 EIGOS 权限

蚂蚁集团 2026-06-16 的官方阿宝发布稿明确介绍点餐、打车、家电维修等实际生活服务，但没有公开咖啡菜单、实时价格、配送范围或对外下单接口。

来源：[阿宝官方发布稿](https://www.antgroup.com/en/news-media/press-releases/1781578800000)。

主任务通过浏览器渲染官方正文，核实了两个更具体的例子：

- **2026-08-17 官方稿的 WAIC 演示**：用户向 STEPX Neo 上的 Amoo 提出找附近充电桩并把咖啡送到家的需求。Amoo 根据路线、价格等因素规划，调用阿宝的充电与咖啡 Agent，推荐选项并生成待确认的订单。稿件同时明确合作可由阶跃原生 AI 终端或其大模型承接需求。
- **2026-09-10 星巴克 Coffee Alarm Clock**：用户能设定冰美式定时任务；缺失必要信息会追问；到时发起服务，提示用户确认并完成付款；用户可以取消任务并查看服务状态。

第一个例子证明合作演示包含“送到家咖啡”的意图和订单准备，不能证明该演示实际完成配送；第二个例子明确用户在订单确认和付款环节保持控制。两篇都没有提供外部 SDK、参数或 EIGOS 可用的咖啡业务权限。用户要求的“确认后下单、不自动付款”在产品方向上有依据，但能否由接口精确控制到待支付状态，仍须合同与实测确认。

来源：[蚂蚁集团 8/17 官方稿](https://www.antgroup.com/en/news-media/press-releases/1786946400000)、[蚂蚁集团 9/10 星巴克官方稿](https://www.antgroup.com/en/news-media/press-releases/1789025400000)。正文由主任务当日浏览器读取；当前 web 文本读取器对这两篇返回空正文。

另有瑞幸 Lucky AI 的官方案例，说明在瑞幸支付宝小程序或 App 内可语音点咖啡并经身份核验支付。此案例属于瑞幸端内 AI 付，不是 EIGOS 调用阿宝的证据。

来源：[蚂蚁集团瑞幸 AI 付案例](https://www.antgroup.com/business-development/digital-pay-related-cases-details/1762704000000)。

### 5. 通用 A2A 网关有公开调用条件，但目标必须确实是已授权资源

主任务渲染读取支付宝官方《A2A 网关调用说明》（页面更新时间 2026-08-11），确认其支持 API_Key 或 RSA2 身份认证，其中交易场景使用 RSA2；网关还会校验调用方是否订阅目标智能体，并提供 SSE 流式响应。

这说明“有 API key”不能替代交易签名与目标资源授权。文档中的目标是资源市场 Subagent，不能直接将其中的通用网关地址等同于阿宝/AHA 的已开放任务入口。是否能把阿宝作为目标资源订阅、获取对应标识并合法执行咖啡交易，仍无本次公开证据。

来源：[支付宝 A2A 网关调用说明](https://opendocs.alipay.com/ai/0jb1nq?pathHash=ca854f82)。此项依据主任务当日浏览器渲染读取，当前 web 文本读取器无法解析页面。

## 平台需明确答复的接口、权限与流程

以下是本项目应索取的接入条件，不是已证实存在的接口名称。

| 项目 | 需要取得的确定答案 |
| --- | --- |
| 调用方准入 | EIGOS 这种第三方云端协调器可否申请；允许的主体、产品类型、地区和业务范围；是否必须有移动客户端/终端厂商合作 |
| 正式入口 | 阿宝/AHA 调用方的产品名称、资格申请入口、负责团队；现有 AI 应用是否可追加资格 |
| 协议包 | SDK 下载及版本、A2A 版本/绑定、Agent Card 或服务目录接口、任务创建/续聊/查询/取消、流式与回调合同 |
| 身份与业务授权 | 调用方注册/证书/RSA2 的具体要求；用户授权、绑定及撤销；可传递的偏好/地址；租户隔离与有效期 |
| 交互承接 | 用户如何补问、选店/选品、确认报价；结构化卡片是否要求特定宿主；可否在 EIGOS/PA 的网页完成并回传 |
| 咖啡能力 | 具体品牌和地区；团购券、自取实物订单、即时配送分别是否开放；菜单规格、门店营业/库存、到手价、配送费和报价有效期 |
| 下单边界 | 能否先返回真实报价/订单草稿，用户明确确认后再生成商家订单，并停留在待支付；是否会合并触发付款 |
| 结果与验收 | 商家订单号、状态查询/事件、取消与失败补偿；送达/自取/券核销可取得什么证据 |
| 联调上线 | 测试账号/门店与沙箱覆盖；生产白名单和业务验收；费用、限流及服务支持方式 |

## 买咖啡最小业务验收

在平台明确调用资格并提供有效合同后，逐步验收：

1. 真实发现可在目标地址服务的咖啡品牌/门店，区分实物配送与团购券。
2. 读取用户已经授权的偏好；只补问缺失的规格、数量、地址/自取方式。
3. 取得可追溯的实时规格、库存、商品价、配送费、优惠限制和总价。
4. 向用户展示具体方案。确认前不提交商家订单。
5. 用户确认后只创建一次真实商家订单，得到订单号及待支付状态；不自动付款。
6. 用户如另行付款，验证商家接单及履约状态。待支付订单只能证明下单链路，不能证明咖啡已送达。

目前这一组标准只是可执行的验收定义。公开新闻、架构演讲和通用市场 Agent 的可调用性，都不能替代 EIGOS 使用正式阿宝权限取得真实报价与订单的结果证据。

## 研究边界

- 本次官方公开检索覆盖蚂蚁集团、支付宝开放平台/文档入口、支付宝官方账号、W3C 演讲和阶跃官网线索。
- 未找到公开合同仅表示本轮公开资料没有提供，不能断言平台不存在私有合作接口。
- 未读取或验证 EIGOS 当前账户、应用签名、资源订阅及申请回执；这些由主任务依据本地记录与控制台另行核查。
- 不把支付 SDK、AI 付/Agent Pay、阿宝调用、商家供给发布、任意第三方市场 A2A Agent 混为同一产品。

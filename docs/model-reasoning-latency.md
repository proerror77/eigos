# Worker 本体推理耗时、会话复用与实时上下文

一次真实只读路线样本的 10 次模型回复，分为需求解释 2 次、第一次动作决策 2 次、下一次动作决策 3 次、完成判断 3 次。业务读取实际只有三次；模型回复分别负责提出本体读取、理解返回的来源、选择动作或完成。

此前每次回复都使用新的 `codex exec --ephemeral` 进程和会话，重复发送应用提示、完整工具接口及此前的本体读取记录。样本每次输入约 3.2–4.9 万 token，十次模型运行合计 147.38 秒，PA 提交到收到完整结果为 150.668 秒。模型运行包含 CLI 和模型请求，不是纯服务端推理耗时；原始回执及地址保留在本机私密验证目录。

## 优化方式

- 每次需求解释或业务决策使用一个独立、临时的 Codex app-server 会话。该次决策中的多次结构化回复复用上下文；首轮发送完整接口，之后只发送新读取结果和剩余预算。
- 使用简短的业务推理基础指令，避免携带通用代码助手说明。保持原有默认模型选择，没有在代码中指定另一个模型或降低来源验收要求。
- 从当前 Ontology 的注册函数和已绑定对象类型生成函数导航。模型因此可以把已知对象的查询和评估放在同一批请求中。导航只提供定义，不执行函数、不产生数据读取回执或授权。接口同时列出已绑定对象是否已在本次决策中真实读取，并明确所有动作 ObjectRef 参数（包括 scope）都需要本次读取的对象快照；上下文或历史计划中的引用不算已读取。该通用校验说明不选择业务工具、动作顺序或来源对象，也不预先执行读取。
- 每次实际模型回复仍保存独立 RunEvidence、threadId、turnId、时间、输入字节数、模型返回的推理强度／服务档位和 token 用量。会话数减少不能表述为模型回复数减少；必须分别统计。

宿主本体接口仍执行实际 `describe_ontology`、`query_ontology` 与来源评估；没有伪造读取回执、ActionPlan、Intent、Attempt 或独立验收。业务工具映射及依赖继续维护在独立 [Ontology 文件](../ontology/README.md)，没有新增供应商步骤、自动补齐、复查或重试流程。

协议使用 [Codex app-server 的线程与 turn 接口](https://learn.chatgpt.com/docs/app-server)，并以部署主机安装的 CLI 生成协议校验字段。每个结构化 turn 要检查 `turn/completed` 的成功状态和最终 JSON。启动与首个模型回复共用原有执行超时预算，后续每次回复继续使用该预算；不额外设置更短的启动确认超时。单次模型回复预算、每次决策最多 20 次宿主读取、读取字节限制及任务总预算保留。

## 从八次响应中省去机械发现往返

上一版真实样本的八次响应是四个决策阶段各两次：先让模型请求本体上下文，再把数据交回模型作决定。需求解释、第一次动作决策、后续动作决策、完成判断分别耗时24.781、17.233、25.753、26.604秒；模型合计94.371秒，PA提交至收到完整结果101.758秒。

当前原生推理器支持 `worker_snapshot` 上下文模式。Worker在第一次模型响应前，使用同一有权限的本体会话真实读取当前请求、已绑定对象和已登记动作定义。所需的纯评估函数从当前MCP动作的依赖及模块完成定义中取得，并只对已读取的兼容对象评估。定义读取可按实际动作与函数ID裁剪，避免重复返回整份无关字典。这里不调用连接器，不发起MCP业务请求，不生成动作或选择来源候选。

实际结果与回执ID交给模型，模型可以直接选择动作，或主动请求缺失的定义、对象、评估和刷新。只读MCP程序使用这种上下文；复杂业务操作阶段保留原有显式读取循环。未声明支持的模型适配器也保留原有循环。原子工具、模型的工具和参数选择、后续规划及显式完成决策仍然存在。

每次决策的初始上下文最多10次真实读取、约80KB返回数据，单个自动纳入的结果上限30KB；这些读取计入原有20次读取／200KB总预算。超大的自动结果以拒绝回执返回，不取得对象快照信用，模型可用原子接口作更窄的查询。上下文不是跨任务缓存；每个新决策重新读取并校验owner、请求版本、对象和关系摘要。未知或过期的来源保持未知，不扩展权限或授予业务许可。

回执用 `origin=worker_context` 或 `origin=model` 区分发起方；快照模式分别记录纯Worker上下文、混合追加查询或原有模型查询。RunEvidence保留上下文摘要、对应真实回执ID及准备时间，独立观察器重新计算摘要，并确认读取先于模型请求。每个实际模型响应依旧单独统计。

估价返回之后，Worker仍将真实来源对象和评估结果交给模型，由模型显式选择完成证据；随后原有来源核验、硬要求检查及外部MCP回读独立验收。四次是简单只读任务在上下文足够时的目标，不是强制固定次数。

此读取归属契约使用 `ontology-execution-v17`；v16已用于仓库的另一条业务分支，本改动不包含该分支功能。业务对象模型和三份MCP模块未改变。历史任务保留只读，不将旧回执改写成新模式。

## 四次响应后的输入与 PA 开销

2026-10-24 的同路线真实 PA 样本为四次模型响应、四个会话，模型运行合计 50.106 秒，其中会话准备约 8.610 秒，请求发出至运行完成约 41.5 秒。这不是供应商纯推理时间。四次输入合计 137612 token、未命中缓存。PA 提交至收到结果 53.641 秒；原生对话发送到显示完整回复约 81 秒，其中提交前约 12.700 秒、收到结果后约 14.443 秒。供应商估价往返仅 580 毫秒。

当前进一步缩减的是模型呈现和客户端往返：

- 对接口中仅函数名不同、其他约束完全相同的 JSON Schema 分支合并为枚举。原子函数和完整宿主校验器保持不变，不根据路线筛选或预选工具。
- 初始本体定义读取使用 `includeLinks=false`，避免携带 ServiceRequest 面向所有业务的关系导航。实际动作定义中的 MCP 工具映射、依赖、输入和函数仍完整返回。模型可另行使用 `describe_ontology` 取得关系，默认读取仍包含关系。没有省去来源对象或来源状态评估。
- 将任务上下文和实际读取放入同一数据帧。完全相同的重复 JSON 值可用 `shared-json-v1` 字典引用表达；展开后与原数据逐项相等。候选、金额、地址、来源、未知状态和原始回执均不截断。源数据包含保留标记时保持原样，节省不足时使用内联表示。RunEvidence 的 `promptData` 记录实际编码、编码前后字节数和共享值数。
- PA 客户端的 `run` 在一次调用内完成发现、单次提交、等待同一任务、保存原始回执和末次回读，只输出简明交付结果。以同样的输入与目录再运行只续读已保存的 taskId；不确定的提交拒绝自动重发。遇到需输入、授权或失败即停，不替用户回复、授权或重试业务操作。

这一轮未合并需求解释与第一次动作决定：后者依赖前者通过要求校验并实际创建的任务 scope。地点选择依赖真实搜索来源，完成判断依赖真实估价，也不能提前替模型选定。独立主机验收与另一个 MCP 客户端回读继续存在。响应次数仍按实际记录统计，允许额外查询，不强制四次。

这些呈现与客户端调整继续使用 v17 的原有读取归属和验收契约；完整持久账本、读回执摘要、对象版本和来源校验不改。新实测需要另行保存相同自然语言目标、PA 客户端时间分段、模型每次响应、输入字节及 token、供应商往返和独立回读，不能用离线输入尺寸代替真实耗时。

## 合并解释与首次只读动作选择

v18允许同一次真实模型响应返回能力解释及可选的`initialSteps`草案。可选动作从当前、该身份可用的纯只读MCP程序定义中发现，必须没有已返回来源的依赖；定义数量超出初始读取界限时保留普通分阶段规划。动作和参数由模型选择，没有供应商名字、固定步骤或默认首项。

scope尚未创建时，模型在草案的`scopeInputs`中明确指定需要绑定程序scope的输入键，并从`argumentsJson`中省略这些键。Worker先校验解释与用户要求、纯初始化实际scope，再真实读取scope并只绑定这些已声明的槽。注册输入类型、业务参数、条件、动作、owner和领取校验全部继续执行。已有来源依赖的动作、写入、任意对象替换、猜造scope ID和完成主张均不能进入此首轮路径。

首轮计划引用原始grounding响应的同一个RunEvidence，并保存原始草案、初始化前的读取快照、初始化后的绑定快照。独立观察器验证原始模型摘要，展开仅scope槽的绑定，并逐项核对执行输入。不会产生虚构的新模型回复，也不把模型之后的scope读取写成模型之前的知识。解释与绑定合计仍受20次读取／200KB限制；每个回执记录实际`outputBytes`。普通路径继续要求直接模型决定的摘要匹配。

草案或绑定校验失败时不派发动作，记录反馈并回到常规自主规划；取消、领取丢失和迟到返回保护保留。合法首轮草案可在干净释放领取后由新Worker继续，不重跑解释模型。地点候选选择、估价及估价后的显式完成决定继续依据实际返回数据。三次是上下文足够时的实测目标，不是强制响应次数。

PA的`run`默认在同一次客户端调用中等待至多55秒，原有`poll`仍保持45秒。可用私密`--spec-file`保存profile路径、自然语言目标文件、稳定请求ID、回执目录和时间参数；不包含Key或业务计划。PA因此只需要转交简短命令。stdout只投影交付文本，完整结果和来源仍原样保存，减少PA二次解析重复字段的开销。超时继续相同任务，未知提交不自动重发。

新首轮来源与延后scope绑定契约使用`ontology-execution-v18`；旧任务仍只读，不迁移回执。业务对象模型和三份独立MCP工具映射／依赖文件保持不变。实际性能仍需原生PA同路线新任务及独立MCP回读确认。

## 隔离与失败行为

会话可在同一 owner、request ID、request revision 和本体定义摘要内跨只读业务决策复用。每次领取仍使用独立本体读取会话、实时对象快照和当前领取校验；会话历史不能提供当前读取信用或业务授权。不跨用户、任务、回复版本或本体定义复用。取消、租约丢失后的结果不能继续本体读取或业务派发。

app-server 没有 exec 的 `--ignore-user-config` 参数，因此使用独立的临时配置与工作目录，只向既有私密 Codex 认证文件建立引用。宿主不读取或复制认证值，不载入用户的 MCP、插件、hooks、项目指令或历史。线程设为 ephemeral、read-only、approvalPolicy=never，原生执行工具保持禁用；任何意外工具、审批请求、跨线程消息、失败状态、超时或协议超限均终止该会话，不自动切换旧执行器重跑。

Worker 将原生模型失败记录为固定的阶段与错误代码，不再把已执行读取后的规划故障误报成供应商动作失败。该记录不保存上游错误原文，也不触发重试。

调用方只记录结构化输出和回执元数据，不保存隐藏推理或上游诊断文本。任务完成、需输入、失败或 Worker 停止时回收进程、临时配置及会话；活动模型调用取消时立即销毁该会话。干净释放任务领取后最多保留30秒，最多两个任务会话，空闲超时或容量淘汰后从持久任务状态建立新会话，不自动重发业务动作。文档生成的独立 `runStructured` 入口保持原有方式；测试替身可以继续显式使用该接口。

## 同一任务跨决策复用与增量数据

原有单次决策内复用不能省去三阶段之间的启动。当前 Worker 为支持实时上下文的只读决策提供明确任务键，需求解释、来源选择和完成判断因此可以使用一个临时进程和线程，仍分别记录每次实际模型响应。每个阶段重新发送当前阶段指令、输出契约、任务状态及新的真实读取回执。旧阶段指令和输出仅作历史；重启后以持久状态和新读取恢复，没有会话迁移或跨任务缓存。

`session-json-v1` 只把同一会话中完全相同的 JSON 值保存一次。每帧用 offset 明确发布新增字典项，已发送的相同定义、工具接口或来源值以索引表达；变化的事实和新的回执仍完整发送。独立展开器可逐帧恢复与原始 JSON 完全相同的数据。字典最多512项、原始值总计256KB；达到上限后新增值原样内联，来源含保留标记时整帧原样发送。底层本体读取、记录、快照摘要、来源候选和独立验收不删减。模型上下文若发生自动压缩则终止，避免引用缺失的字典；不自动重跑模型或业务动作。

RunEvidence增加 `sessionOpenedAt`、`processInitializedAt`、`threadReadyAt` 和 `sessionReused`，区分进程初始化、线程创建与实际响应等待。复用后的 `sessionReadyAt` 等于当前运行开始时间，启动开销为零，不能把首轮启动重复计入后续响应。`promptData`分别记录本轮逻辑数据字节数、新发送字节数和复用值数。模型 usage 的 input_tokens 可能包含完整会话历史，应与 cached_input_tokens、输入字节和实际等待分别报告，不能将增量输入字节下降直接宣称为全部模型计算量下降。

## 验证口径

协议夹具覆盖会话复用、早于确认的通知、逐回复用量、配置和凭据隔离、跨会话隔离、取消、超时、失败、错误线程及禁止原生工具；这些不是业务联调证据。

性能结论须由本机 Grok PA 提交相同自然语言路线的新任务验证。保留 PA 提交／首次完整结果／对话回报、本体读取、模型回复与会话数、每次滴滴业务调用的起止时间。提交接口的异步受理时间、完整结果耗时和供应商工具往返分别统计；不把供应商客户端往返称为服务端纯计算时间。真实下单和付款继续禁止。


## 从隔离工作区更新本机 PA

主目录有其他开发在途时，在同一仓库的独立 worktree 完成构建，再运行 `npm run setup:pa -- --owner-root <原有管理目录>`。安装器先检查既有运行实例的 owner 记录与两个工作区的 Git common directory 一致，再从当前工作区读取构建文件、依赖、连接客户端与提交号；保留原有运行实例、管理目录和凭据。该选项不能接管其他仓库或未建立 ownership 的实例。


## v20：模型选择只读图与未来证据绑定

v20 在滴滴只读模块声明纯函数输入绑定与可选条件验收。模型可在首次解释中选择有界依赖图；Worker 只在真实来源产生后绑定参数，重新执行来源与硬要求检查。unknown 返回新的模型决策，不自动选择首个候选。模型也可继续分轮规划。后来的 Worker 读取独立记录，不能当成模型已知信息或新的模型回复。合同与迁移边界见[只读数据流说明](ontology-read-dataflow-2026-10-24.md)。

本轮使用同配置隔离实例、相同自然语言路线，旧／新各两次、交替运行：真实模型响应由每次 3 次变为 1 次，模型线程均为 1，供应商业务读取均为 3。受理至独立验收平均 31.681 → 24.004 秒，约减少 24.2%；连续 PA 客户端平均 31.989 → 24.323 秒。另一个只搜索地点的真实目标由模型选择一次搜索，未追加估价。详见[脱敏实测记录](evidence/ontology-read-dataflow-2026-10-24/README.md)。

这些是隔离实例的小样本，不包含原生 Grok 对话派发／回报时间，不能据此宣布常驻实例已升级或所有任务固定一次响应。前述历史 PA 样本与这次目录／负载不同，分别保留原口径。

# N2：对象查询与条件驱动的 LLM 规划

2026-10-18。N2 接入了 N1 对象模型和条件契约，保留 `eigos.delegate`、MCP／A2A、认证、补问与任务读回。独立 Agent 演练和实际模型验证见 [验收记录](evidence/ontology-n2-2026-10-18/README.md)；[人工演练](ontology-n2-human-drill.md) 尚待安排。

## 模型与程序的分工

解释和规划两个阶段都使用同一组有界能力：发现业务类型、查询对象或关系、调用登记函数、核对条件、提出业务决策提案。模型通过结构化消息请求这些能力，Worker 校验后执行本地读取，再把实际结果交给模型。Codex 子进程没有原生 shell、浏览器、MCP、插件或其他 Agent 的调用权限；它不能把模型生成的地址、代码或工具名交给任意执行器。

模型必须实际读取定义与对象，才能返回最终解释或计划。每次模型调用及每次读取都有独立回执。记录输入／输出摘要、对象版本及关系摘要，不保存隐藏推理。模型只提出解释、候选及步骤；计划中的权限、条件检查和证据快照由程序生成，不能由模型自报通过。

每个阶段最多 8 次模型响应，整个任务沿用最多 12 次模型调用；一次模型响应最多提出 4 个请求。一个查询会话最多 20 次工具调用、150 个已读对象和 200,000 字节结果。每轮提示剩余模型／工具预算，并为最终答复保留回合。连续三次相同的读取失败终止该路径；不靠无限重试取得结果。

## 五种模型能力

| 能力 | 作用与边界 |
| --- | --- |
| `describe_ontology` | 按名称／别名读取类型、属性、关系、函数及 Action 定义。模型内默认简要属性说明，可用 includeSchemas 获取完整 schema |
| `query_ontology` | 对象集、单跳关系或准确对象读取，沿用 owner 和字段限制。函数使用对象前先实际读取它 |
| `evaluate_ontology` | 运行登记的只读函数，保留 unknown 和证据等级 |
| `assess_conditions` | 对当前委托按 precondition／result 阶段计算条件；可指定已检索候选或对象，不能借此核验其他委托 |
| `propose_action` | 校验登记 Action 的输入类型、准确对象版本及请求归属，返回固定变更集和提交条件；始终 proposal_only、executionAllowed=false |

公共 MCP／HTTP 继续提供 N1 的三个只读入口。新增的精确对象读取输入为：

```json
{"object":{"type":"DeliveryQuote","id":"已取得的报价ID"},"select":["quoteId","pricingTerms"]}
```

业务决策提案与技术执行步骤分开。SelectOffer 可以表达选择哪份报价，但不会创建订单、付款或获得执行许可。只有现有受控适配器的固定步骤可以进入 Action Runtime；现实副作用拒绝策略继续生效。既有确定性沙箱售后使用显式 trusted_template 路径，仍受原计划、原业务键和准确许可约束。

## 条件与证据

模型在 `conditionsJson` 中提出类型化条件。程序核对原消息及精确引用、对象／角色、阶段、操作符、单位与规则版本；对象引用须来自已检索数据、既有固定条件或用户明确提供的引用。已有硬条件和通用 PA requirements 不能被模型削弱、删除或换成另一种含义。

公斤／kg／克／g 使用明确的精确换算，杯、件、人数保持不同维度；合法单位归一化不等于允许数量改写。路线保留寄件与收件两个角色，不把“从 A 到 B”压成一个通用地点字符串。来源的数字或文本金额均规范化为整数 minor；缺失费用范围继续 unknown。

已有获验证的只读准备结果会在规划前投影为对象，模型可以调查真实的当前记录，而非只看事先拼好的候选摘要。这个映射不调用新的来源，也不声明业务完成。硬性前置条件未知或失败会阻止计划派发；未来结果条件不要求在准备时就已实现，交付前必须按实际观察再次核验。说明文档不能代替合格报价，订金不能代替预订生效。

计划固定本体定义摘要、条件摘要、已用对象及关系版本、读取回执和决策提案。新派发或重新授权前检查对象变化、证据时效及前置条件。已产生未知副作用的原操作仍可只读查证，不能因快照变更自动重做。取消、租约失效或需求版本变化后，迟到模型响应和读取不能继续推进任务。

## 数据范围与 PA 兼容

对象实例始终按受信 owner 隔离。具备 tasks:read 的调用者可让模型在本人对象范围内有界调查；受限联系人、源地址 ID 和原始载荷仍不公开。只有 tasks:write 的 PA 仍可提交并接收本次写操作的响应，但模型只能读取当前委托、其直接关系及从本次委托取得的准确对象，不能借模型枚举其他委托。这个范围在认证边界保存，模型输出不能扩权。

N2 使用 `ontology-execution-v4` 和计划格式 4；业务模型为 `eigos.business@2`，变更类型及函数各自固定版本。v3 及更早任务保留按 owner 读取，不自动迁移或继续执行。对象定义摘要不匹配时明确拒绝重解释。本轮没有切换常驻服务；以后部署前仍须按项目规则核对在途任务和历史数据。

## 验证范围

1. 常规及进程 E2E 回归覆盖模型查询预算、权限、原文约束、前置条件、结果条件、版本变化、取消和原有恢复路径。
2. 实际 Codex 模型经 A2A 提交、本体查询、合成来源和 MCP 读回完成查价；另一次实际模型调查提出 SelectOffer，回读变更集和提交条件，数据库没有发生业务变更。
3. 两个独立 Agent 分别在不继承建模对话或答案路径的上下文完成九题。首轮角色表述问题保留原记录；修正通用定义和数据歧义后，第二个新上下文重新作答。评分依据实际数据和查询轨迹，不以 Agent 自报完成计分。
4. 人工非建模者演练仍未进行；真实商品／预订来源、真实候选方案及领域整体验收属于后续 N3／N4。所有本轮业务数据均为合成，没有真实交易或常驻部署。

复现实际模型验证需明确使用 `--live`，只产生模型调用：

```sh
node --import tsx examples/verify-ontology-planning.ts --live
node --import tsx examples/verify-ontology-decision.ts --live
```

两个程序使用隔离内存库和合成来源；不读取真实个人地址、启动提供方 CLI 或执行付款。输出进入忽略目录 `data/`，公开证据只归档检查过的内容。

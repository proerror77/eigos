# 单项服务盘点与逐项补齐顺序

盘点日期：2026-10-20。运行回读时间：23:15（Asia/Shanghai）。本轮只盘点、核对和排序，不实施复杂行程编排，不修改运行代码、不合并分支、不部署、不续期来源授权、不调用新的供应商业务。

后续更新：用户另行授权整合现有实现，结果见[2026-10-21 整合与本体回读](ontology-integration-readback-2026-10-21.md)。下文保留盘点当时的分支及运行状态，服务缺口和逐项补齐顺序仍有效。

## 1. 结论与判定标准

目前不能把项目整体描述为“各项真实服务都已建立完成”。

- **四类只读服务有真实来源及 PA 往返证据**：本人地址簿、跑腿查价、公开地点查询、Shopify 商品查询／比较。它们完成的是各自明确的读取目标；当前能否再次使用仍取决于实例、身份、配置和有效授权。
- **三类本地工具能完成限定交付**：任务说明、Markdown 草稿、固定范围 CSV 审计。其中草稿只验证格式／摘要，不独立认证内容质量；三者的专用领域本体仍不完整。
- **已有可复用的交易与预约沙箱**：商品查询至模拟交付、UCP 准备／确认、通用预约与 PA 付款交接、通用履约及取消／退款、六类领域服务。不能将这些结果升级为真实供应商履约。
- **航班和日历没有专用服务实现**。餐厅预订有基础对象和计算规则，但没有独立可执行接入。通用预约沙箱不等于航班出票、酒店多晚入住或餐厅真实预订服务。
- **实现分布在分叉代码与不同运行包中**。它们不能直接相加成“当前平台已提供的服务总和”。先对齐已有实现，再逐项收口；不重复开发已有预约付款和商品沙箱。

本报告按五项判断一个服务：**Ontology、完整服务流程、供应商／来源接入、授权、验收**。另外单列实际运行范围与剩余缺口。

“独立完成”只针对声明的业务终点。查价不等于配送；预订确认不等于实际入住；任务说明不等于完成说明中的业务；付款通知不等于供应商收款；沙箱交付不等于真实送达。

## 7. 部分模型、未实现服务与不应混入清单的支撑能力

| 项目 | 已有内容 | 当前缺口／正确归类 |
|---|---|---|
| **航班预订** | TravelLeg 可以描述通用交通段；通用 Booking 可以表达简单服务预约 | 两条分支均无专用 Flight／FlightReservation 类型、航班服务能力或连接器。需航班与航段、旅客、报价与条款、占位／确认／出票、变更取消及独立票证回读。通用预约号不是航班出票能力 |
| **日历忙闲** | 通用时间、来源、权限基础设施 | 两条分支均无 Calendar／CalendarAvailability、日历连接器或日期范围许可。需单独建立账号与日期范围限定的只读服务；不能复用美团来源令牌 |
| **餐厅预订** | Venue、ReservationSlot、ReservationOffer、Reservation，以及空位／确认／订金计算规则 | 有基础模型，但无对应可执行服务与实际餐厅来源。可复用通用预约交接，仍需餐厅、人数、时段、条款、确认及取消的专用流程 |
| **Stripe 测试付款适配** | 主干保留 StripePaymentObservation、测试客户端和测试夹具 | 当前标准启动明确拒绝商家侧 Stripe 配置，目录工厂只容许显式注入的测试 transport。不是已启用独立付款服务；后续遵循 PA 自主付款交接，不恢复 EIGOS 代持用户钱包 |
| **监管／运输规则** | 主干有 CustomsRuleSet、RegulatoryReference、CustomsAssessment 及硬关卡 | 是商品沙箱的支撑能力；结果限定 `pass_sandbox`、`legalApproval=false`。参考文献不证明实时准入、真实税费或进口批准 |
| **网络询价／报价选择** | 成员、发布、私有询价到任务及报价选择、结果卡片 | 是接入和协作入口，不是新增的履约供应商。报价选择不授予订单／付款权，网络成员关系与业务本体仍需统一 |
| **支付宝／阿宝等平台探索** | CLI 前置检查、接入研究及既有沟通记录 | 不在当前执行目录中；平台可登录、应用可见或收到回应，都不能算已有可调用的业务服务 |

## 8. 横向缺口：应该先统一标准，但不先造复杂编排平台

1. **服务目录与真实本体不完全一致。** Brief／Document／CSV 的描述性对象没有注册；部分旧地点／沙箱目录仍使用旧称。应明确实际复用的通用对象或补领域类型，并检查 Action、对象、关系与执行绑定是否对应。
2. **服务流程分散。** 有些在 Agent guidance 和校验方法里，有些在适配器 recipe 与通用状态机里。当前没有统一的、可查询且可校验的服务级流程契约，完整描述输入、合法分支、授权节点、终点、异常和补救。已有 Object／Link／Action 及运行校验必须保留，不因此另起一套执行引擎。
3. **用户请求、来源许可、业务许可、PA 付款各有边界。** 会员自有来源目前针对美团；沙箱预订许可和主干 PA 付款交接不是同一种许可。整合时保持账号、安装身份、来源版本、撤销、期限、金额和原操作身份。
4. **真实写入仍关闭。** 会员分支 `checkDispatchPermit` 只放行明确沙箱业务操作；主干相关业务程序和付款交接也限定合成／测试环境。增加供应商 URL 不能直接变成真实可执行服务。
5. **验收终点必须按服务固定。** “说明已生成”“查询完成”“已预约”“已出票”“已送达”“已退回款项”分别判定。独立回读和对应证据要进入本体，不能从 HTTP 200、Agent 自报或任务状态推断。
6. **取消／补救覆盖不均。** 当前通用沙箱的售后不能自动套到酒店、外卖、医院、航班或通用 PA 付款预约。每项服务必须说明可执行补救与需要人工处理的边界。

建议每项服务补齐一份同样可核验的契约：目标与非目标、输入和补问规则、对象及来源、合法状态／动作、供应商绑定、授权点、成功证据、未知／失败／补救、版本与测试矩阵。首先以已有真实只读闭环实现样板，随后应用于每个单项服务。

## 9. 建议实施顺序

排序依据是现有证据、复用关系和首次独立完成的成本。以下为逐项补齐计划，不表示已经开始实现或取得真实交易授权。

| 顺序 | 单项工作 | 必须交出的结果／退出条件 |
|---:|---|---|
| **0** | **对齐已有实现与服务契约** | 选定统一开发基线；保留主干的受控写动作、商品与预约付款交接，以及会员分支的来源隔离、业务图和摘要。列出模型／任务兼容策略与启用矩阵，验证两边既有回归。不给“合并后编译通过”标注业务完成 |
| **1** | 本人地址簿 | 统一当前版本、本人身份／来源授权、空结果／到期／撤销／换账号流程和独立回读；在有效授权下能单独完成 |
| **2** | 跑腿查价，作为第一份完整服务样板 | 从业务目标和当前对象到预览、适用性核验和 PA 回传；缺信息、更正、失效与恢复明确。只承诺费用预估，不扩成配送 |
| **3** | 公开地点查询 | 对齐实体命名，完成范围、来源、覆盖未知和失败分支；不混用私人地址与商品／库存语义 |
| **4** | 商品查询／比较 | 保留现有 Agent 自选动作；补会员／实例范围、商家配置、无结果和来源失效契约；不赋予采购许可 |
| **5** | 通用预约与 PA 付款交接收口 | 将已有主干实现接入统一业务链；验证准确预约许可、PA 与 EIGOS 凭据分离、固定付款身份、双独立回读与暂停恢复。仍以沙箱为完成范围 |
| **6** | 单项商品购买／履约沙箱收口 | 复用已有 Commerce Agent，逐终点验证购物车、结账、订单、付款、包裹及补救边界；单独建立将来真实商家的接入门槛。UCP 两阶段作为协议适配能力保留 |
| **7** | 酒店预订 | 首个具体预订服务：完整酒店／房型候选、日期人数条款、确认、变更／取消规则和证据。先独立沙箱，再完成一个受控真实来源的准入及只读契约验证 |
| **8** | 预约接送／带司机用车 | 独立的预约确认、时段地点车型、费用、取消／改时与运力异常流程；明确预订确认与实际接送两个终点 |
| **9** | 航班预订 | 补专用领域本体与服务流程，区分预订和出票，覆盖票证、旅客、费用条款及变更退票。先沙箱，不把通用 Booking 或 TravelLeg 当成现成航班实现 |
| **10** | 日历忙闲只读 | 建立独立账号、指定日历和日期范围许可，最少必要数据、有效期与撤销；完成单项忙闲查询，不依附复杂行程编排 |
| **11** | 餐厅预订 | 将现有 Venue／Slot／Reservation 与通用预约基础接通，明确人数、时段、订金、确认和取消 |
| **12** | 即时打车 | 在真实来源契约明确后补等车、取消、上车、到达和最终费用；保留与预约接送的差别 |
| **13** | 外卖 | 补菜单／规格选择、缺货、商家拒单、部分交付、送达和退款；从一个受控供应商开始 |
| **14** | 自驾租车 | 单独验证驾驶资格授权、租期条款、保险、押金、交接验车及押金结清，不能沿用接送服务的完成判定 |
| **15** | 行政挂号 | 从一个受控医院／平台契约开始，完成身份、号源、费用、确认、退号及资料最小暴露；保持非医疗判断范围 |

本地任务说明、文档、CSV 是现成功能的维护收口线：步骤 0 修正目录映射；随后分别补需要的产物／快照／报告关系和适用验收，不以它们替代上面的业务服务主线。原单一行程方案能力保留，但不扩成多系统、多 Agent 行程协调。

真实来源若缺少准入、账号权限或可验证的结果接口，该服务停在清楚的接入门槛，继续下一项独立服务的建模／沙箱工作；不能将合成证据填成真实完成。任何真实下单、付款、挂号或预订都须另有明确授权，本计划不授予这些权限。

## 10. 每项服务何时算完成

单项服务应先达到 **“本体＋流程＋沙箱独立完成”**，再按实际接入证明 **“指定真实来源下可独立完成”**。两个状态分别记录。

每项至少验证：

1. PA 单独提出业务目标，无须知道内部类型、动作名或供应商技术标识。
2. Agent 读取当前本体事实，必要时补问；已有明确事实不重复索取。
3. 可查询的流程、实际可用来源、动作及授权范围一致；无法满足时明确返回缺口。
4. 动作使用准确条款与原操作身份；未知结果先对账，避免重复业务动作。
5. 独立来源回读证明该服务的具体终点，逐项检查用户约束；缺证据保持 unknown。
6. 取消、失效、结果不明、变更和适用补救有明确出口，保留已发生事实。
7. PA 收到正确、完整、可继续处理的业务结果；同一任务通过协议和持久记录独立核对。
8. 记录具体环境、代码／模型版本、来源与有效期；沙箱、源码、CI、部署、真实服务完成分开。

**本轮产出为盘点和实施顺序。复杂行程编排暂缓，尚未执行上述补齐计划。**

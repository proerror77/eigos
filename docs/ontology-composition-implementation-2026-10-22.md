# 本体执行契约与跨服务组合：实现与验收

日期：2026-10-22。对应[已批准计划](ontology-composition-foundation-plan-2026-10-22.md)。

新任务先固定整个用户目标，再由模型发现准确动作绑定、建立各组件的纯输入范围，并依据已接受的来源结果继续选择动作。完成判断逐项检查整个目标；一个组件成功、生成了一份文档或收到 HTTP 200，都不能自行结束缺少其他必需结果的任务。

本次交付是仓库实现和隔离运行验收。没有更新常驻公开内测副本、迁移线上在途任务或开放真实订单、付款。

## 运行与版本

- 本文记录的组合实现基线为 `ontology-execution-v17`／`eigos.business@17`。后续 [Shopify 未付款结账](shopify-unpaid-checkout-2026-10-23.md) 在 v18 增量扩展；v17 摘要保持不变。
- v15 和 v16 的固定定义及摘要保留。当前默认模型不能覆盖旧任务所固定的发布版本；旧 backend 任务保留原始结果，不自动领取、续接或重放。
- 新模型解释只产生整个目标的条件，不再选择一个全任务独占的 `capabilityRef`。模型执行计划使用 v3，每个动作固定自己的定义、程序、提供方、配置、上下文、输入摘要和模型读取凭据。
- 已有明确的调用者直调受管数据动作仍保留 `callerDecision` 和精确预览许可；它不能伪造模型决策，也不能调用外部提供方动作。
- 固定 recipe 代码只服务明确的兼容实现与回归；新原生模型没有失败后转入 recipe 的路径。定义、注册、来源授权、动作许可及业务完成仍是不同状态。

历史旧库不会因安装本次代码而自动激活新内核。生产切换需另外审查旧 Worker 停止、数据库备份、准确发布版本、在途／未知业务效果和回滚安排；不能让新旧 Worker 在同一业务库混跑。此次发布副本检查使用独立目录和隔离数据库。

## 契约、发现与数据连接

`composition-contract` 扩展现有定义注册库，声明具名对象／值输出、类型与接口、输入角色、业务阶段、来源、有效期和已注册校验器。错误角色、阶段、单位、币种、来源、版本或对象快照不能因为 JSON 形状相同而直接连接。接口动作映射也检查输入、输出及证据强度。

`discover_actions` 与 PA 的 `discover_task_actions` 共用任务范围解析器，按当前 owner、请求版本、本体发布、程序和来源配置返回准确绑定。分页按绑定计数；超过初始能力页的服务仍可查询。目录读取不签发许可，来源撤销或配置变化使旧绑定失效。

`prepare` 是模型明确作出的上下文选择，只能建立内部请求对象、解析已确认用户事实。它不读取提供方、不下单，也不能改写已存在组件的范围。来源读取是独立动作。跨动作传递使用持久接受的具名输出，保存原 Intent、观察、来源、时点、版本和证据；不接受模型提供的任意 JSON 路径或伪造中间结果。

文档读取选定来源的公开字段及准确引用回执，调用有界文档模型，保存原模型运行、正文摘要与引用版本。原始文件内容、CSV 冻结字节和准备载荷保留在私有 Intent 账本，不塞进公开本体对象或模型计划。公开查询的有界预览明确标出不完整；原始交付物继续完整保留。

## 授权、预算与恢复

业务写入仍逐个批准。许可绑定实际 Action Binding、固定计划、输入、金额、收款方和期限；每批最多一个业务写操作。原操作结果未知时先查原键，不切换供应商重复提交。

金额占用区分任务总预算与单步许可。例如总限额 100，分别获准的 40 和 50 可以顺序执行，第三个 20 会被拒绝。同一业务承诺的占位和后续付款按同一经济身份核算；服务费与可退押金分别累计，一次操作也可以同时占用这两类额度。未知效果保留占用，退款不作为新消费。模型调用、计划、动作和等待的累计记录不会被重规划或技术恢复清零。

来源续期保留原任务、原业务请求版本和已接受历史，仅退役受影响的组件上下文。模型须明确准备新上下文，不能把新连接授权套给旧私有输入。取消、租约失效、撤权及迟到结果仍以原 Intent／Attempt 为准；迟到事实进入审计，但不能推进已取消任务。

UCP 的发现、报价回读和正式请求之间另有派发检查：即使许可在异步回读期间被撤销，也不能再发送创建／确认请求。新组合路径与显式兼容路径都覆盖了该反例。

售后任务绑定原已核验订单、原已支付金额和独立的取消／退款许可。售后成功不会改写原履约目标的失败或部分交付。无关来源失效不应阻止有权限的原单补救。当前入口仍要求原任务有唯一可补救订单；多个候选会拒绝并要求先消除歧义，不自动挑选。

## 迁移清单

| 范围 | 新执行方式 | 保留的证据边界 |
| --- | --- | --- |
| 商品目录 | 搜索、详情、商家发现、商家回读独立选择 | 公开显示信息、库存数量、合作关系及履约分别判断 |
| 跑腿报价／地址 | 原原子读取按准确程序与成员来源绑定 | 寄件／收件角色不同；报价不等于订单 |
| 交易与 Stripe 测试 | 原原子操作进入逐动作分派 | 订单、独立支付回读与配送分开；仅显式注入测试提供方 |
| 预约与 PA 付款交接 | 领域模块持有付款条款、路由核验与原操作查证 | 原预约与原付款分别回读；当前公共交接协议每任务仍限一个 PA 付款交接 |
| 动态受管数据 | 发布的声明式 CRUD 动作使用同一执行器 | 精确对象写入许可、事务记录、最终版本／删除标记回读 |
| 任务说明 | `PrepareTaskBrief` | 说明可交付，底层业务仍为 `not_started` |
| 文档 | `ComposeDocument` | 模型生成正文及引用证据，不把内容当外部事实 |
| CSV 审计 | 读取冻结源文件，再单独审计 | 五项完整检查、原字节摘要、独立校验与准确模拟批准 |
| 公开地点 | `ReadPublicLocations` | 只发送已准入的城市／关键词；POI 不变成商家或配送承诺 |
| 打车、挂号、外卖、酒店、行程、用车 | 每个提供方分别读取候选、验证并提交原子操作 | 原领域类型、身份、参数、费用／押金与对应终点验证 |
| UCP | 读取条款、创建会话、重新读取确认条款、确认原会话 | 同任务接受前一步结果；不提前完成父任务；订单确认不证明付款到账或送达 |
| Sandbox 履约与售后 | 报价、订单、支付、原单读取、履约观察、取消／退款独立选择 | 原业务键、不重付、部分交付及到账退款各自验证 |

当前清单含 20 组程序声明，覆盖上述全部现有家族；只有实际配置并通过权限检查的绑定才可用。9 个请求／授权／验收概念动作继续保持不可派发，不能变成模型给自己签发许可的工具。旧的包裹读取及文档适配器声明保留为明确兼容记录，不是新原生执行的隐藏回退。

首轮有界范围仍为同一调用者、同一任务固定的本体发布和已准入来源。最多 16 个组件上下文；现有文档引用使用有界的两个来源组。跨成员私有数据共享、任意命名空间合并、无限来源集合和生产支付不在本次实现范围内。

## 验收与证据

机器清单、实际模型记录和发布副本检查集中在[证据目录](evidence/ontology-composition-2026-10-22/README.md)。原始 P0 基线不会被当前清单覆盖。

确定性回归包含：错类型／角色／币种／阶段、私有来源隔离、同名动作多绑定、分页、旧版本摘要、报价变化、来源续期、跨服务总预算与押金、许可撤销、取消、租约失效、未知写入、进程重启、迟到结果，以及 A 成功／B 失败时的部分结果。域规则及原提供方校验器继续复用。

真实模型验收由独立的原生 Codex PA 经 HTTP MCP 提交业务目标；Worker 模型自己查询本体、选择上下文、动作和依赖，文档由独立有界模型执行。驱动不给 Worker 动作序列、不伪造模型读取回执。正常、候选变化、第二服务故障分别验证，并比较 PA、A2A 和独立数据库读取的原任务交付物。复验结果以对应证据文件为准。

真实外部来源使用已有准入：Purity Coffee 的匿名公开 Shopify 目录，以及美团已允许的“北京市／天安门”公开地点查询。它们已在同一原任务中分别读取、核验并进入报告，未读取私人地址簿，也未产生业务写入。该结论不证明商家合作、完整库存、目的地配送、付款或实际履约；验证时的显示价格也不是之后的价格承诺。

`examples/verify-ontology-composition.ts` 是显式启动的验收入口，不进入普通 CI，也不自动部署。默认是隔离提供方；`real_sources` 使用上述本机既有来源与固定公开查询范围。`--resume` 只通过 PA 的 `resume_task` 恢复原有技术暂停任务，不替换任务或删掉累计记录。

本地检查与对应提交的 GitHub Actions 均覆盖类型检查、测试、构建和端到端协议回归。完成同步还须核对本地 HEAD 与远端分支一致、ahead／behind 为零、该提交 CI 成功及本次工作区无未提交文件。部署、版本切换和真实业务完成另行验收。

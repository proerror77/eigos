# Ontology v0.2：三个场景的设计验证

日期：2026-10-18。依据 [Ontology 规格](ontology-spec-v0.2-2026-10-18.md)及按 Palantir 指南修订的[对象目录](ontology-model-catalog-v0.2-2026-10-18.md)。本文件是作者的静态结构走查，未运行独立人／Agent 业务问题演练；下列主体、地址引用、价格、日期、容量、回执与许可均为合成数据，不能作为现实能力证明。

这里验证模型是否能表达正确结果和失败边界。表中的 pass／fail／unknown／needs_human 是规则预期，不是现有代码已通过这些测试的报告。后续将用例转为自动测试，再单独开展获准的真实读取或业务验收。

## 1. 共用验证方法

每个场景依次追踪：原始目标 → 对象与条件 → 所需事实及来源 → 候选与方案 → 动作及授权边界 → 业务观察 → 逐条件结果 → PA 读回。

| 检查项 | 必须能从规格得出的答案 |
| --- | --- |
| 目标 | 是获得信息、取得确认，还是实际交付；何时评价完成 |
| 条件 | 条件针对哪个对象／角色，属于选择前还是结果验收，单位与来源是什么 |
| 事实 | 哪个来源有权支持此属性，是否新鲜、完整、冲突或仅为推断 |
| 动作 | 哪个注册动作、哪个绑定和准确输入可以推进；哪些授权尚缺 |
| 异常 | 无响应、过期、部分完成和未知副作用如何保存及处理 |
| 交付 | PA 读回的结果、解释与实际证据能否对应同一需求版本 |

## 2. D：配送查价

### D-BASE 原始目标与实例

原句：“查询 1 公斤文件从已选的寄件地址 A 到收件地址 B，普通送的当前估算费用，只查价。”A、B 是本设计中的本人地址引用，没有实际地址内容。

| 对象 | 合成实例及语义 |
| --- | --- |
| ServiceRequest | `demo:D`，revision 1，目标为取得当前配送估价；无配送下单目标 |
| Parcel | `demo:parcel-D`，用户申报文件、1 公斤；未发生实际称重 |
| DeliveryRoute | origin=A、destination=B，各有角色和选定快照；二者为已核对的同城地址 |
| ProviderBinding | `demo:delivery-reader`，只读报价能力；不要求零售门店或商品 id |
| DeliveryQuote，实现 Offer | ordinary，估价 `1680` minor CNY；费用范围完整，适用于该申报重量和路线 |
| 事实与证据 | 已选地址／重量来自请求；估价来自假定的有效来源回执，输入摘要绑定原查询；本地刷新上限明确标记 |
| 成功条件 | `parcel.quote_matches_request`；结果披露 estimate、费用范围和有效性；未发生写动作 |

### D-FLOW 逐步走查

| 步骤 | 状态与职责 | 验证结果 |
| --- | --- | --- |
| 1. 理解 | LLM 选择配送查价目标，保留“1 公斤文件、普通送、仅查价” | 不要求将申报重量证明为实际称重 |
| 2. 输入核对 | A／B 未明确时，经已授权地址读取让 PA 补问；本例已选，可直接核对路线 | 不猜地址、技术 id 或把搜索城市当目的地 |
| 3. 请求与读取 | RequestDeliveryQuote 记录准确查价决策；Worker 通过注册的只读 ProviderOperation 取得观察 | 只读许可适用；不创建订单或付款意图 |
| 4. 规范化 | 来源映射产生 DeliveryQuote 对象、Parcel／Route 链接、价格性质与期限属性 | 供应方估价保留为 estimate；不扩大成固定最终收费承诺 |
| 5. 验收 | 对路线、物品、申报重量、服务与回执关联逐项核对 | 全部通过则信息目标 satisfied |
| 6. PA 读回 | 同一任务收到 16.80 元估价、适用条件、来源与时间 | 可以报告查价完成；无需虚构商品或配送已完成状态 |

### D-反例

| ID | 变化 | 必须得到的判断／动作 | 对应规则 |
| --- | --- | --- | --- |
| D-01 | 只给出城市／关键词，没有选定目的地 | 路线条件 unknown，补问；地点列表不满足路线 | 地点角色、`parcel.quote_matches_request` |
| D-02 | 回执实际按 2 公斤或 express 计价 | fail，不交付为原请求的报价 | `parcel.quote_matches_request` |
| D-03 | 用户要求“最终全包价不超过 20 元”，来源只有估价或遗漏必付费用 | 费用上限条件 unknown；可以披露已有估价，不能宣称目标全部满足 | `offer.total_within_budget` |
| D-04 | 计划派发前报价已过刷新期限 | 不用旧值派发；在已有读取范围内刷新，固定新版本 | 事实有效性、RevalidateOffer |
| D-05 | 来源超时 | 查询覆盖为 timeout，费用 unknown；不能填零或称无服务 | 观察与事实分离 |
| D-06 | “查价”被规划成 CreateOrder | 策略 deny；保留只读目标 | `execution.within_authority` |

设计走查结果：共用核心能够表达一次信息目标，领域扩展承载路线、重量和估价。所需变化是类型化映射与规则，不需要虚构 Merchant／ProductVariant。当前真实地址到报价的已有验收可作为后续回归基线，但并未在本轮重跑。

## 3. G：商品送达

### G-BASE 原始目标与候选

原句：“2026-10-21 上午 9 点前，把 20 杯指定规格咖啡送到已确认的公司地址，总支出不超过 500 元。”时区为 Asia/Shanghai，规格在本合成请求中已明确；用户没有允许更换规格或拆单。

| 条件 | 选择前证据 | 执行后证据 |
| --- | --- | --- |
| 20 杯及精确规格 | 匹配 OrderLine／ProductVariant 的可售数量与规格 | 对应业务对象的实际交付数量和规格 |
| 公司地址 | 已确认 destination 快照及可服务该路线的事实 | 实际交付地点与目标一致 |
| 9 点前 | 有效的提供方承诺覆盖该数量和路线 | 实际交付时间，不用系统收到消息的时间代替 |
| 全包不超过 500 元 | 费用范围完整、币种一致且在预算内的报价／上限 | 实际费用或足以核对结算义务的可靠记录；未知费用不视为零 |

| 候选 | 合成来源事实 | 选择结论 |
| --- | --- | --- |
| G-A | 商家 M，经渠道 A；20 杯同规格，完整总额 480.00 元，容量和 08:45 前交付承诺有效 | 可行候选；实际送达仍未知 |
| G-B | 独立商家 N，经渠道 B；450.00 元，20 杯产能未知 | 硬性前置条件 unknown，不可作为可执行方案 |
| G-C | 经渠道 C 返回同商家 M，有证据的身份映射；490.00 元，条件齐全 | 与 G-A 归到同商家，保留不同 Offer；不算第二家商家 |

G-A／G-B／G-C 是 ProductOffer 的实例。LLM 可通过比较函数解释选择；SelectOffer 记录 G-A 的选定关系和方案版本。Comparison 保留 G-B 未知项、G-A／G-C 的同店依据及各自条款。没有查过的渠道不进入“全网最优”声明。

### G-FLOW 逐步走查

| 步骤 | 状态与职责 | 验证结果 |
| --- | --- | --- |
| 1. 固定需求 | Request 保存数量、规格、目的地、绝对期限和预算 | 不把 20 杯改成 18 杯，也不放宽截止时间 |
| 2. 查询与比较 | 获准来源读取经映射形成 ProductOffer；对象集查询／比较函数检查上述事实 | 能区分独立商家、同店不同渠道及未知容量 |
| 3. 方案与计划 | Proposal 固定 G-A 及条款；Plan 绑定业务条件、动作、提供者和验收目标 | 用户看到可行方案，尚未达到商品送达目标 |
| 4. 权限门槛 | 实际环境没有本轮交易许可，必须停在方案／待授权；本表后续只讨论合成许可分支 | 规格本身不授权真实订单或付款 |
| 5. 合成执行分支 | 假定精确沙箱许可；RequestOrder 等决策动作固定意图，Worker 执行创建、付款、观察等 ProviderOperation | 来源映射形成订单／付款记录，不能提前报告送达 |
| 6. 合成结果 | 取得同单 20 杯、原规格、正确地点、08:40 到达及总费用 480 元的独立证据 | 逐条件 satisfied 后，商品送达目标才完成 |
| 7. PA 读回 | 读回原需求、选定方案、各业务状态和条件依据 | 协议完成来源于整体验收，而非远端一句“完成” |

### G-反例

| ID | 变化 | 必须得到的判断／动作 | 对应规则 |
| --- | --- | --- | --- |
| G-01 | G-B 便宜但容量未知；模型断言一般能做 20 杯 | 前置条件 unknown，推断不能补库存／产能事实 | `goods.capacity_covers_quantity` |
| G-02 | 两渠道名称相同但没有商家身份映射证据 | 同店关系 unknown，不擅自合并身份或报价 | 带来源的身份关系 |
| G-03 | 候选同名，但杯型或配方不同且未允许替代 | fail／规格不兼容；不因名称相同视为同款 | `goods.variant_matches` |
| G-04 | 只有“预计 08:45”，用户硬性要求 9 点前送达 | 承诺条件 unknown；披露局限或请求用户改变要求，不能自行放宽 | `delivery.commitment_covers_deadline` |
| G-05 | 收到订单号、paid 或远端 COMPLETED，但没有交付证据 | 送达条件 unknown，继续获准观察或人工核实 | `delivery.receipt_matches_request` |
| G-06 | 08:30 只送到 18 杯，另 2 杯仍在路上且尚未到期限 | Fulfillment=partial，保持等待；不完成、不提前判全部失败 | 部分完成与评估时点 |
| G-07 | 到期仍只有 18 杯，或供应方终结交付明确缺 2 杯 | 数量／期限条件 unsatisfied；保留已交付事实，按授权进入关联补救 | 逐条件 OutcomeAssessment |
| G-08 | 商家已接单，本地在保存回执前崩溃 | effect_unknown；查原业务键，不换商家或重下单；未知支出仍占用额度 | ActionIntent／Reconcile |
| G-09 | 退款已受理，到账结果仍未知 | 退款需求 pending／unknown；不称退款完成，也不把原购买改为成功 | 独立 Refund／AfterSalesCase |

设计走查结果：选择前可行性、实际交付和售后分开建模；供给不足、失败及部分完成均有表达。多提供者比较的反例不要求现实中必须存在两个供应商。真实商品供给、订单及交付证据仍需以后取得相应渠道契约与具体授权。

## 4. R：餐厅预订

### R-BASE 原始目标与实例

原句：“帮我预订餐厅 V，2026-10-23 晚上 7 点，4 人，取得确认；如需订金，最多 100 元。”时区为 Asia/Shanghai。V 是合成餐厅标识；订金上限是一条需求约束，不单独构成执行付款的准确许可。

| 对象 | 合成实例及语义 |
| --- | --- |
| ServiceRequest | `demo:R`，目标为有效的已确认预订，非排队、推荐或实际用餐完成 |
| Venue／ReservationSlot | `demo:venue-V`，2026-10-23 19:00+08:00，4 人；可用性带查询时间与期限 |
| ReservationOffer，实现 Offer | 需要 50 元订金；保留期限和取消条款明确 |
| Reservation | 本地关联 `demo:reservation-R`，真实外部确认号在本场景中仅用合成观察模拟；未观察到时保持缺失 |
| Payment | 订金状态独立保存；与该 Reservation 及收款方关联 |
| 成功条件 | 准确餐厅、时间／时区、4 人；`reservation.confirmation_effective`；满足实际要求的生效条件 |

### R-FLOW 逐步走查

| 步骤 | 状态与职责 | 验证结果 |
| --- | --- | --- |
| 1. 查询 | 获准的时段来源读取经映射形成 Slot／ReservationOffer，对象集与函数返回可用选项 | 可查到不等于占位，更不等于已订妥 |
| 2. 选择 | Proposal 固定时段与生效条件，比较订金是否在需求上限内 | 缺取消条款是否阻塞，取决于用户条件及动作所需信息，不自行猜测 |
| 3. 权限门槛 | 实际环境停在方案／待授权；后续为合成许可分支 | 只有可用时段或订金上限都不授予实际 reserve／payment 权限 |
| 4. 申请／占位 | 假定已获精确沙箱许可，RequestReservation 返回 held 与到期时间 | Reservation=held；等待必要条件，尚未完成 |
| 5. 订金 | 假定准确付款许可，得到 paid 回执 | 只证明订金已付；还需预订确认 |
| 6. 确认 | 餐厅或授权渠道返回同一 Reservation 的 confirmed、餐厅、时间和 4 人信息 | 核对订金条件及所有必需项，目标 satisfied |
| 7. PA 读回 | 返回确认凭据、人数、时间及有关条款 | 不要求实际到店用餐才完成“取得预订确认”的目标 |

如果提供方明确免费且直接 confirmed，可以跳过 held／付款；不能为套用统一流程制造付款步骤。申请阶段的本地引用不冒充供应商确认号。

### R-反例

| ID | 变化 | 必须得到的判断／动作 | 对应规则 |
| --- | --- | --- | --- |
| R-01 | 只有排队号、团购券或推荐卡片 | 不满足确认预订目标，说明能力或证据不足 | 领域对象与目标类型 |
| R-02 | “19:00”没有日期或必要时区 | 输入 unknown，先补问；不得用服务器当前日期／时区猜测 | `reservation.slot_matches_request` |
| R-03 | 订金 paid，但预订仍 pending | 预订结果 unknown／等待，不报告已订妥 | `reservation.confirmation_effective` |
| R-04 | 未确认的 hold 已过期 | held → expired；不沿用旧占位付款或自动新建预订 | Offer／Hold 有效性、授权复核 |
| R-05 | 回执 confirmed，但实际 2 人或日期／时区不同 | 对应条件 fail；不得修改原需求使其通过 | `reservation.slot_matches_request` |
| R-06 | 提供者明确无需订金，且确认符合 4 人和时段 | 直接满足目标；无需人为插入付款 | 领域动作前置条件 |
| R-07 | 取消受理但预订仍有效，或订金退款仍处理中 | 分别记录取消／退款状态；原确认记录保留，售后目标未完成 | AfterSalesCase／独立观察 |
| R-08 | 供应方回执与用户接到的“已取消”通知冲突 | 保留两份证据，按来源规则查证；无法判定则 needs_human | 事实冲突与证据权限 |

设计走查结果：Restaurant 使用 Venue／Slot／Reservation 与独立订金条件，复用核心需求、Offer、授权、观察及验收。不会借用商品库存／杯数表达人数，也不会将 held、paid、confirmed 合成一个“成功”。目前这些仍是规格和合成验证目标。

## 5. 对照结论与实施回归

| 共用要求 | 配送查价 | 商品送达 | 餐厅预订 |
| --- | --- | --- | --- |
| 明确业务终点 | 匹配请求的当前估价已交付 | 实际商品符合交付条件 | 预订确认且生效 |
| 领域对象 | Parcel／Route／DeliveryQuote | ProductVariant／OrderLine／Order／Fulfillment | Venue／Slot／Reservation |
| 真实来源决定的事实 | 费用及适用条件 | 供给、交易与实际交付 | 可用时段、订金与确认 |
| 可复用核心 | Request／Requirement／Offer／Plan／Evidence／Assessment | 同左，增加业务授权与异步动作 | 同左，采用预订领域状态 |
| 必须保留的未知 | 费用缺项、查询失败 | 产能、最终费用、交付证据 | 日期／时区、生效条件、确认状态 |
| 本轮验证性质 | 静态设计走查 | 静态设计走查 | 静态设计走查 |

三个正常路径及 23 个编号反例均已逐项写出对象、条件或证据依据及预期处理。作者的结构走查覆盖了这些情形；它不证明独立参与者可以发现正确对象和路径，也不代表对应 schema、规则或运行路径已实现。按官方方法要求的独立演练仍待进行。

后续自动回归按以下边界组织，优先扩展现有测试：

1. **契约／规则测试**：把 D-01～D-06、G-01～G-04、R-01～R-06 转成角色、阶段、单位、费用范围和状态规则反例。
2. **规划测试**：针对固定需求，禁止改数量／规格／期限、选未检索绑定、跨 owner 引用或把占位当确认；先用可控模型夹具验证规则，再单独评价真实模型解释。
3. **运行／恢复测试**：扩展现有独立进程故障注入，覆盖 G-05～G-09、R-03／R-04／R-07／R-08 的证据聚合、部分进展、原键查证与售后。
4. **真实验收**：只在后续明确范围内启动；PA 发起、真实模型决策、实际来源与同任务读回分别有证据。来源不存在或权限不足就报告缺口，不能以这些合成案例替代。

## 6. 独立业务问题演练主持人参考

只向参与者提供[独立题目](ontology-drill-questions-v0.2-2026-10-18.md)和获准数据／通用查询能力。下表是主持人的检查参考，不是必须遵循的唯一导航路线；业务上有效的其他路径也应接受。

| 问题组 | 模型应自然支持的导航 | 预期判断依据 |
| --- | --- | --- |
| QD-1～QD-3 | ServiceRequest → DeliveryQuote → Parcel／DeliveryRoute；报价 provider／evidence 关系与有效性函数 | 原包裹、路线、服务、估价性质和期限匹配；输入变化或过期需重查，不能读取隐藏联系人凑答案 |

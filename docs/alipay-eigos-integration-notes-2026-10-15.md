# EIGOS 接入支付宝 Agent Pay：本地实现核对

核对日期：2026-10-15。范围是当前仓库的接口、领域模型、存储、认证及测试；支付宝能力和准入条件由主研究报告根据官方文档另行核验。以下是接入设计建议，不代表已接入、测试通过、部署或获准真实付款。

## 当前可以复用什么

| 现有实现 | 证据 | 接入时的用途和限制 |
| --- | --- | --- |
| MCP 与 A2A 共用 TaskService、JobStore | [app.ts](../apps/gateway/app.ts)、[mcp.ts](../apps/gateway/mcp.ts)、[a2a.ts](../apps/gateway/a2a.ts) | 可复用同一用户在两种协议间提交、读取和继续任务的能力；支付逻辑也应放共享服务层，避免两套授权和状态处理。 |
| JWT 的 issuer／tenant／subject 隔离 | [domain.ts](../packages/core/domain.ts)、[auth.ts](../apps/gateway/auth.ts) | 可用来拥有任务和支付意图；支付商户凭证、支付宝用户授权与 EIGOS 登录身份不能自动视为同一身份。 |
| requestId／messageId 重试收据 | [store.ts](../packages/core/store.ts)、[integration.md §4](integration.md#4-重试隔离与存储) | 只保障本地同步写入与响应快照，不保障外部扣款 exactly-once。 |
| input-required 与继续任务 | [tasks.ts](../packages/core/tasks.ts) | 可借鉴暂停及恢复机制；当前 answer 只填 deliverable，不能把普通聊天回复当成精确付款授权。 |
| 跨协议、权限、幂等与持久化测试 | [gateway.test.ts](../tests/gateway.test.ts) | 测试源码覆盖这些入口行为；本次未重新执行测试，也没有支付测试。 |

当前严格限定 `service: brief.prepare`，`JobState` 只有 `input-required / completed / canceled`，artifact 固定 `execution: not_started`；[tasks.ts](../packages/core/tasks.ts) 的 `prepareBrief` 在说明齐备时立即完成。支付接入不能通过修改这段函数把“准备好说明”悄悄升级为购买授权。需要独立、显式的业务服务定义。现有 [A2A 输入验证测试](../tests/gateway.test.ts) 还明确拒绝 `service: purchase`。

## 建议的最小分工

`现有 MCP／A2A → 业务任务编排 → 授权记录 → 支付提供方适配器 → 支付宝`

`商家／业务系统 → 交付证据 → EIGOS 验收 → 补交／跟进／经授权的退款请求`

支付适配器负责供应商规定的预下单、支付启动材料、查询、通知核验和可用的退款接口；业务执行器负责创建真实商家订单和获得真实交付。不要把一个支付适配器当成覆盖所有支付宝商家的下单接口。首先确认 EIGOS 是向用户收费的商户／服务平台，还是代用户向第三方商家采购的 Agent；两者的商户身份、授权与 API 路径不同，不能仅凭代码选择确定商业角色。

建议将以下对象分别持久化，字段是 EIGOS 内部设计建议，不是支付宝原生字段：

- **任务**：目标、约定交付、执行阶段、负责人及截止时间。
- **支付意图与尝试**：关联任务和商家订单、收款主体、金额／币种、报价版本、商户订单号、提供方流水、当前支付状态、每次调用结果及查询时间。一项任务允许多个受控支付／退款尝试，不能只存一个 paid 布尔值。
- **授权记录**：授权人及来源、目标动作、订单和报价摘要、金额上限、有效期、使用范围、撤销和消耗状态。报价／收款方／订单变化使原授权失效或重新匹配授权范围。EIGOS 任务 scope 与支付宝付款认证是不同层次。
- **履约与验收**：预期、证据来源和取得时间、核验规则版本、判定与原因。区分待核验、已验收、部分完成、未达标、证据不足。
- **补救动作**：补交／重试／退款申请分别记录“决定、已请求、被受理、确认完成”；退款成功也不抹去原支付与履约历史。

支付成功只更新支付事实；验收依赖交付证据。任务取消不自动等于支付撤销或退款完成；用户关闭付款页面也不证明未扣款。状态名称和转换应在选定服务后确定，避免预先搭建一个过大的通用工作流。

## 必须补齐的工程能力

1. **外部副作用与故障恢复**：当前 `JobStore.once` 在同步 SQLite 事务内执行 action。不能直接把远程请求塞入这个事务。先事务性写入意图与待执行工作，再由持久 worker 执行、记录回执；以稳定商户订单键关联提供方去重。远程成功但本地落盘失败时，先查询和对账，不盲目新建订单重付。提供方具体幂等契约需要核验。
2. **独立回调入口**：[app.ts](../apps/gateway/app.ts) 只有 MCP／A2A 用户 Bearer 入口，没有支付通知处理器。应按支付宝要求解析和验签、核对应用／收款主体／商户订单／金额，使用服务器保存的映射归属租户；不能信任通知任意声明的 tenant。重复、乱序、迟到事件需持久去重和单调／合法状态转换，补充查询修复漏通知。签名有效只证明消息来源和完整性，不证明商品质量。
3. **权限与密钥**：目前只有 `services:read / tasks:read / tasks:write`；增加独立支付／退款权限或等价策略，并在共享业务服务内执行。不能依赖 MCP annotation 作为授权。密钥和支付宝授权材料由服务端管理、日志脱敏，不进入 Agent Card、提示词或通用任务 artifact。当前 Config 尚无支付配置。
4. **客户端支付承接**：现有服务是 HTTP 网关，没有支付宝客户端唤起 UI。如果接入路径要求用户在客户端付款，需要受控的订单展示和支付交接界面或合作宿主能力；MCP 工具返回字符串不证明目标客户端能唤起并完成支付。支付通知与 A2A push notifications 是不同机制，不需为了收支付宝通知就宣称支持 A2A 推送。
5. **协议与商户履约回执的边界**：主研究确认 PC 路径涉及 `page.pay → alipay-bot trigger-payment-signal → submit-payment`，Machine Pay 涉及 HTTP 402 和支付证明，以及 `payment.verify`／`fulfillment.confirm`。这些不是当前 MCP／A2A 客户端天然具备的能力，需分别做宿主和供应商适配。支付宝已经包含商户履约确认与 ACT 存证，不能把“没有履约状态／存证”当作 EIGOS 的竞争空白；EIGOS 可验证商户回执所声称的交付是否满足用户约定，并推进补救。具体字段与能力以主研究中的官方链接为准。
6. **真实执行和验收**：没有商家下单器、后台执行器、订单读回、交付收集或验收器。第一项能力应限定一个能读回结果的真实服务；验收不应只依赖提供方自述或模型自行说完成。沿用[服务完成研究](agent-service-completion-research-2026-10-14.md)的范围：复用支付，重点验证完成及补救。

## 可检验的首轮试点

先确定一个服务商、一个商品／服务、一个交易角色和一个授权路径。场景可选“购买并交付一份约定字段与来源的研究报告”，但前提是该服务商真实提供订单与交付接口且符合支付宝接入要求；这不是已验证的商家覆盖。

本地模拟先验证（Agent Pay 文档明确无沙箱，不能把本地模拟称为官方沙箱）：相同请求只产生一个意图；改金额或收款方不能复用授权；伪造通知不更新状态；重复／乱序通知不重复触发业务；请求超时保留未知并查询；已付款但未交付不会标记任务完成；取消与迟到支付通知竞争后能进入对账／补救；退款受理不被写成退款完成；MCP 与 A2A 同用户读到同一状态且跨租户隔离。

通过本地测试只证明实现逻辑。随后用真实准入材料和服务商合作验证客户端付款、支付回读、交付回读、验收失败和补救结果；真实付款、对外联系与部署仍按用户具体授权执行。首轮成功指标是可验收完成率、错误宣告完成率、证据缺失率、补救完成率与人工介入量，不只记录交易成功率。

### N1 已实现范围

1. 实现具体 Object Type／Property／Link Type／Interface 定义目录，登记主键、标题、别名、属性来源、双向关系、基数及权限。
2. 提供有界对象集查询和关系导航；常规事实在所属对象维护，事件及 SourceReceipt 可追溯，派生值由 Functions 计算。
3. 用 Offer 接口复用 DeliveryQuote／ProductOffer／ReservationOffer 的真实共性；分别表达重量、规格、时段、人数和订金，不建宽泛可空对象。
4. 让条件明确对象、角色、阶段、单位与来源；Action 定义明确变更集／提交条件，来源同步与技术 ProviderOperation 分开；准备三领域合成数据与规则测试。

N1 的验收要求是：三个场景的对象与关系实际可查询，错误语义映射被规则拒绝，缺失证据保持 unknown，当前已验证流程继续通过；为 N2 的独立演练提供模型与数据。该阶段不需要真实来源调用、交易或新权限。

实现和查询示例见 [N1 使用说明](ontology-n1.md)。SourceReceipt 固定对象属性及业务关系摘要；更新数量、地址或归属会使旧证据失效。当前任务和获验证的公开地点／配送报价可投影为对象；完整地址簿、商品及预订真实映射仍未开放。两个 Action 已由 N2 支持经过检查的只提案调用，没有新增执行入口。

## 第一阶段：新后端内核

目标：替换通用委托后端；业务能力、提供者绑定、任务要求、候选、计划、执行和验收各有明确契约。LLM 先理解需求并选择相关本体，再根据实际候选提出计划；程序校验后才执行。

验收：

- 同一个版本化业务能力可登记两个独立提供者；模型不能选择未检索、禁用、无权限或不存在的绑定。
- 需求保存原文、来源、revision、类型化硬条件及偏好。模型不能改写既有要求；计划固定需求摘要和绑定版本。
- 候选逐条件返回 pass / fail / unknown；硬条件失败或未知不得作为可执行方案。
- 计划输入、动作、绑定、依赖、时效及需求版本通过确定性检查。执行和模型调用在数据库事务之外。
- 本地说明和 CSV 用新适配器验证主路径；CSV 全量审计明确拒绝子集，不静默扩大检查范围。
- 旧委托记录保留只读，不自动迁移或恢复执行。前端身份、隔离、幂等、补问和取消保护继续通过测试。
- 通过项目检查，提交、推送并回读对应 SHA 的 CI。

状态：完成。初版内核 f74f106 的118项测试及7次模型调用是 [v2 历史证据](evidence/ontology-backend-2026-10-17/README.md)；本轮已扩展为 v3，并对定义/提供者/配置做摘要固定。v1/v2 计划只读，不作为兼容或执行 fallback。当前代码统一接入文档、美团只读和 CSV；最终同步以本轮对应提交的 CI 为准。

## 第二阶段：真实只读供给与事实规划

目标：将获准的真实来源接入 Resolver，迁入已有专用读取能力；为现实需求产生可审计候选与可行方案。

验收：

- 记录渠道、终端商户、商品规格、价格组成、库存/产能、地区、时效、来源及有效期；无法查到的字段保持 unknown。
- 同店跨渠道归组但保留各报价；同名非同款、超时、报价过期、总费用未知和权限不足均不能误选。
- LLM 仅看到有界检索结果及相关本体，不能虚构店铺、动作或修改20杯/预算/截止时间等硬条件。
- 完成一个现实需求的只读比较及方案读回。两提供者是反例测试覆盖要求，现实供给不足时如实报告。
- 真实模型运行、真实渠道读取与合成夹具分别记录；不以下单或支付证明查询。

状态：通用发现、候选比较与约束反例使用合成提供者验证；现实来源按用户纠正限定为美团跑腿真实查价。实际 PA 已发起并读回；真实模型经 Worker → Ontology MCP → 官方查询程序取得并复查52.5元费用，通过只读和1公斤硬条件的独立验收。见 [本轮 E2E](evidence/service-network-e2e-2026-10-17/README.md)。未知库存、履约能力和送达事实不从报价推定。

## 第三阶段：异步动作、恢复与履约核验

目标：由固定计划驱动 ActionIntent、ExecutionAttempt、Observation 和 Reconciliation；业务结果逐条件验收，异常进入查证或补救。

验收：

- 稳定业务防重键先落盘，网络调用在事务外；外部成功后本地崩溃时查原操作，不重下单或换供应方。
- 取消、租约丢失与迟到回执的事实可保存，但不能覆盖当前任务状态；租约失效不得开始新派发。
- 支付、订单、送达、退款各自观察和核验；订单号不等于送达，退款受理不等于到账，部分成功不等于整体完成。
- 独立验收及失败/补救记录有证据；unknown 不进入已完成或成功统计。
- 先用故障注入验证恢复机制。现实操作与现实履约验收等待具体业务授权及渠道条件，当前禁止真实下单和付款。

状态：完成当前授权范围内的工程验收。独立 Gateway、两个竞争 Worker、独立持久 HTTP 提供方验证接单/模拟扣款后崩溃原键恢复、撤销/取消竞态、部分交付拒绝、退款到账读回及原任务不重开。ActionIntent/Attempt/Observation、累计预算、逐条件 OutcomeAssessment、关联售后及有界私有反馈均已实现。**现实商家订单/资金/配送仍未运行，现实履约不是本次完成声明**；该门槛按原规则继续等待具体业务授权。

## 最终 E2E 门槛（按用户 2026-10-17 12:39 纠正）

两段必须分别有真实运行证据，并能关联到同一 taskId、计划和交付物：

1. **PA 前端接入**：实际用户的 Personal Agent（当前为 Grok Bot／Monk）发现 EIGOS Agent Card，通过既有 A2A 接入提交原始目标；处理必要补问、查询同一任务并实际收到交付物。固定 HTTP 客户端、观察器代提交或历史 PA 测试不能代替。
2. **后端真实读取**：EIGOS 的实际协调模型基于版本化本体规划 `delivery.quote`；Worker 经独立 stdio Ontology MCP 读取定义并调用 `ontology_delivery_quote`，由官方美团程序执行真实 `delivery_preview`。记录输入/结果摘要、来源调用、模型运行收据和独立验收，不能用 fixtures。
3. **只读边界**：仅已有同城地址间的配送查价；不下单、不付款。MCP 不开放创建、支付或取消工具。报价及预计送达时间不证明订单、支付或实际配送。
4. **交付回读**：PA 保存的完整 A2A Task 与 EIGOS/MCP 的 taskId、完成状态和交付物摘要一致；个人地址、电话和凭据不进入公开证据。

独立进程故障注入仍是工程回归：验证竞争领取、崩溃原键恢复、取消/撤销、部分交付和模拟退款；这些 fixtures 不属于上述真实来源或 PA 验收。

本轮类型检查、133项常规测试、构建、7项工程 E2E 与上述实际 PA／真实来源 E2E 已通过。提交推送后的交付以该 SHA 的 CI 终态、远端与工作区回读为准。运行证据见 [两段 E2E](evidence/service-network-e2e-2026-10-17/README.md)。

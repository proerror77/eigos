# EIGOS 的本体与执行边界

2026-10-15 用户明确的产品方向：用户通过 Personal Agent，以 MCP 或 A2A 接入 EIGOS 执行网络；EIGOS 根据需求与业务本体完成服务。本体用于提高任务完成的稳定性，而非只增强聊天回答。

## 目标设计

Personal Agent 提交目标、必要背景和授权。EIGOS 负责澄清、规划、执行与验收。协议只负责传递消息、状态和交付物。

业务本体应明确以下对象与关系：

- Service：服务范围、所需输入、支持的交付物和验收规则。
- BusinessObject：具体业务对象、类型、关系与状态。
- Action：可执行动作、输入输出、前置条件、权限与执行连接器。
- Constraint／Authorization：预算、范围、有效期和禁止动作。
- Execution／Evidence：实际调用、结果、失败、重试依据和业务系统回执。
- Artifact／Acceptance：交付物及其逐项验收结论。

模型理解目标、提议计划、指出信息缺口；确定性执行层核验输入、权限和状态转换后执行动作。只有满足服务的验收条件，才将业务标记完成。工具响应不明时应查证，不能凭模型猜测成功或重复执行外部副作用。

稳定性来自本体定义加上真实连接器、持久状态、幂等、故障恢复和验收证据。单独使用本体，或使用结构化模型输出，不构成稳定性的实证。

## 本轮实现与边界

agent.execute 是真实模型驱动的文档执行能力，完成目标澄清与文档生成；brief.prepare 继续作为明确标注的固定流程参考能力。两者共用任务库和身份边界。

本轮直接 A2A 测试用于验证真实两端的需求提问、回复、上下文续接和交付。它不是对本体驱动业务动作、长期可靠性或支付履约的验证。下一阶段应选一个具体服务，定义其对象、动作和可被程序检查的验收条件，再用实际成功／失败案例检验稳定性。

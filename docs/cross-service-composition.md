# 跨服务任务编排

运行合同 `ontology-execution-v22`，本体 `eigos.business@19`。本次把跨服务编排作为执行内核的一部分，继续使用同一个 `eigos.delegate`、Task、所有者、授权账本和结果查询接口。

## 图与执行边界

同一环境有至少两个已配置的 Ontology Action 程序时，目录提供 `services.compose.live@1` 或 `services.compose.sandbox@1`。模型选择 2–4 个不同程序组成有界无环图。现有滴滴、美团各读取能力、Shopify 目录、参与者免费报名以及配置的交易／预约沙箱可按实际环境参与。旧文档、CSV、预制适配器尚未转换成 Action 程序，不会被伪装成可组合节点；缺少必要服务时不能用部分完成代替整个目标。

每个组件固定能力版本、业务子目标、输入、依赖和原要求／条件的归属。独立组件可以在一个只读 frontier 中并行；有依赖的组件先保持未激活。模型必须显式选择 `CompleteServiceComponent`，由原程序的验证器检查当前来源，再产生 `ServiceComponentResult`。随后显式选择 `ActivateServiceComponent`，只使用预先声明、实际已验收的上游字段来初始化下游。宿主不补选供应商、不添加业务步骤、不重放已完成的动作。

`ServiceComposition` 关联原 Task；其 `components`、`results` 关系可追溯实际程序 scope、输入摘要、依赖结果和来源回执。组件完成不使主任务完成。主任务的最终 complete 再次检查全部组件、原始要求和条件，之后才通过既有 `OutcomeAssessment`／`ExecutionFeedback` 原子写回完整结果。

## 输入传递

图输入包含：

```json
{
  "components": [
    {"id":"geo","capabilityRef":{"id":"geo.search","version":"1"},"goal":"查询公开地点","input":{"city":"北京市","keyword":"天安门"},"dependsOn":[],"bindings":[],"requirementIds":[],"conditionIds":[]},
    {"id":"didi","capabilityRef":{"id":"ride.estimate.query","version":"1"},"goal":"用滴滴查询上游唯一地点名称","input":{"mode":"places","city":"北京市"},"dependsOn":["geo"],"bindings":[{"from":"geo","targetKey":"keywords","path":["places","0","name"]}],"requirementIds":[],"conditionIds":[]}
  ]
}
```

这是模型内部图合同，不要求 PA 手写；PA 仍然表达自然语言目标。每个来源程序通过 `handoffFields` 声明允许传递的类型化结果字段。路径以已验收的 artifact.data.result 为根；未声明字段、原型链键、缺失字段、类型不符及未经许可的私密内容不能传递。消费者被绑定的字段必须从字面输入中省略，并在激活时重新通过其输入 Schema。数组字段只允许无歧义的单项结果；多个候选不能自动取第一项，需明确用户选择后重新解释目标。

当前公开地点名／地址／城市、报名事件时间／标题和预约场所／时间等有明确导出声明。没有导出声明的程序仍可独立参与编排，但不能被任意取出内部数据当作下游输入。

## 要求、授权与恢复

独立目标覆盖核查检查整个图，所有原要求和条件必须分配给组件。共享数量和预算在父级按实际证据求和；其他共享要求逐个检查。缺少金额不是零，也不自动换汇。

涉及共享预算的写入可在图中声明 `budgetShares=[{requirementId,minor}]`：每个相关组件都有固定额度，额度之和不得超过原预算。额度只收紧子组件约束，不授予写权限。没有明确额度时，新的业务提交须等待其他相关组件成本已独立确认。

每个有业务效果的 frontier 仍至多一次写入，每次使用自己的精确计划许可。另一个组件已成功、已有许可或已有付款都不授予本次写入权限。真实下单和付款仍未开放；配置的真实免费参与者报名只使用既有零费用许可。PA 沙箱付款交接同时绑定父任务执行配置与原预约来源配置，仍需原付款和预约的独立回读。付款交接后继续保留原来的写入冻结边界。

所有组件共用同一持久 Task 和执行领取。意图、原操作键、观察及组件结果在领取与 revision 保护下保存。重启继续原图；取消阻止后续组件，迟到结果不能把任务变为成功。已发生的外部效果不会因主任务失败而被假定撤销，也没有隐式补偿性付款／取消。每个组件的反馈与父任务反馈分别标记，组件成功不能计作整个目标成功。

## 常驻升级

安装器继续备份现有任务库、配置和旧版本。跨合同升级前、停止旧进程后各检查一次当前运行版本的未完成任务及未知业务效果，遇到在途工作先停止升级。已退役版本的历史队列不迁移、不领取、不重放。

旧 Task JSON 保留可读。旧本体对象维持原定义摘要，不改写为新类型。Worker 的类型搜索使用 `currentDefinitionsOnly=true`；PA 也可显式使用此参数，只查询符合当前定义的对象。响应标明 `definitionScope=current_definitions_only`。精确读取不兼容旧对象仍拒绝，默认严格查询不变。这允许新任务和历史数据共存，不代表已迁移历史本体或授予新权限。

## 验证边界

工程测试涵盖并行读取、已验收输出到下游输入、每个组件分别授权、PA 付款交接、共享预算／数量、图循环与遗漏、未声明字段、部分成功、取消与重启。真实模型与合成来源、实际常驻部署及只读真实来源验证分别记录，不能互相替代。

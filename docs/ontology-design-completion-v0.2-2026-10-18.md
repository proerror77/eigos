## 2. N3：真实来源与候选比较契约

每个来源登记固定 `sourceId / version / schemaDigest / ownerScope / capabilityRefs / allowedOperations / credentialRef / retentionPolicy / timeoutPolicy`。凭据只保存受控引用。读取白名单由配置建立，模型不能新增端点、扩大地域或将个人账户开放给其他用户。接口存在、账户登录与本次业务许可分别核验。

每次查询回执固定需求 revision、准确输入摘要、实际来源／操作、观察时间、有效期依据、源事件或结果引用、可留存字段及验证结论。响应分别标记 returned、no_results、timeout、requires_access、unsupported_query、error；取消和来源超时必须终止实际进程并记录退出结果。没有退出证据就保留该验收缺口。

来源到对象的每条映射登记字段和单位、目标属性／关系、身份 namespace、版本、缺失值、冲突、撤销和保留策略。缺字段为 unknown，超时不写成“没有供给”。来源 schema 改变在边界拒绝；新映射经过验证再发布。

比较函数的输入是同一需求的已检索候选及 coverage，输出为：

- 固定需求 revision、候选对象／版本、计算规则版本、查询范围与时点；保留支持和排除证据。
- 按实际领域及可兼容价格范围分组；估价、固定报价、订金和含税／配送总额不混排。
- 每个候选有 pass／fail／unknown 条件、有效期、缺失事实及必要补问。硬性失败排除，硬性未知继续取证或披露，不进入可执行选择。
- 同店跨渠道保留多份报价和条款；只有已验证身份关系才归组。未知销售方不能自动升级成明确交易对手。
- 偏好只能在可行候选之间影响选择，不能改变硬条件。只查到一个就报告一个，不能声称“全网最优”。

选定 Proposal 固定具体报价、条款、费用范围和需求版本；执行计划另固定绑定、授权和恢复契约。展示或派发前重新核对时效；刷新产生新报价版本，不覆写原选择。没有额外权限时仅继续已获准的读取。

## 3. 决策 Action 与执行操作

共用提交信封为：Action 定义版本、当前需求 revision、输入对象及 expectedRevision、输入／条款摘要、提交者身份、clientSubmissionId 和授权引用。身份及 owner 由认证边界建立。一次本地提交原子校验所需对象版本、写权限、关系和提交条件，保存变更审计及待处理意图；外部 I/O 不在该事务中。

同 owner、同 clientSubmissionId、同输入返回原提交；同键不同输入冲突。业务操作键绑定原业务意图，技术重试不换键。对象、关系或条件改变时旧提案失效。只读查询／Function 不允许产生这些变更。

原三领域的完整决策定义如下；六类新增定义及已实现运行操作见六类实现 §3。

| Action | 参数及提交条件 | 本地变更集 | 来源结果及未知处理 |
| --- | --- | --- | --- |
| AmendRequest | 原需求、当前 revision、用户明确的新要求；操作未知时先识别受影响意图 | 新需求 revision、条件及失效的 Proposal／Plan 引用；保留旧版本 | 不改已发生订单／付款；无法安全承接的在途操作只查原键 |
| RequestDeliveryQuote | 准确 Parcel／Route／服务、读取权限、完整输入 | Request.progress=planning、selectedRoute、沟通及只读意图 | 回执映射 DeliveryQuote；失败／缺字段不产生虚构价格 |
| SelectOffer | 同需求报价与 revision；时效和前置硬条件通过 | 新 Proposal、selectedOffer、Request.selectedProposal | 不改来源价格、库存、授权或履约状态 |
| RequestOrder | 已选 ProductOffer、订单项、目的地、费用／条款和精确 order 授权 | 请求／沟通记录与 order 意图 | 供应方回执才产生 Order／OrderLine；超时只查原操作，不换商家重买 |
| RequestReservation | 已选 ReservationOffer、Venue／Slot、人数、日期、条款和 reserve 授权 | 预订请求／沟通及 reserve 意图 | 回执区分 pending、held、confirmed；付款不代替预订确认 |
| RequestPayment | 原订单／预订、明确金额币种收款方、payment 授权、累计预算 | 付款意图和预算预留 | 支付观察才形成 paid；未知保留预算占用，不重复付款 |
| RequestChange | 原业务对象、明确变更集、条款差额和 change 授权 | 关联变更请求及独立意图，保留原确认 | 只有来源接受且必要生效条件齐备才更新当前安排；未知不创建替代订单 |
| RequestCancellation | 原业务引用、取消条款与 cancel 授权 | 关联售后事项／取消意图 | 来源 canceled 才表示业务取消；本地 Task canceled 不能代替 |
| RequestRefund | 原已付记录、可退范围／金额、refund 授权 | 关联售后事项／退款意图 | 受理保持 pending；到账金额、币种及原付款关联齐备才 resolved |
| RequestRedelivery | 原不足／错误交付证据、补交数量规格、费用及新许可 | 关联补交需求／意图 | 新交付分配关联原订单项；不重复计算旧交付或删除失败历史 |
| RecordReceiptConfirmation | 获准接收方、原交付引用及具体确认内容 | 人的确认事件和来源身份 | 只支持约定的接收／质量条件，不成为支付或商户状态事实 |

表内未接入的执行操作维持 unavailable。登记 Action 不等于获得外部执行权限。发布支持动作的绑定前，必须提供其实际输入、结果、幂等、查证、错误及撤销契约；不能通过空实现把“不支持查询”当成“未执行”。

## 4. 状态、观察与整体验收

每个领域分别维护业务状态，Operation 是否发生与目标是否满足分别核验。观察包含 provider namespace、原业务键或外部引用、source event／version、occurredAt、observedAt、映射版本及证据等级。

状态更新规则固定如下：

1. 相同事件与相同内容去重；相同事件内容冲突保留双方并进入复核。
2. 较旧来源版本不覆盖当前事实。查询失败不能抹掉已经确认的付款或预订。
3. 未知副作用继续查原键；没有可靠查证契约则交接人工，不自动换渠道、换键或释放未知预算。
4. 领取／取消 fence 只控制新派发和任务推进；晚到事实保存在审计中。失效 Worker 不覆盖新计划，也不能把已取消任务改成完成。
5. 定义／报价／权限变更只影响后续可执行性；历史证据保持原版本。

验收按固定 SuccessCriteria 和业务终点聚合所有相关对象，不仅使用最后一个工具响应。结果包含 criterion、subject、ruleVersion、evaluationTime、supportingEvidence、counterEvidence、status 和未决事项。用户预算使用实际结果金额；订单数量不被调整为已经送到的数量。

进行中的不足可继续等待。业务期限与证据等待期限分别保存：证明晚到、最终数量不足等是 unsatisfied；到了观察上限仍缺回执是 unknown。可人工判断的质量条件进入 needs_human。只有所有必须条件满足才 satisfied，偏好未满足单独披露。

原任务终态不重开。后来取得的证据追加到原业务记录或关联查证／售后任务；退款任务完成不能把原未交付购买改写为成功。

## 5. PA 读回与运行约束

PA 继续以原 MCP/A2A 入口提交目标、回答补问、授权并查询同一 taskId。协议状态沿用现有映射，新增业务状态放在明确的业务数据中，不发明 A2A 标准枚举。

| 业务情况 | PA 可读结论 |
| --- | --- |
| 需要明确地点、时段或选择 | input-required，给具体问题及获准选项 |
| 缺实际业务许可 | auth-required，展示准确计划、动作和费用范围 |
| 来源仍 pending／未知且在观察期限内 | working，说明已发生什么、尚待什么证据 |
| 观察期限耗尽／来源不支持查证 | 需要人工核对或终止自动观察；业务结论保留 unknown |
| 必需结果证据齐备 | completed，交付准确业务终点、来源、时间和逐条件结论 |
| 确认违反目标或来源明确拒绝 | failed／rejected，附失败依据，不提供成功交付物 |
| 本地取消但外部操作已发出 | canceled，注明外部事实仍需查证／取消 |

A2A Task 和 MCP get_task 的 taskId、状态与 artifact 摘要必须一致。只有模型运行证据不算 PA 已接收；只有观察器 HTTP 调用不算用户实际 PA 实测。

预算分为业务费用、执行工具成本及模型成本。未知支出继续占用，退款和新购买不相互抵扣以绕过限额。来源读取、模型轮次、候选数、对象量、输出字节及总等待均有上限；三个相同失败且输入未变时停止该路径，健康 pending 不计失败。

## 6. 图谱、反馈与后续产品阶段

定义发布保持不可变版本；声明、格式测试、只读探测、模拟执行、真实履约分别记证据等级。能力反馈按 owner、目标、领域、地区／时段、版本和样本量保存，unknown、取消、未终结任务保留分母。LLM 只能提出有来源和影响面的改动；验证与人工发布后才成为新定义或新绑定。

聚合渠道和终端直连都通过相同 ProviderBinding 与领域映射进入系统。目录只提供候选声明；默认不连接新的联邦发现服务，不从目录签名推导商家履约信誉。

未来多服务行程以 CoordinationGroup 关联多个独立需求、预算分配及依赖；各子任务保持自己的身份、授权和验收。组合目标要求所有必须子目标通过，部分成功明确显示；存在未知订单时先查原键，不能自动拆成新订单补齐。当前短计划和单次购买限制保留到专门实现与验证之后。

长期偏好采用单独 PreferenceRecord：owner、内容、用户确认／推断来源、适用领域、用途、保存期限和撤销版本；推断不晋升为事实。默认不保存、不跨用户共享。主动服务先建立新提议，只有既有许可准确覆盖动作和费用时才可执行。收费方式、首个真实商家和外部平台条件仍由实际商业与接口决策确定；没有选择时相应功能保持关闭。

## 7. 版本、来源接入与切换

定义包固定对象／接口／关系、函数、Action、映射及验收版本。当前仓库为 v6／模型 4；v5 及更早计划不执行、不自动迁移，历史 Task 只读。旧对象指纹不被新模型自动重解释。

真实来源接入必须逐项取得：正式调用资格、允许动作和账户范围、类型化输入输出、身份映射、金额及时间语义、错误／取消、原键查证、数据保留政策、可核对的业务终点。缺一项只禁用依赖它的动作；读权限不自动扩成订单或付款权限。

未来获准部署时先备份、停止新领取并盘点在途意图；未知外部操作保留原引用并处理查证，不能借升级重做。按构建摘要切换后回读健康、任务库、原 PA 身份、查询及只读 E2E；失败时停止新派发。代码回退不重放旧业务意图，数据库恢复不能抹掉切换后已发生的外部事实。本轮没有执行该流程。

# Ontology 模型验证

这里的模型是领域对象、属性、关系、Interface、Function 和 Action 的可执行定义。三维文件查看是一个可选应用，本体模型的发布与执行不依赖该界面。

## 连续执行验收

`tests/07-protocol.test.ts` 通过认证后的真实 MCP HTTP 入口完成下列流程：

1. 在独立 Ontology 中创建定义提案，准备候选并审核，再激活发布；准备期间正式版本保持原值。
2. 通过新发布的 Action 创建 Route，创建绑定该 Ontology 发布版本的 Scenario。
3. 在 Scenario 中执行修改。正式查询仍返回原值，方案查询返回新值；另一份 Ontology 看不到该方案或对象。
4. 用旧修订号合并时拒绝提交，正式对象保持原值；用已审阅修订号提交后，MCP 查询与独立 SQL 读回均返回新值。
5. 创建并放弃另一个方案；创建、列表、检查和放弃使用一致的数字修订号。TypeScript 客户端能够读取同一份列表和到期时间。

`tests/e2e/gateway.test.ts` 在构建后启动独立 Gateway、Worker 和 Indexer，使用同一个隔离 PostgreSQL schema：

- 原任务完成滴滴估价，来源映射创建对象与 Links；共享名称、时间 Value Type、坐标 Struct 在正式领域定义中被使用。
- 通过派生 `estimateCount` 筛选询价，执行集合聚合，保存并读取动态对象集。
- MCP 提交来源批次，由独立 Indexer 消费；通过 Location Interface 和 Struct 字段过滤读回。
- MCP 提交排程任务，PA 忙闲请求经 A2A 回传到原任务，Worker 在 Scenario 中生成活动。
- 正式查询看不到候选活动；显式合并 Action 提交后，活动可从正式对象查询及结果 Function 读回，Scenario 元数据从 open 变为 merged。

供应商响应、PA 日历和 Agent 决策使用明确标注的合成夹具。该验收证明协议、模型解释、权限、数据库事务及进程协作链路；真实来源返回、模型决策质量与生产业务完成需要独立验收。

## 执行

```sh
npm run check
npm run build
npm run ontology:check
npm test
npm run test:e2e:run
git diff --check
```

`npm test` 自动创建临时 PostgreSQL；测试不会使用生产数据库。CI 包含 01–23 全部测试组及构建后的进程 E2E。真实嵌入模型可先运行 `npm run embeddings:warm` 下载固定权重，再通过 `semantic_configure`、`semantic_index`、`semantic_search` 服务验证自己的授权文本；MCP 工具名带 `ontology_` 前缀。

## 当前边界

- 业务实例继续按 owner 隔离；共享集合和方案元数据不授予底层业务数据访问权。
- 跨本体实例迁移是显式映射的复制，保留源对象；资源包只携带定义，目标运行环境仍需注册相应 Function 与来源实现。
- 扩展查询和语义检索有 10,000 个授权候选上限；向量检索使用精确余弦计算。当前没有把这一实现描述为大规模近似向量索引。
- 物理只读副本、企业数据连接器、其他业务领域和完整 Foundry 应用需要另外配置或开发。可选工作台提供已有模型服务的入口。
- 新增能力的本地和 CI 验证不代表已合并或已部署。内部排程不写入外部日历，询价不下单、不付款。

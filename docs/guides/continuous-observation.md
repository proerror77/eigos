# 持续关注与观察中断

在 Machinery 打开一个可读的业务对象，选择要跟进的过程、阶段和未来截止时间。关注的生命周期独立于单次任务。酒店取消和机票付款默认登记的四小时回查负责近期交易结果；用户可另外授权持续关注，越过这段窗口继续跟进。业务对象的权限、可执行的 Action、来源账号和授权到期时间在后续执行中继续生效。

## 阶段与依据

- **等待事件**适合已有来源生产者的过程。设置目标状态和允许无新证据的最长时间。Indexer 从已提交的业务变化检查条件。来源接入仍由对应连接器负责。等待阶段本身不会注册供应商 webhook。
- **主动回查**需要选择发布定义标记为 `observation/readback` 且绑定原对象的 Action。登记时明确检查间隔或参数。已有相容的原单回查可被观察使用；后续检查继续进入现有 ScheduledActions。审核此标签时应核实执行只读取供应商或管理本地观察，不能用于下单、支付或退改签。
- **关联对象交接**由已批准的 Action 建立实际业务 Link，并在同一事务登记关联对象和负责观察它的排程。发布变更需要保持原契约与当前权限。完成由目标对象的状态与证据决定。

等待阶段可声明 `evidenceProperty` 指向对象上有读取权限的日期时间属性，以来源实际观察时间判断新鲜度。适合“供应商又确认了一次，状态与上次相同”的场景。没有该属性时，依据是当前可见且与对象状态匹配的过程日志转换时间。后台重新扫描对象不会延长来源证据有效期。主动回查阶段也可同时设置来源时间属性与 maxSilenceSeconds，识别读取成功但持续返回旧回执的情况。短期来源静默会显示缺口，期限内出现新证据可继续推进。

## 查询与中断

`start_observation_interest` 接收 `requestId`、原对象 `object`、整体 `deadline` 和 `phases`。创建请求使用稳定 ID，重复提交同一请求可读回原记录。下面是等待进入已出票状态的阶段示例。应根据来源的数据更新时间选择允许静默的时长。

```json
{
  "name": "等待出票回执",
  "process": "FliggyFlightBookingIssuanceStateLog",
  "complete": ["issued"],
  "stop": ["closed"],
  "evidenceProperty": "observedAt",
  "wait": { "maxSilenceSeconds": 1800 }
}
```

`observation_interests` 支持按当前身份分页列出，也可限定原对象。工作台显示当前阶段、证据时间、下一次检查或等待事件、授权截止与中断原因。关注已超期、排程缺失、任务失去执行路径、租约或检查逾期、契约不兼容、来源长时间无新证据时，应先检查该原因及原单，再决定是否重新授权。`cancel_observation_interest` 按关注 ID 停止已授权的后续跟进。关联的第三方订单继续沿各自的业务 Action 管理。

通用关注需要明确的最终期限，单次排程窗口与该期限分别计算。检测依赖运行中的 Indexer 或调用方读取状态；平台停机期间无法承诺即时送达提醒。查询返回的下一次平台复核时间与下一次供应商读取时间含义不同。

## 部署

先使用管理角色运行 `npm run db:upgrade` 创建 `observation_interests` 与待处理索引。Gateway 登记、列出和撤销自有关注，Indexer 领取并推进阶段，Worker 验证授权、关联排程及目标。按这些职责授予所需 SELECT/INSERT/UPDATE 权限，并复核 `scheduled_actions`、`tasks` 和日志读取权限。发布需要使用包含相应对象、ProcessLog、Action 标签和 Link 的定义；授权主体还需要该业务对象及其来源的读取权限。

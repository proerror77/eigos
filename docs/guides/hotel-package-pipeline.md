# 酒店套餐来源映射与优化边界

酒店、房型、房价计划与可销售套餐规格是不同对象。沿用 `HotelProperty`、`RoomType`、`HotelRatePlan`、`RoomInventory` 与 `ProductVariant`，来源商品用 `TravelProduct` 标识。Pipeline 的字段/关系映射、版本与验证机制负责来源接入；它不从标题推定已确认的 SKU、库存、会员资格或预订。

## 当前接入

飞猪查询程序已将来源商品身份与一次候选观察分开。`itemId` 映射到渠道 SPU，展示价、卖点与权益保存在观察中。`prepareFliggyProductPipeline` 只为现有规范投影准备 Intake；映射夹具验证及独立任务证据不能授予权限，也不证明日期可订。

## 完整 SKU 接入前须补齐

| 对象/事实 | 必需的来源依据 |
| --- | --- |
| 商品/SPU | 来源、账号/目录、原生商品 ID |
| 套餐 SKU | 原生 SKU ID 与固定规格版本，不能用标题代替 |
| 住宿组合项 | 明确房型/房价计划、间数、晚数、是否连住、成人/儿童及年龄限制 |
| 附加权益 | 早餐、餐饮、接送、门票等各自的数量、人数、使用次数、条件与期限 |
| 使用条款 | 可用/排除日期、预约提前量、周末/节假日加价、退款与部分使用规则 |
| 日期报价与可用性 | 准确 SKU/版本、酒店、日期、人数、全部必需费用、库存/预约状态、时效 |

套餐组合应通过可版本化的组合项关联房型/房价计划和权益，不复制房型来制造一款新 SKU。房型名称相似仅能生成待核验的匹配候选；跨渠道身份需要当前版本的来源身份断言。纯餐饮套餐不能映射成客房。

套餐“可购买份数”、指定日期“可兑换份数”和客房库存分别建模。购买券或权益不等于已有 `HotelReservation`，更不等于入住完成。

## Pipeline 顺序

1. 固定来源文档、工具、配置、原始观察及 schema 合同。
2. 先导入可验证酒店/SPU/房型，再建立 SKU 与组件的明确来源关系；目标缺失、过期、冲突或不同账号时拒绝更新。
3. 校验来源原生 ID、数量单位、条款与未知状态。营销文字抽取先标为来源宣称，不升级为验证事实。
4. 使用合成夹具验证映射，并以独立来源任务验证对应动作；发布准确本体/Intake，保留历史版本与原任务 pin。
5. 对具体需求独立验价、验库存和验资格；相关字段或关系变化使受影响方案失效。

当前已交付第 1 阶段的搜索/商品投影与 Intake 准备。完整 SKU、组合权益和兑换日历映射需要正式账号提供相应来源字段，不能仅从现有搜索摘要补造。

## 优化准入

先匹配同酒店、同日期、可接受的同房型/床型、间数/人数、退款需求和必需权益。不满足者淘汰，缺失者保持 unknown；仅已验证方案进入确定性总价比较。

用户必需支出为套餐实付价、日期加价、必需未包含服务及税费/服务费之和，减去已确认且归用户所有的优惠。套餐数量、房间数、晚数和权益次数分别计算，防止重复抵扣。

“599 起/1–2 晚”不能除以 2 当成确定每晚价；“¥4xx”不能当作 400。可选权益只有用户确实会使用且条款可兑现时才体现效用。积分/房晚资格和价值单独呈现，不假设所有渠道或套餐同等累计。

用户支出、可退灵活性、需求满足度与平台佣金分别呈现。平台返佣不是用户折扣，缺失佣金率不是 0%；不以高佣金替代用户最优，也不把未归因/未结算收入算成已兑现优惠。

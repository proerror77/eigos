# 查询内核原型（C1–C4）

这是 [查询内核](../architecture/query-kernel.md) 路线 C 的前四个阶段：C1 建立执行引擎，C2 加入权限、派生属性和 Interface，C3 让内核跟随提交日志，C4 让 Object Set 求值和聚合经过内核。

- `kernel/` 是 Rust 服务，基于 Apache DataFusion。它从 PostgreSQL 载入一个发布投影的快照，然后执行 TypeScript 规划层编译出的 Object Set 计划。
- `packages/runtime/kernel/` 是规划层和客户端。

`EIGOS_KERNEL` 默认为 `off`，这时 Gateway、Worker 和 Indexer 只用参考实现；开启方式见下文的路由与影子模式。

## 构建与测试

```bash
cargo build --release --manifest-path kernel/Cargo.toml
EIGOS_KERNEL_BIN=$PWD/kernel/target/release/eigos-kernel npm test -- --suite=46
```

- **服务启动：** 服务只监听 `127.0.0.1`。端口由 `EIGOS_KERNEL_PORT` 指定，不设置时随机分配，启动后输出一行 `kernel_listening` JSON 报告实际端口。
- **测试套件：** `tests/46-query-kernel.test.ts` 在同一份数据上分别用参考实现（`ObjectSets.evaluate`、`aggregate`）和内核执行同一批表达式，逐项比较结果。没有 `EIGOS_KERNEL_BIN` 时，只运行回退测试。
- **CI：** 在套件 46 的 job 里先构建内核，再运行这个套件。
- **发布：** `Kernel release` 工作流手动触发，输入一个 CI 已经通过的 main 提交。它在 ubuntu-24.04（x86_64，glibc 2.39，与生产主机相同）上编译，剥离符号并检查服务能启动，然后以 `kernel-<提交号前 12 位>` 发布二进制和它的 SHA-256。已有的发布不会被替换。

## 覆盖范围

规划层只编译与参考实现可证明等价的部分，其余返回 `undefined`，调用方继续使用参考实现。

- **集合：**
  - `query`：具体对象类型或 Interface，支持 `where`、`filter`、`from`。Interface 查询对每个实现类型分别扫描，再求并集，详见下文；
  - `refs`：跳过不存在的对象、未知类型和不可读类型，与参考实现相同；
  - `union`、`intersection`、`difference`；
  - `traverse`：多跳，集合可以混合类型，每一步按每个源类型分别导航；`as` 按 Interface 的链接名导航。
- **谓词：**
  - `eq`、`ne`、`in`、`all`、`any`、`not`；
  - 数值之间的 `gt`、`gte`、`lt`、`lte`；
  - 字符串的 `contains`。

  谓词按参考实现的二值语义翻译：缺失与 null 相同，`ne` 对缺失值成立，`not` 不会遇到未知值；类型不符的字面量折叠为常量。
- **字段：** 存储标量字段（字符串、整数、数值、布尔），以及下面说明的派生属性。
  - 字段可见性用参考实现的 `Access.cellRule` 判断，副作用与 `cellSql` 相同。
  - 对当前主体整列不可见的字段，在谓词和聚合里一律当作 null。
  - 带单元格策略的字段，只在策略允许的行上显示原值。
- **行安全：** 内核读每个类型的表时都套用同一条行谓词。行谓词来自参考实现的 `Access.rowRule`，即 `rowSql` 的结构化形式，副作用也相同，覆盖三种情况：
  - 对象策略：`equals`、`subject` 和 `member` 三种条件，按 `all`、`any` 组合；
  - 标记：对象的标记必须都在主体的标记里；
  - 模型许可级别：行分级的等级不高于许可，分区都在许可之内；标记都在可用标记里。
- **只能走参考实现的类型：**
  - 文档分块和过程日志要借助别的对象过滤行，仍然只由参考实现执行。
  - 带属性级分级标签的类型也一样。参考实现在每个读到的行上，只为行里实际存在的属性记录该标签；内核不记录一行有哪些属性。

  行规则为 FALSE 的类型不贡献任何行，与参考实现相同。
- **输出：**
  - 分页：按 `canonical(ref)` 排序；内核为每个对象预先计算等价的排序键。
  - 总数。
  - 聚合：对单一类型做 `count`、`sum`、`min`、`max`、`avg` 和 `groupBy`，分组按首个成员出现的顺序排列。
- **出口分级与依赖：** 内核报告参考实现求值同一个集合时会读取的每一行，而不只是最终成员：
  - 每个节点的成员，包括遍历的起点集合、每一步的目标，以及集合运算的每个操作数；
  - 过滤条件用到派生属性时，类型的全部可读行（参考实现先读出全部候选再过滤）；
  - 这些行的派生属性沿关系读到的每一层目标。

  对每个类型，内核返回读到的行数、最高的行分级等级、全部分区，以及这些行带的全部标记。客户端把这些与文档分级、类型分级合并后记录一次，并记下读到的标记，效果与参考实现逐行读取相同。
  - 带对象策略的类型，内核还返回读到的全部行 id，客户端为每一行记录依赖。这类行超过 10,000 个时，交回参考实现，由它决定能否完整求值。
  - 有些行是参考实现连同派生值一起读取的。只要内核读到这样的行，客户端就记录这些派生属性的可见性检查。

## 派生属性

内核按参考实现的 `DerivedProperties` 计算派生属性的值，用在谓词和聚合里。返回对象的值仍由参考实现补读，所以结果里的派生值总是来自参考实现。

- **表达式：** 字面量、属性、四则运算、关系聚合。
  - 属性：存储字段按单元格遮罩读取，也可以是同一类型的另一个派生属性。
  - 关系聚合：`count`、`select`、`sum`、`min`、`max`、`avg`。
    - 每一步只到达可见的目标并去重。
    - 链接分级标签不可见时，这一步什么也到达不了。
    - 关系聚合的值可以是目标类型的存储字段或派生属性。
- **值语义：**
  - 运算数为 null 时结果为 null，除以零得 null；
  - `count` 在没有目标时为 0；
  - 其他聚合只计算非空值，没有值时为 null。
  - 非整数之和的末位可能因求和顺序与参考实现不同。
- **何时计算：** 参考实现读取一行时会计算这一行的全部派生属性，所以只要内核读取某个类型的行，规划层就登记这个类型的全部派生属性。下列任一情况，整个集合都交回参考实现：
  - 有派生属性无法编译，或者对当前主体不是直接可见（整列不可见或带单元格策略）；
  - 引用嵌套字段；
  - 属性 schema 除了类型和数值上下限之外还有别的约束。
- **路径：** 派生关系路径可以经过 Interface（`as`），按实现类型映射到它自己的链接。
- **参考实现会失败的行：** 内核为每个派生值逐行标记参考实现会抛错的情况。只要被读取并需要求值的行里有一个命中，整个请求就交回参考实现，由它报告自己的错误。这些情况是：
  - 运算结果不是有限数；
  - `sum` 或 `avg` 溢出；
  - `select` 到达不止一个对象；
  - 某一步从一个对象到达超过 10,000 个对象；
  - 值违反属性 schema：整数超出安全整数范围，或数值越过上下限。
- **不复现的限制：** 参考实现每次派生求值最多 50,000 次操作，这是资源上限而不是语义，内核不复现。

## Interface 与视图

规则与参考实现相同。

- **Interface 查询：**
  - 每个可读的实现类型各扫描一次，再求并集。
  - 谓词里的字段按类型映射到它自己的属性，存储属性和派生属性都可以。类型没有映射的字段一律读作 null。
  - 只要有一个实现类型把过滤用到的字段映射到派生属性，参考实现就先读出全部候选再过滤，内核按同样的读取记录依赖。
  - Interface 的分级标签不可见时，结果为空。
- **导航：** 遍历、关系查询和派生路径里的 `as`，按每个源类型的映射取实际链接，并检查 Interface 定义。源类型没有实现该 Interface 时，参考实现报错，规划层交回参考实现。
- **视图（`view`）：**
  - 求值结果按参考实现的投影展示。
  - 视图标签不可见时，结果为空，也不求值集合。
  - 只要有成员的类型无法在视图中展示，就交回参考实现，由它报告冲突。
- **聚合：** 带视图或跨多个类型时，每个成员类型把视图字段映射到自己的列，经遮罩后按统一的类型合并，再分组。
  - 整数与数值合并为数值；其他不同类型的字段交回参考实现。
  - 没有视图时，每个成员类型都必须有这些字段，否则交回参考实现。
- **只能走参考实现：** 带属性级分级标签的 Interface。参考实现在投影每个对象时记录这些标签，内核不复现。

## 增量维护与读取版本

内核载入一次投影后，按提交日志持续更新，不再重新载入。

- **载入：** 在同一个 REPEATABLE READ 快照里读取对象、边，以及每个 owner 已提交的最大 `commit_seq`。同一个 owner 的提交按顺序可见，所以这些位置正好对应快照里的数据。
- **应用：** 按 owner 读取这些位置之后的提交，按提交顺序写入改动层。
  - 对象取 `edit_history` 的 `after_values`，删除时为 null；
  - 边取 `link_history` 的 `link` 和 `unlink`。

  读取时，用基础表减去改动的键，再并上仍然存在的改动行。改动超过 4,096 行或基础行数的 1/16 时，合并回基础表；`EIGOS_KERNEL_COMPACT` 可以改这个阈值。
- **版本：** 每次应用都生成一个新版本，与旧版本共享没有改动的表。查询使用开始时的版本，应用和查询互不阻塞。
- **读取版本：**
  - 查询开始时，客户端读取 owner 的最新提交号，内核先应用到这个提交再回答，所以查询能看到它开始前完成的全部 Action。
  - 在 `waitMs`（默认 2 秒）内做不到，或者内核持有的是另一个投影，内核就返回 409，客户端改走参考实现。
  - 响应带上回答所对应的提交号。
- **后台跟随：** `EIGOS_KERNEL_POLL_MS`（默认 1000，0 表示关闭）设定轮询新提交的间隔。轮询只影响新鲜度；正确性来自每个查询自己的读取版本。
- **权限：** 内核不保存权限。规划层每次查询都从当前的访问状态编译行规则，所以撤销立即生效。
- **数据库角色：** 载入、后台轮询和检查点要读取所有 owner 的数据，需要能绕过 owner 隔离的角色。按 owner 追平时，事务里会设置 `eigos.owner`，在 owner 隔离下也能读取。

## 检查点与重启恢复

设置 `EIGOS_KERNEL_DATA` 后，内核把当前版本写成 Parquet 检查点，重启时从检查点恢复，而不是从 PostgreSQL 全量载入。

- **内容：** 每个类型一个对象文件，每个 Link 一个边文件，另有一份清单。清单记录这些文件遵循的定义（数据库 schema、投影、各类型的列与分级属性、Link、分级等级），以及每个 owner 已应用到的提交和它的事务号（`xact`）。
- **写入时机：**
  - 每次全量载入之后；
  - 版本有变化时，每隔 `EIGOS_KERNEL_CHECKPOINT_S` 秒（默认 300，0 表示不定期写）；
  - 收到 `POST /checkpoint` 时；
  - 收到 SIGTERM 或 SIGINT、退出之前。
- **替换：** 检查点先写到一个新目录，写完后才更新 `current` 指针，再删除旧目录，所以中途失败不会损坏上一个检查点。
- **恢复条件：** 以下全部满足才从检查点恢复，否则全量载入：
  - 定义与本次载入相同；
  - 清单里的每个位置，连同它的事务号，仍在这个数据库的 `change_commits` 里，用来识别从别的数据库或重建过的数据库带来的检查点；
  - 文件的列与预期一致。
- **恢复之后：** 内核先应用每个 owner 在检查点之后的全部提交，载入请求才返回。之后每个查询照常带读取版本。

## 路由与影子模式

`EIGOS_KERNEL` 决定 Object Set 求值和聚合怎样使用内核：

- `off`（默认）：只用参考实现。
- `route`：内核能回答的由内核回答，其余由参考实现回答。
- `shadow`：参考实现回答，内核和参考实现再各算一遍，分别在一份分叉的访问上下文里，然后比对两边的结果。
  - 比对不计入数据库语句统计。
  - 设置 `EIGOS_KERNEL_SHADOW_STRICT=true` 时，比对在请求返回之前完成，不一致会让请求失败。
  - 否则比对在请求返回之后进行，只记录警告，不增加延迟。
  - 比对期间 owner 有新提交的，跳过这次比对。
  - 结果不一致时，内核先重新载入投影再比一次，以排除它看不到的提交日志之外的写入。
  - 设置 `EIGOS_KERNEL_SHADOW_REPORT=true` 时，每个进程退出前打印比对、交回参考实现、跳过等次数。

比对的内容：
- 结果（缺失与 null 视为同一个值）；
- 行依赖、读到的标记和出口分级；
- 类型级依赖：内核记录的必须覆盖参考实现记录的。

**内核来源：**
- `EIGOS_KERNEL_URL`：连接一个已在运行的内核服务。它只持有一个投影，需要别的投影时就重新载入。
- `EIGOS_KERNEL_BIN`：启动本机内核进程，每个投影一个，最多 `EIGOS_KERNEL_INSTANCES` 个（默认 2）。需要新投影时，先停掉最久未用的进程。

内核连接 `EIGOS_KERNEL_DATABASE_URL`，没有设置时用运行时自己的连接串。

- 投影在第一次使用时载入。路由模式下，载入完成之前由参考实现回答，不等待。
- 载入失败的投影改由参考实现回答，60 秒后再试。
- 路由模式下，查询不会因为内核而失败。以下情况都由参考实现回答这次查询，并记录一条警告：
  - 内核连不上；
  - 内核服务重启后还没有载入投影（503）；
  - 内核读不懂请求（422），例如运行时比内核新；
  - 内核在这次查询上出错。

  前两种情况说明内核已经失去投影，这时按载入失败处理，60 秒后重新连接，连上后重新载入。

**不经过内核的求值：**
- 在调用方的事务里，内核看不到这个事务自己的写入；
- 在 Scenario 中；
- 正在记录决策证据时，证据要逐条记录读取；
- 求值上限不是默认的 10,000 时；
- 开启 owner 隔离（`EIGOS_ENFORCE_OWNER_RLS=true`）时，不在主体 owner 的上下文（`db.withOwner`）中。内核用的数据库角色绕过行级安全，所以只在行级安全允许参考实现读取这个 owner 的数据时回答。Gateway 和 Worker 都在请求或任务的 owner 上下文中运行。

**游标：**
- 内核的页带内核游标，记录求值的身份、下一页的起点和成员摘要。
- 页与页之间成员变化时，游标失效，与参考实现在数据变化后的行为一致。
- 内核游标只能在内核上继续，参考游标只能在参考实现上继续。内核不可用时，内核游标会失效。

**补读：** 页内对象按类型批量读取（`Objects.readBatch`），检查和遮罩与逐个 `read` 相同。页内有对象已被删除或不再可见时，这一页交回参考实现。

### `Objects.query`（C4b）

`EIGOS_KERNEL` 同样决定 `Objects.query` 怎样使用内核，条件与 Object Set 相同。只有参考实现完整求值的查询才经过内核，也就是有 `filter` 或 `orderBy`、类型有派生属性，或者字段是嵌套路径的查询。其余查询由参考实现按页从存储读取，本来就是一条带键集分页的 SQL。

**排序：** 与参考实现完整求值时一致。
- 先按 `orderBy` 的每个键排序，null 在升序和降序里都排在最后：
  - 数值按 JavaScript 数值（Float64）比较；
  - 布尔值 `false` 在前；
  - 字符串按 UTF-16 码元比较，与 JavaScript 的 `<` 相同。内核用 `utf16_key` 把字符串转成大端 UTF-16 字节，补充平面的字符因此排在 U+E000–U+FFFF 之前，这一点与按 UTF-8 字节比较不同。
- 最后按 JSON 编码的 type 和 id 逐字节比较，与参考实现比较 `JSON.stringify(ref)` 的结果相同。
- Interface 查询按视图字段排序：
  - 每个实现类型映射到自己的属性；
  - 没有映射的类型取 null；
  - 整数与数值合并为数值；
  - 其他不同类型的字段交回参考实现。
- 属性安全遮罩的单元格按 null 排序，与参考实现看到的值一致。

**投影：** 页内对象按 Object Set 的方式补读，再按参考实现的方式投影到查询的类型：
- 列出该类型的每个属性，没有映射或没有值的取 null；
- 有 `select` 时只保留所选字段。

**交回参考实现的查询：**
- `orderBy` 有嵌套字段、列表字段，或者在不同实现类型上的类型不一致；
- 有 `intervalOverlap`；
- `select` 有参考实现会拒绝的字段；
- 补读期间 owner 有新的提交。

最后一条保证同一页的对象和它们的顺序出自同一个版本：内核按版本 V 排序，补读时如果 owner 已经提交到 V 之后，页里的值可能比排序新，这一页就交回参考实现。

**游标：**
- 内核游标记录查询的身份（不含 `limit` 和游标本身）、下一页的起点，以及成员和排序值的摘要。
- 页与页之间成员或排序值变化时，游标失效；其他属性的变化不影响游标。参考实现更严格：任何匹配对象的变化都会让它的游标失效。
- 与 Object Set 一样，内核游标只能在内核上继续，参考游标只能在参考实现上继续。

## 等价标准

以下对比在同一个出口作用域里进行，也就是 `Access.measureEgress`：
- 结果、记下的出口分级和读到的标记必须一致；
- 行依赖和类型级依赖（`view_objects` 与安全摘要）必须一致；
- 字段依赖必须是参考实现的子集。参考实现会读取每一行的全部声明字段；内核记录谓词和聚合读的字段，以及它返回的对象的字段。

类型级检查在规划时完成，输入为空时也照常进行：
- 包括目标类型、链接定义、链接与类型的分级标签；
- 参考实现遇到没有可处理的行时会跳过这些读取，于是记录得比内核少；
- 内核路径因此至少记录参考实现记录的内容，不会更少。

以下各项与参考实现完全一致：引用、顺序、总数、revision、每个有值的属性，以及聚合结果。

缺失值与 null 视为同一个 Ontology 值。参考实现自己会因表达式形态不同，把缺失值写成不存在的键、`undefined` 或 `null`。

## 基准

### Engine Benchmark 08

`scripts/benchmarks/engine-08.ts` 在同一份合成数据上分别运行参考实现和内核：

```bash
cargo build --release --manifest-path kernel/Cargo.toml
EIGOS_KERNEL_BIN=$PWD/kernel/target/release/eigos-kernel \
EIGOS_TEST_DATABASE_URL=postgres://postgres:synthetic-only@127.0.0.1:5432/postgres \
  node --import tsx scripts/benchmarks/engine-08.ts --sizes=100000,1000000 --runs=7 --out=engine-08.json
```

- **数据：** 每个规模 N 有 N 个 Route、N 个 RideRequest、N/10 个 Place，以及 2N 条边。还有一个 Interface `Measured`，由 Route 和 Place 实现。
- **读取：**
  - 过滤 0.5% 后取首页；
  - 从 0.5% 的请求走 1 跳和 3 跳；
  - 聚合 0.5% 和全部 Route；
  - 全部 Route 取首页；
  - 过滤 10% 后按两个键排序取首页（C4b）；
  - Interface 查询。

  每项先预热一次，再运行 `--runs` 次。
- **写入：**
  - 每次单对象编辑的提交耗时，以及紧接着的内核查询耗时，也就是读后写延迟；
  - 导入 1% 的对象作为一次源提交，以及之后第一次查询的耗时。
- **恢复：** 全量载入、写检查点、重启后从检查点恢复的耗时，以及检查点大小。
- **报告字段：**
  - 每项的 p50、p95、p99；
  - 数据库语句数；
  - 内核引擎自身的耗时；
  - 内核进程的常驻内存和峰值内存。Linux 上读 `/proc`；macOS 会压缩内存，读数偏低。
- **超出上限：** 参考实现超出 10,000 个对象的完整求值上限时，记为错误。加 `--skip-over-limit` 后，更大规模上不再尝试。

每晚在 main 上运行 `Nightly` 工作流（`.github/workflows/nightly.yml`）：
- **基准：** 在 10 万规模上运行 Engine Benchmark 08，报告保存为 `engine-08` 产物，保留 90 天。`scripts/benchmarks/compare.mjs` 把它与前一晚的报告比较：
  - 内核中位数变慢 20% 以上时，在摘要里标出；
  - 变慢 1 倍以上时，工作流失败。

  共享 runner 两次运行之间常差几十个百分点，所以门槛只拦截明显的退化，趋势看摘要。
- **严格影子：** 以 `EIGOS_KERNEL=shadow EIGOS_KERNEL_SHADOW_STRICT=true` 运行全量测试，任何比对不一致都会让它失败。摘要汇总比对、交回参考实现和跳过的次数。

### 本机测量（C1–C3）

在本机 Docker 的 PostgreSQL 17 上测量。数据规模：
- Route 和 RideRequest 各 N 个，Place 为 N/10 个；
- 每个请求有一条 `RequestRoute`，每条路线有一条 `RouteOrigin`。

表中取每个用例的第二次运行；"内核"一列包含 HTTP 往返和补读页内对象的时间。

| 用例 | N = 100,000 参考实现 | N = 100,000 内核（引擎） | N = 1,000,000 参考实现 | N = 1,000,000 内核（引擎） |
| --- | --- | --- | --- | --- |
| 过滤 0.5% 后取首页 | 167 ms | 58 ms（6.7） | 8.9 s | 49 ms（9.9） |
| 从 0.5% 的请求走 1 跳 | 121 ms | 43 ms（6.8） | 759 ms | 77 ms（30） |
| 走 2 跳 | 60 ms | 26 ms（6.9） | 889 ms | 77 ms（35） |
| 0.5% 按 lanes 聚合 | 110 ms | 6.7 ms（4.3） | 8.5 s | 14.6 ms（11.5） |
| 全部 Route 按 lanes 聚合 | 20.8 s 后超出 10,000 对象上限 | 12.9 ms（10.8） | 26 分钟后超出上限 | 86 ms（80） |
| 全部 Route 取首页 | 20.5 s 后超出上限 | 44 ms（6.8） | 未运行 | 83 ms（32） |

内核载入耗时与数据量：

| N | 对象 | 边 | 载入耗时 | Arrow 缓冲区 |
| --- | --- | --- | --- | --- |
| 100,000 | 21 万 | 20 万 | 2.2 s | — |
| 1,000,000 | 210 万 | 200 万 | 22 s | 409 MB |

- 409 MB 是按缓冲区容量统计的上限。macOS 上测到的常驻内存受内存压缩影响，偏低且不可信，Linux 上的实测放在 C6。
- 内核端到端时间的大部分花在逐个补读页内对象上，批量补读属于 C4。

增量维护在 10 万个 Route 上测得如下（关闭后台轮询，首次查询负责追平）：

| 阶段 | 首次查询（端到端） | 分页（引擎） | 全量聚合（引擎） | 改动行 |
| --- | --- | --- | --- | --- |
| 载入后（载入 780 ms） | 85 ms（含预热） | 4.2 ms | 16.6 ms | 0 |
| 200 个单对象编辑提交之后 | 53 ms | 7.0 ms | 16.1 ms | 200 |
| 一个 7,000 对象的源提交之后 | 85 ms | 3.6 ms | 10.7 ms | 0（已合并） |

端到端时间里约 40 ms 用于补读页内的 100 个对象。扣除这部分后：
- 追平 200 个提交约 12 ms；
- 追平并合并 10 万行约 40 ms；
- 200 行的改动层让分页多花约 3 ms，合并后回到原值。

重启恢复测得如下（数据规模同上一张表，此时没有待追平的提交）：

| 对象与边 | 全量载入 | 写检查点 | 检查点大小 | 从检查点恢复 |
| --- | --- | --- | --- | --- |
| 21 万与 20 万 | 1.33 s | 211 ms | 3 MB | 159 ms |
| 210 万与 200 万 | 24.2 s | 400 ms | 14 MB | 264 ms |

合成数据重复度高，Parquet 压缩比偏高，真实数据的检查点会更大。

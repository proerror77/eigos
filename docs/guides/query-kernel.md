# 查询内核原型（C1–C2）

这是 [查询内核](../architecture/query-kernel.md) 路线 C 的第一阶段。

- `kernel/` 是 Rust 服务，基于 Apache DataFusion。它从 PostgreSQL 载入一个发布投影的快照，然后执行 TypeScript 规划层编译出的 Object Set 计划。
- `packages/runtime/kernel/` 是规划层和客户端。

**目前还没有任何运行路径调用内核。** Gateway、Worker 和 Indexer 继续只用参考实现。

## 构建与测试

```bash
cargo build --release --manifest-path kernel/Cargo.toml
EIGOS_KERNEL_BIN=$PWD/kernel/target/release/eigos-kernel npm test -- --suite=46
```

- **服务启动：** 服务只监听 `127.0.0.1`。端口由 `EIGOS_KERNEL_PORT` 指定，不设置时随机分配，启动后输出一行 `kernel_listening` JSON 报告实际端口。
- **测试套件：** `tests/46-query-kernel.test.ts` 在同一份数据上分别用参考实现（`ObjectSets.evaluate`、`aggregate`）和内核执行同一批表达式，逐项比较结果。没有 `EIGOS_KERNEL_BIN` 时，只运行回退测试。
- **CI：** 在套件 46 的 job 里先构建内核，再运行这个套件。

## 覆盖范围

规划层只编译与参考实现可证明等价的部分，其余返回 `undefined`，调用方继续使用参考实现。

- **集合：**
  - `query`：仅限具体对象类型，支持 `where`、`filter`、`from`；
  - `refs`：跳过不存在的对象、未知类型和不可读类型，与参考实现相同；
  - `union`、`intersection`、`difference`；
  - `traverse`：多跳，集合可以混合类型，每一步按每个源类型分别导航。
- **谓词：**
  - `eq`、`ne`、`in`、`all`、`any`、`not`；
  - 数值之间的 `gt`、`gte`、`lt`、`lte`；
  - 字符串的 `contains`。

  谓词按参考实现的二值语义翻译：缺失与 null 相同，`ne` 对缺失值成立，`not` 不会遇到未知值；类型不符的字面量折叠为常量。
- **字段：** 存储标量字段（字符串、整数、数值、布尔），以及下面说明的派生属性。
  - 字段可见性用参考实现的 `Access.cellRule` 判断，副作用与 `cellSql` 相同。
  - 对当前主体整列不可见的字段，在谓词和聚合里一律当作 null。
  - 带单元格策略的字段，只在策略允许的行上显示原值。
- **行安全：** 内核读每个类型的表时都套用同一条行谓词。行谓词来自参考实现的 `Access.rowRule`，即 `rowSql` 的结构化形式，副作用也相同，覆盖三种情况：
  - 对象策略：`equals`、`subject` 和 `member` 三种条件，按 `all`、`any` 组合；
  - 标记：对象的标记必须都在主体的标记里；
  - 模型许可级别：行分级的等级不高于许可，分区都在许可之内；标记都在可用标记里。
- **只能走参考实现的类型：**
  - 文档分块和过程日志要借助别的对象过滤行，仍然只由参考实现执行。
  - 带属性级分级标签的类型也一样。参考实现在每个读到的行上，只为行里实际存在的属性记录该标签；内核不记录一行有哪些属性。

  行规则为 FALSE 的类型不贡献任何行，与参考实现相同。
- **输出：**
  - 分页：按 `canonical(ref)` 排序；内核为每个对象预先计算等价的排序键。
  - 总数。
  - 聚合：对单一类型做 `count`、`sum`、`min`、`max`、`avg` 和 `groupBy`，分组按首个成员出现的顺序排列。
- **出口分级与依赖：** 内核报告参考实现求值同一个集合时会读取的每一行，而不只是最终成员：
  - 每个节点的成员，包括遍历的起点集合、每一步的目标，以及集合运算的每个操作数；
  - 过滤条件用到派生属性时，类型的全部可读行（参考实现先读出全部候选再过滤）；
  - 这些行的派生属性沿关系读到的每一层目标。

  对每个类型，内核返回读到的行数、最高的行分级等级、全部分区，以及这些行带的全部标记。客户端把这些与文档分级、类型分级合并后记录一次，并记下读到的标记，效果与参考实现逐行读取相同。
  - 带对象策略的类型，内核还返回读到的全部行 id，客户端为每一行记录依赖。这类行超过 10,000 个时，交回参考实现，由它决定能否完整求值。
  - 有些行是参考实现连同派生值一起读取的。只要内核读到这样的行，客户端就记录这些派生属性的可见性检查。

## 派生属性

内核按参考实现的 `DerivedProperties` 计算派生属性的值，用在谓词和聚合里。返回对象的值仍由参考实现补读，所以结果里的派生值总是来自参考实现。

- **表达式：** 字面量、属性、四则运算、关系聚合。
  - 属性：存储字段按单元格遮罩读取，也可以是同一类型的另一个派生属性。
  - 关系聚合：`count`、`select`、`sum`、`min`、`max`、`avg`。
    - 每一步只到达可见的目标并去重。
    - 链接分级标签不可见时，这一步什么也到达不了。
    - 关系聚合的值可以是目标类型的存储字段或派生属性。
- **值语义：**
  - 运算数为 null 时结果为 null，除以零得 null；
  - `count` 在没有目标时为 0；
  - 其他聚合只计算非空值，没有值时为 null。
  - 非整数之和的末位可能因求和顺序与参考实现不同。
- **何时计算：** 参考实现读取一行时会计算这一行的全部派生属性，所以只要内核读取某个类型的行，规划层就登记这个类型的全部派生属性。下列任一情况，整个集合都交回参考实现：
  - 有派生属性无法编译，或者对当前主体不是直接可见（整列不可见或带单元格策略）；
  - 路径经过 Interface（`as`）；
  - 引用嵌套字段；
  - 属性 schema 除了类型和数值上下限之外还有别的约束。
- **参考实现会失败的行：** 内核为每个派生值逐行标记参考实现会抛错的情况。只要被读取并需要求值的行里有一个命中，整个请求就交回参考实现，由它报告自己的错误。这些情况是：
  - 运算结果不是有限数；
  - `sum` 或 `avg` 溢出；
  - `select` 到达不止一个对象；
  - 某一步从一个对象到达超过 10,000 个对象；
  - 值违反属性 schema：整数超出安全整数范围，或数值越过上下限。
- **不复现的限制：** 参考实现每次派生求值最多 50,000 次操作，这是资源上限而不是语义，内核不复现。

## 等价标准

以下对比在同一个出口作用域里进行，也就是 `Access.measureEgress`：
- 结果、记下的出口分级和读到的标记必须一致；
- 行依赖和类型级依赖（`view_objects` 与安全摘要）必须一致；
- 字段依赖必须是参考实现的子集。参考实现会读取每一行的全部声明字段；内核记录谓词和聚合读的字段，以及它返回的对象的字段。

类型级检查在规划时完成，输入为空时也照常进行：
- 包括目标类型、链接定义、链接与类型的分级标签；
- 参考实现遇到没有可处理的行时会跳过这些读取，于是记录得比内核少；
- 内核路径因此至少记录参考实现记录的内容，不会更少。

以下各项与参考实现完全一致：引用、顺序、总数、revision、每个有值的属性，以及聚合结果。

缺失值与 null 视为同一个 Ontology 值。参考实现自己会因表达式形态不同，把缺失值写成不存在的键、`undefined` 或 `null`。

## 基准

在本机 Docker 的 PostgreSQL 17 上测量。数据规模：
- Route 和 RideRequest 各 N 个，Place 为 N/10 个；
- 每个请求有一条 `RequestRoute`，每条路线有一条 `RouteOrigin`。

表中取每个用例的第二次运行；"内核"一列包含 HTTP 往返和补读页内对象的时间。

| 用例 | N = 100,000 参考实现 | N = 100,000 内核（引擎） | N = 1,000,000 参考实现 | N = 1,000,000 内核（引擎） |
| --- | --- | --- | --- | --- |
| 过滤 0.5% 后取首页 | 167 ms | 58 ms（6.7） | 8.9 s | 49 ms（9.9） |
| 从 0.5% 的请求走 1 跳 | 121 ms | 43 ms（6.8） | 759 ms | 77 ms（30） |
| 走 2 跳 | 60 ms | 26 ms（6.9） | 889 ms | 77 ms（35） |
| 0.5% 按 lanes 聚合 | 110 ms | 6.7 ms（4.3） | 8.5 s | 14.6 ms（11.5） |
| 全部 Route 按 lanes 聚合 | 20.8 s 后超出 10,000 对象上限 | 12.9 ms（10.8） | 26 分钟后超出上限 | 86 ms（80） |
| 全部 Route 取首页 | 20.5 s 后超出上限 | 44 ms（6.8） | 未运行 | 83 ms（32） |

内核载入耗时与数据量：

| N | 对象 | 边 | 载入耗时 | Arrow 缓冲区 |
| --- | --- | --- | --- | --- |
| 100,000 | 21 万 | 20 万 | 2.2 s | — |
| 1,000,000 | 210 万 | 200 万 | 22 s | 409 MB |

- 409 MB 是按缓冲区容量统计的上限。macOS 上测到的常驻内存受内存压缩影响，偏低且不可信，Linux 上的实测放在 C6。
- 内核端到端时间的大部分花在逐个补读页内对象上，批量补读属于 C4。

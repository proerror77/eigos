# 共用属性、关系与任务事实读取

EIGOS 使用同一 `ServiceRequest / GoalContract` 保存用户目标。活动、旅行和购物复用查询、约束、授权与验收机制；具体业务对象保留自身含义，不为每个场景再建立一套 Context 或安排中心。

## 定义、事实与应用分别复用

- 属性语义通过接口集中定义；具体属性名用 `propertyMap` 映射，关系名用 `linkMap` 映射。映射不会创建另一份属性值或关系。
- 稳定实体按可靠来源身份复用。不同来源同名不代表同一实体；历史来源观察和当前业务对象分开。
- 应用沿当前目标已选对象读取所需字段，只有缺失、过期或不适用的数据才成为后续补证需求。读取本体不自动调用供应商。

当前共用读取接口：

| 接口 | 含义 | 重要边界 |
| --- | --- | --- |
| `ObservedFact` | 来源观察时间、有效期及可选的请求／主体版本 | 当前观察有效不等于履约完成 |
| `MonetaryFact` | 金额、币种、金额单位、计价口径及价格性质 | major/minor、不同币种、单价/总价不能直接混比；未知口径保持未知 |
| `Located` | 对象明确的地点关系 | 不把酒店名或活动名当成坐标；关系缺失时返回缺口 |
| `OriginDestination` | 行程起点与终点两个独立角色 | 航班出发机场不是用户当前位置 |
| `Scheduled` | 对象代表的业务时间区间 | 开始时间不自动等于登机、入场或交付截止 |
| `Addressable` | 复用已有地址值契约 | 公共地点与私有地址保留各自权限，不合并身份 |

在本仓库中，`propertyCompatibility: structural_v1` 是显式采用结构化兼容检查的接口。说明文字和来源标签可以不同；字段类型、验证约束、读写权、保密限制和派生行为仍需兼容。有限枚举与更窄的标量约束可以实现较宽的接口；有明确 date-time schema 的字符串可以通过时间视图读取，普通字符串和仅日期字段不因此成为时间戳。未声明该模式的历史接口继续使用原校验合同。

`projectionOnly: true` 表示只读视图：不能声明动作约束或引入新的必需存储关系。新增此类视图不改变原对象的数据校验指纹，映射本身仍进入发布摘要并受元数据权限控制。已有执行接口的动作映射规则保持独立；只读视图不产生执行能力。结构兼容不能证明两个字段业务含义相同，具体映射仍须通过来源说明和业务场景验证。

## 使用同一个读取入口

`query_ontology` 支持通过接口读取已知引用：

```json
{"object":{"type":"RideEstimate","id":"实际读取到的ID"},"as":"MonetaryFact","select":["amount","currency","amountUnit","priceKind","priceBasis"]}
```

关系映射使用相同方式，例如具体 Event 的 `venue` 与 HotelProperty 的 `location` 都可通过 `Located.location` 读取。内部仍查询各自实际 Link，并检查实际端点权限。

规划会话还支持有界的 `facts` 批量请求：

```json
{
  "facts": [
    {"key":"destinationName","query":{"from":{"type":"HotelProperty","id":"实际酒店ID"},"as":"Located","link":"location","select":["name"]}},
    {"key":"destinationAddress","query":{"from":{"type":"HotelProperty","id":"实际酒店ID"},"as":"Located","link":"location","select":["address"]},"requiredFields":["address"]}
  ]
}
```

这两个请求合并为一次当前关系查询，返回同一地点引用的不同字段投影。每批最多八个请求、每项最多十个对象，总结果有字节上限。`requiredFields` 指定必需内容；空结果、缺少字段或观察核验失败会出现在 `needsRefresh` 中。未读完分页单独返回 `needsContinuation` 和准确的 continuation 查询，不能误当成需要再次访问供应商。

`evaluate: true` 通过 `businessFactStatus` 校验实现 `ObservedFact` 的对象，并沿共用关系检查版本。查询上下文的技术信息位于后台来源元数据，不能作为普通业务属性读取。新来源结果取代旧结果后，旧记录仍保留为历史证据。

`read_task_context` 可在首次读取时附带同样的 facts 请求；后续只读取新增缺口时使用 `query_ontology.facts`，避免再次搬运整个目标、指令与定义。模型必须引用实际成功的读取回执；它不能拿历史上下文或缓存内容冒充当前证据。

缓存只存在于一次同步、有界读取内。后续决策重新检查权限与数据版本，不复用旧授权。`present` 表示所选字段已取得；只有请求了观察核验且核验通过，才说明该观察满足相应证据条件。补证需求本身不授权来源调用、下单或付款。

## 三个场景共用同一套机制

活动读取 Event 的时间与地点，交通引用同一 Place；东京旅行读取 TravelLeg 的起终点与时间，并引用酒店地点；购物读取已选 ProductVariant、Offer 与 SavedAddress。各步骤继续使用原目标和已选对象，不重新搜索名称来恢复已知身份。

合成测试通过真实规划会话入口验证：每组四项属性／关系需求合并为三次查询；再次读取复用同一对象身份；酒店地点变化使相关旧规划快照失效；缺少坐标只报告坐标缺口。测试不调用供应商，也不证明机票、淘宝或真实交通服务已接通。

## 对照 Palantir 反模式

[官方反模式文档](https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns/)作为建模检查依据：

- 来源系统的读记录保留作技术证据，默认业务发现优先展示可复用实体；不按来源复制同一业务主体。
- 技术查询上下文留在后台；进入业务属性的字段必须有明确使用目的。
- 不用万能对象容纳活动、机票与商品；真正共有的形状通过接口表达。
- 数据映射、纯计算、业务动作和定时／事件驱动分别承担职责；不新增只为计算或读取单字段的业务动作。
- 业务主体保持稳定身份；历史观察作为关联证据保留，不把每次查询误当成新主体。
- 地点角色、金额单位、时间含义和状态阶段保持明确，不用模糊名称掩盖差异。

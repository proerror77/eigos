# 商户面向 Agent 的服务接入现况

核验日期：2026-10-16。目的：支持 EIGOS Pitch Deck 的问题陈述与第一阶段策略。采用三个官方平台样本，未进行商户总体抽样；不能据此得出“大部分商户未准备好”的比例、市场规模或跨行业普及率。

## 用户纠正后的接入主体与策略

当前第一阶段的接入对象是**聚合厂商/平台**，不是逐家接入最终履约商户。EIGOS 利用聚合方已建设的供给、订单和相关接口减少初期接入工作；长期再向终端商户和服务提供者推广直接接入。聚合接入与直接接入可以并存，用户未指定替代时间表。

因此应区分两个维度：产品路线是“日常服务 → 复杂场景与信任 → 主动服务”；供给拓展路线是“复用聚合供给 → 逐步推广终端接入”。不能把二者合成一个固定阶段表。

下面官方样本分别涉及供应链接口、支付与商户 Agent 适配、商业 SaaS 平台，角色不同，不能统称为同一种聚合厂商，更不能把 EIGOS 接入这些平台描述成已逐家直连所有终端。现况研究仍可支持能力与准入差异，但“先逐商户接入”的策略不符合用户此次明确方向，以下旧建议应据此理解。

## 核心判断

现有平台呈现不同准备程度：有些已有面向 Agent 的发现、结账等能力；有些拥有传统业务 API，但须合作准入和适配；另一些服务的接入范围仍需逐项查明。可支持的判断是：**现有业务能力与外部 Agent 可直接使用的完整服务链路之间，存在授权、接口适配和生命周期衔接工作。**

这里的完整链路包含服务发现与条件、价格/库存或时段、订单创建、支付衔接、履约查询、变更/取消、退款与售后结果。不能把其中一个环节的可用状态推广到整条链路。

| --- | --- | --- | --- |
| [支付宝：商品和生活服务商户接入智能体平台](https://aipay.alipay.com/docs/agent-pay/skillpay.html)（页面更新 2026-10-09） | PC 路径要求商户接入电脑网站支付，并在原有系统外增加商家下单 Skill，再把支付阶段交给支付处理能力。 | 商户已有网站和收款能力后，仍有供 Agent 使用的业务适配工作。 | 支持支付宝不等于 EIGOS 已取得该商户选品、订单与售后权限。此页未覆盖的能力不能直接判定不存在。 |
| [京东 IOP 官方对接指南](https://static-iop.jd.com/) | 包含商品、价格、库存、订单、支付、售后等模块；需要项目申请取得凭证，商品可采购范围还涉及商品池及合同等条件。 | 可以复用既有供应链 API；接入资格、业务范围和具体模块对接需要落实。 | 这是工业采购渠道，不能代表普通消费者全站商品或任意商家的接口情况。 |
| [Shopify：Carts and checkout for agents](https://shopify.dev/docs/agents/carts-and-checkout) | 已有 Cart MCP、Checkout MCP 与浏览器内 WebMCP 路径；直接结账有资格条件，需要升级/复核时转到商户结账页；访问与限流依 Agent 身份区分。 | 有成熟方向可以直接适配，不应假设整个供给侧从零开始；仍需能力协商、认证及接续。 | 不能声称所有 Agent 均可直接无人确认结账，或仅凭结账能力就证明退款全流程可调用。 |
| [Shopify：Checkout MCP 教程](https://shopify.dev/docs/agents/get-started/checkout) | 支持创建和完成 checkout；后续步骤另列订单查询、webhook，以及 UCP 订单中的退款/退货等调整信息。 | 订单和售后状态已进入标准化范围，应验证具体动作与结果是否开放。 | 订单中的退款状态不等于任意客户端都能发起、跟进并完成退款。 |

这些资料证明供给端已经存在真实能力，也证明各路径的准入、适配和后续步骤有差别。它们不提供全体商户采用率。

## 将“没准备好”拆成可检查的问题

1. **信息是否可用**：能否取得实时服务范围、价格、库存或可预约时段、取消与退款条件。
2. **业务动作是否开放**：是否具备创建/查询订单、修改/取消及售后动作，而不只是商品介绍或客服聊天。
3. **谁能调用**：接口面向内部系统、签约渠道还是外部 Agent；EIGOS 的身份和任务授权是否被接受。
4. **调用是否可恢复**：请求超时后能否查到原订单，避免重复下单或付款；处理中间态是否可持续跟踪。
5. **售后是否贯通**：能否提交申请、补充材料、回应商户要求，并查到最终退款或拒绝事实。

这些是后续逐商户调查框架，不是断言每家都缺少上述能力。

## EIGOS 的第一阶段建议

先在衣食住行中挑选有明确需求、已有正式接入路径、可读回结果的服务。为每个提供方记录逐动作覆盖范围：可查询、可下单、可接续支付、可查履约、可发起售后、可核对退款。不要使用一个“已接入”标签代替全部状态。

优先复用官方 Agent 接口或已授权业务 API；需要时补业务适配器、状态映射与任务上下文。获允许的网页或人工协作可作为补充路径，但应明确成本、维护和能力限制。缺少权限或正式入口时，走合作准入，不能靠 MCP 包装凭空取得业务权限。

第一阶段的可验证产出应是一组能实际执行并跟进的服务，而非仅有接口列表。可记录每项服务的真实完成率、售后闭环覆盖、人工介入、每个新增商户的适配成本和接口故障恢复情况；本次没有填造指标数值。

## 对产品定位与长期价值的影响

EIGOS 可以承担两侧衔接：面向用户/PA 接收目标与上下文；面向商户把分散能力组织成可授权、可执行、可跟进的任务服务。

这是机会假设，仍需检验需求、接入成本和付费意愿。随着平台原生 Agent 能力改善，单纯接口封装的价值可能缩小。长期差异应继续在用户场景理解、多服务协调、履约与售后经验、以及围绕用户积累的可信服务关系上验证，衔接已有三阶段路线。

## 可用于 deck 的表述

> 商户业务系统与 Agent 之间，仍存在接入缺口。EIGOS 将已有服务逐步连接为用户 Agent 可委托、可执行、可持续跟进的服务网络。

不采用“绝大多数没有 API”“全行业尚未准备好”“支付平台只管付款”等未经证实或过于宽泛的表达。

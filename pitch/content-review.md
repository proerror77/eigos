# EIGOS Pitch Deck 内容依据与修订

核对日期：2026-10-15。范围：Eigo8 项目及直接相关的产品架构、服务完成、支付和执行试点对话。此文件记录 deck 的叙事依据，不替代品牌说明、产品设计文档或运行证据。



## 2026-10-16：用户明确三阶段产品路线（当前方向）

1. **日常服务接入**：先连接衣食住行的服务，让用户需求可以推进到查询、下单购买、交付与可支持的售后动作。
2. **复杂场景与个人信任网络**：旅行、餐厅预订等涉及多方、变更及个人偏好的场景；网络不止包含商家，而是围绕用户持续建立可信赖的服务关系。
3. **主动服务**：当 Agent 足够了解用户，根据过去想法与偏好预判需求，提前询问是否需要，或在已有授权内提前执行。

该顺序由用户明确提出。没有附加实施日期或已具备能力的承诺。信任关系如何建立、评价和撤销仍待产品细化；deck 中的商户、专业服务者、协作 Agent 是对网络参与方的说明，不是已签约名单。第三阶段不把预测当作新的付款/执行授权，也不把 Personal Agent 的长期了解等同于复制完整私人记忆。

已同步中英文 deck：封面与角色页强调围绕用户；原 CSV 独立页改为第二阶段信任网络；路线图改为三阶段。CSV 仍保留在进展页作为技术验证，不再充当第一阶段商业切口。进展页保留有日期的 2026-10-15 快照，本次不重跑运行验证。

以下为此前修订记录，时间较新的产品方向优先。

## 后续澄清：需求、商户服务与持续售后

2026-10-15 用户在本次对话进一步明确：EIGOS 连接用户与商户。理解需求后寻找和执行相关服务，包括直接推进下单购买；购买以外还有售后动作。退款不是给出建议或提交申请即结束，而是继续完成材料补充、商户沟通、进度查询与结果核对。

本轮两版 deck 相应改动：

- 封面和角色分工明确“需求 → 服务匹配 → 业务执行 → 售后”。Personal Agent 是委托/沟通入口，不把项目缩成 Agent 问答或单纯验收服务。
- 完整链路独立讲述理解需求、寻找匹配、下单购买、履约交付、售后跟进。
- 售后独立一页，以退款为例区分核对要求、提交申请、持续跟进、实际结果。负责后续执行不等于保证商户批准退款；拒绝或待处理须如实返回。
- 本体仍用于定义业务对象、规则、动作与验收，现有支付体系继续复用。
- CSV 保留为技术验证场景，不成为项目的唯一商业定位。

## 采用的主线

Personal Agent 理解用户并提供必要上下文与授权；通过 MCP 或 A2A 委托 EIGOS。EIGOS 基于业务本体澄清需求、研究、规划、选择服务、执行并验收。使用本体的目标是提高任务完成稳定性；稳定性仍需真实连接器、状态与权限控制、幂等、故障恢复和实际证据。

## 2026-10-16：补入商户准备程度分析

用户提出供给侧尚未为 Agentic 经济完整接入订单等业务能力。本次核验支付宝、京东 IOP 和 Shopify 官方资料，形成 `merchant-readiness-2026-10-16.md`。

采用的结论是“已有业务能力与 Agent 可用的完整链路之间存在接入差异与适配工作”，没有将三个样本推广为“大部分商户未准备好”的比例结论；保留 Shopify 已有 Agent 商务能力的反例。Deck 新增现况页并放在封面之后，替换原服务扩展单页，保持 12 页与两版一致。原服务扩展的定义、绑定与规则仍是架构背景，不因版面替换改变。

第一阶段的机会在于逐项取得权限、适配动作并连接实际业务生命周期。长期仍需验证场景协调、履约售后和围绕用户的可信关系，不能只依赖商户接口暂时缺失。
